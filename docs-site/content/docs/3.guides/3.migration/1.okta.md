---
title: Migrating from Okta
description: Move an application and its users from Okta to auth-service, with the differences that matter in code, a user import script, and a dual-issuer cutover. Includes notes for Keycloak.
---

Okta and auth-service both speak OpenID Connect, so an application that uses a standard OIDC library moves with a configuration change plus a few deliberate adjustments. What does **not** move automatically is the user base: passwords, MFA factors and Okta-specific features have no export path. This guide shows what maps, what does not, and a low-risk way to cut over.

::callout{icon="i-lucide-triangle-alert" color="warning"}
Check the [scope](#what-moves-and-what-does-not) first. auth-service has **no SAML, no LDAP / Active Directory federation, no SCIM provisioning and no Okta Workflows equivalent**. If an application depends on one of them, it cannot move yet.
::

## What moves, and what does not

| In Okta | In auth-service | Notes |
|---|---|---|
| OIDC web / SPA / native app | **Application** (confidential or `isPublic`) | Create it again; client IDs and secrets are not portable |
| Service app (client credentials) | Confidential application, `client_credentials` grant | Token scope is `m2m`; see [third-party guide](/docs/guides/integration/third-party-app#8-service-to-service-calls) |
| Authorization server and its audience (`api://default`) | The service itself; audience = the application `url` (`resource` parameter) | One issuer for every application |
| Custom scopes | [Roles and permissions](/docs/guides/administration/roles-and-permissions) | Scopes are a fixed list (`openid`, `profile`, `email`, `phone`, `offline_access`, `roles`, `permissions`, `features`, `org`, `wallet:self:read`) |
| Groups and the `groups` claim | **Roles**, in the `roles` claim | One role per user per application |
| Custom claims (expressions) | `permissions`, `features`, `plan`, `org_id`, and per-application `metadata` (static string claims) | No expression language |
| Users, profile attributes | Users (name, e-mail, phone, company, position, address) | Imported through the API or CSV |
| Passwords | Not exportable | Users set a new one |
| MFA (Okta Verify, SMS, WebAuthn) | TOTP authenticator app with backup codes | Users enroll again. Passkey endpoints exist server side, with no enrolment screen yet |
| Social / IdP routing | Google and GitHub, per-application allow-list | Other providers are not wired |
| Self-service registration | `allowRegister` per application | |
| Sign-in widget, branding | Hosted pages, [custom templates](/docs/guides/administration/custom-templates) | |
| Admin Console, Management API (SSWS token) | Admin interface and [admin REST API](/docs/reference/api-reference) (session cookie) | No API tokens for the admin API |

## What changes in your code

| | Okta | auth-service |
|---|---|---|
| Issuer | `https://<org>.okta.com/oauth2/default` | `https://auth.example.com` (the root, no path) |
| Discovery | `<issuer>/.well-known/openid-configuration` | `<issuer>/.well-known/openid-configuration` |
| Authorize | `<issuer>/v1/authorize` | `/api/auth/oauth2/authorize` |
| Token | `<issuer>/v1/token` | `/api/auth/oauth2/token` |
| Keys | `<issuer>/v1/keys` | `/api/auth/jwks` |
| UserInfo | `<issuer>/v1/userinfo` | `/api/auth/oauth2/userinfo` |
| Revoke / introspect | `<issuer>/v1/revoke`, `/v1/introspect` | `/api/auth/oauth2/revoke`, `/api/auth/oauth2/introspect` |
| Logout | `<issuer>/v1/logout` | `/api/auth/oauth2/end-session`, off by default per application (`enableEndSession`) and **global** |
| Signature algorithm | RS256 | **EdDSA** (Ed25519) |
| `client_id` | Generated | The application `slug` |
| Client secret at the token endpoint | Basic or POST | **HTTP Basic** only |
| `aud` of the access token | Fixed by the authorization server | The `resource` you request (the application `url`), as an **array** |
| Scopes in the token | `scp`, an array | `scope`, a space-separated string |
| User identifier `sub` | `00u…` (Okta user id) | auth-service user id: **different** |
| Groups | `groups` | `roles` and `permissions` |
| Login name | `preferred_username` | Not issued: use `email` |
| Client id in the token | `cid` | `client_id` and `azp` |
| Refresh token | `offline_access` | `offline_access` |
| Access token lifetime | 1 hour by default | 1 hour |

Three of these cause most of the surprises:

1. **No `resource`, no JWT.** Okta always issues a JWT for its authorization server. auth-service issues one only when the request carries `resource=<application url>`; otherwise the access token is opaque.
2. **`EdDSA`.** A verifier configured for RS256 (the default of many Okta samples, `@okta/jwt-verifier` included) rejects every token.
3. **`sub` changes.** Anything keyed on the Okta `sub` (database rows, ownership, audit logs) needs a mapping, see [User identifiers](#user-identifiers).

## Migration plan

The safe order is: stand up auth-service, rebuild the configuration, import users, make your code accept both issuers, move users in waves, then retire Okta.

### 1. Prepare auth-service

- [Deploy it](/docs/getting-started/deployment) on its final host name: `BETTER_AUTH_URL` becomes your new issuer, and it should not change later.
- Configure [SMTP](/docs/guides/administration/email-setup): imported users receive a verification e-mail, and every user will need the password reset flow.
- Apply your branding with `APP_NAME`, `APP_LOGO_URL` or [custom templates](/docs/guides/administration/custom-templates).
- Decide the MFA policy: `isMfaRequired` per application blocks token issuance for users without a second factor.

### 2. Rebuild each application

For every Okta OIDC application:

1. Create the [application](/docs/guides/administration/managing-applications): `slug` (the new `client_id`), `url` (your API audience), the **same redirect URIs**, `isPublic` for SPAs and native apps.
2. Turn the Okta groups that this application uses into [roles](/docs/guides/administration/roles-and-permissions), and what the group allowed into permissions. Mark the common role `isDefault`.
3. Replace custom claims: plans and feature flags become [subscription plans](/docs/guides/administration/subscription-plans); a static value (a tenant code, say) becomes an application `metadata` entry.
4. If the app signs users out of Okta (`/v1/logout`), decide whether that must become a global sign-out (`enableEndSession` and `postLogoutRedirectUris`) or just a local one. See [sign out](/docs/guides/integration/third-party-app#6-sign-out).

### 3. Export users from Okta and import them

Okta does not release password hashes, so users are created **without** a password. The import creates each account with a random temporary password (returned once in the response; do not hand it out), and sends a verification e-mail when SMTP is configured.

This script pages through the active users of Okta and imports them 500 at a time. Admin routes use a session cookie: sign in with an administrator account that has no second factor enrolled, or use a dedicated service administrator.

```typescript
const OKTA = process.env.OKTA_ORG_URL!;     // https://acme.okta.com
const AUTH = process.env.AUTH_URL!;         // https://auth.example.com

async function* oktaUsers() {
  const headers = { Authorization: `SSWS ${process.env.OKTA_API_TOKEN}`, Accept: "application/json" };
  let url: string | null = `${OKTA}/api/v1/users?limit=200&filter=${encodeURIComponent('status eq "ACTIVE"')}`;
  while (url) {
    const res = await fetch(url, { headers });
    if (!res.ok) throw new Error(`Okta answered ${res.status}`);
    yield* (await res.json()) as Array<{ profile: { email: string; firstName?: string; lastName?: string } }>;
    url = /<([^>]+)>;\s*rel="next"/.exec(res.headers.get("link") ?? "")?.[1] ?? null;
  }
}

const signIn = await fetch(`${AUTH}/api/auth/sign-in/email`, {
  method: "POST",
  headers: { "Content-Type": "application/json", Origin: AUTH },
  body: JSON.stringify({ email: process.env.AUTH_ADMIN_EMAIL, password: process.env.AUTH_ADMIN_PASSWORD }),
});
if (!signIn.ok) throw new Error(`Sign-in failed: ${signIn.status}`);
const cookie = signIn.headers.getSetCookie().map((c) => c.split(";")[0]).join("; ");

async function importBatch(users: { name: string; email: string }[]) {
  const res = await fetch(`${AUTH}/api/admin/users/import`, {
    method: "POST",
    headers: { "Content-Type": "application/json", Origin: AUTH, Cookie: cookie },
    body: JSON.stringify({ users }),
  });
  if (!res.ok) throw new Error(`Import answered ${res.status}`);
  const { created, failed, results } = await res.json();
  console.log(`created ${created}, failed ${failed}`);
  for (const r of results) if (r.status === "error") console.warn(r.email, r.message);
}

let batch: { name: string; email: string }[] = [];
for await (const u of oktaUsers()) {
  const name = [u.profile.firstName, u.profile.lastName].filter(Boolean).join(" ") || u.profile.email;
  batch.push({ name, email: u.profile.email });
  if (batch.length === 500) { await importBatch(batch); batch = []; }
}
if (batch.length) await importBatch(batch);
```

A rerun is safe: addresses that already exist are reported as errors and skipped. For a small user base, the **Users → Import users** button of the admin interface takes a CSV with the columns `name`, `email`, `password` (optional) and `role`.

Then give the users access to each application, with their role. Group the users by target role and grant them in bulk (up to 1000 per call; resolve user ids with `GET /api/admin/users?search=<email>`, 100 users per page):

```sh
POST /api/admin/applications/:id/users/bulk
{ "userIds": ["<id>", "…"], "roleId": "<role id>" }
```

Okta lets a user belong to several groups, while an access record carries one role: pick the most privileged role, or create a combined one.

### 4. Make your code accept both issuers

Keep Okta working while users move. Pick the verification setup from the token's `iss`, then verify fully against that issuer. Reading `iss` before verifying only selects the configuration; nothing is trusted until `jwtVerify` succeeds.

```typescript
import { createRemoteJWKSet, decodeJwt, jwtVerify } from "jose";

const issuers = {
  "https://auth.example.com": {
    jwks: createRemoteJWKSet(new URL("https://auth.example.com/api/auth/jwks")),
    algorithms: ["EdDSA"],
    audience: "https://api.acme.com",          // the application url
  },
  "https://acme.okta.com/oauth2/default": {
    jwks: createRemoteJWKSet(new URL("https://acme.okta.com/oauth2/default/v1/keys")),
    algorithms: ["RS256"],
    audience: "api://default",
  },
} as const;

export async function verify(token: string) {
  const iss = decodeJwt(token).iss;
  const cfg = iss ? issuers[iss as keyof typeof issuers] : undefined;
  if (!cfg) throw new Error("Unknown issuer");
  const { payload } = await jwtVerify(token, cfg.jwks, { issuer: iss, audience: cfg.audience, algorithms: [...cfg.algorithms] });
  return {
    issuer: iss,
    userKey: payload.email as string,                                // see "User identifiers"
    roles: (payload.roles ?? payload.groups ?? []) as string[],      // groups on Okta, roles on auth-service
  };
}
```

On the sign-in side, replace the Okta SDK by a generic OIDC client (see [Integrating a third-party application](/docs/guides/integration/third-party-app)): new issuer, new `client_id` (the slug), PKCE as before, plus `resource=<application url>`. A typical diff:

| Before (Okta) | After (auth-service) |
|---|---|
| `issuer: "https://acme.okta.com/oauth2/default"` | `issuer: "https://auth.example.com"` |
| `clientId: "0oa1b2c3…"` | `clientId: "acme-app"` |
| `scopes: ["openid","profile","email","groups"]` | `scopes: ["openid","profile","email","roles","permissions"]` plus `resource` |
| `@okta/jwt-verifier`, RS256 | `jose`, EdDSA |
| `claims.groups.includes("Admins")` | `claims.roles.includes("admin")` |

### User identifiers

The `sub` of an auth-service token is not the Okta `sub`. To keep your own records attached to the right person:

1. Add a column for the new identifier next to the Okta one.
2. On a user's first sign-in through auth-service, find your record by **e-mail** and store the new `sub` in it. From then on, look users up by `sub`.
3. Do this only when the token says `email_verified: true`. Imported accounts are unverified until the user follows the e-mail link, which is what stops someone from claiming an address they do not own.

### 5. Move users in waves

1. Tell users what will change: new sign-in page, **set a new password** with "Forgot your password?", **enroll the authenticator app again**.
2. Switch one application at a time (or one group of users) by pointing the sign-in side to auth-service; the dual-issuer verifier keeps old sessions valid.
3. Watch the [login history](/docs/guides/administration/login-history) to see who has moved.
4. For users who never come back, decide whether to import them later or not at all.

The password reset and verification e-mails are rate limited, so avoid sending thousands at once: let users trigger them when they sign in.

### 6. Retire Okta

When the login history shows no remaining traffic through Okta, remove the Okta issuer from the verifier, delete the Okta applications, and keep the user mapping table for as long as your audit trail needs it.

## Coming from Keycloak

The plan is the same: OIDC to OIDC, users re-created without passwords, dual issuer during the transition. The differences are in the vocabulary:

| In Keycloak | In auth-service |
|---|---|
| Realm | The whole instance. Users are global; each application grants them access separately. Several realms with overlapping users need merging (the e-mail is the unique key) or separate instances |
| Issuer `https://kc/realms/<realm>` | `https://auth.example.com` |
| Endpoints under `/protocol/openid-connect/` (`auth`, `token`, `certs`, `userinfo`, `logout`) | The `/api/auth/…` endpoints listed above; keys at `/api/auth/jwks` |
| Realm roles and client roles, in `realm_access.roles` and `resource_access.<client>.roles` | The application's roles, in the flat `roles` claim |
| Groups, client scopes and mappers | Roles, permissions, plans and application `metadata`; the scope list is fixed |
| RS256 by default | EdDSA |
| `aud` set by an audience mapper (often `account`) | `aud` is the requested `resource` |
| Client secret: Basic or POST | HTTP Basic |
| Credentials in a realm export (PBKDF2 or Argon2 hashes) | Cannot be imported: users reset their password |
| User federation (LDAP, Kerberos), identity brokering, SAML clients, UMA / authorization services, token exchange | Not available. Social login is limited to Google and GitHub |

Export users from the Keycloak admin API (`GET /admin/realms/<realm>/users?first=0&max=100`) and feed the same import endpoint as above.
