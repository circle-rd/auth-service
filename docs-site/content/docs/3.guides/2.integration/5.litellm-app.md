This guide is for developers of an application that lets its users run LLM calls or MCP tools through the [LiteLLM gateway](/docs/guides/integration/litellm-gateway). Users sign in once with auth-service; the gateway recognises them from their access token and bills their **credit wallet**. Your application holds no provider API key and no billing logic.

Read [Integrating a third-party application](/docs/guides/integration/third-party-app) first: registration, sign-in and token verification work exactly the same here. This page adds what is specific to the gateway and to the wallet.

```
                        1. sign in (resource = your app, gateway, auth-service)
   User ──▶ Your app ─────────────────────────────────────────────▶ auth-service
              │                                                          ▲   ▲
              │ 2. LLM / MCP call, Bearer <gateway token>                │   │
              ▼                                                          │   │ debit, reported by the
          LiteLLM gateway ── 3. may this user spend? ────────────────────┘   │ gateway after each call
              │              (402 when out of credit)                        │
              └──────────────────────────────────────────────────────────────┘
              Your app ── 4. GET /api/user/wallet (balance, canSpend) ──────▶ auth-service
```

## How the wallet works

- **One wallet per user**, in euros, shared by every application and every call that goes through the gateway. It never expires.
- Amounts are integers in **micro-euros** (1 EUR = `1000000`), sent as strings.
- Before each call, the gateway refuses the user if the balance is zero or negative: **HTTP 402**. After a successful call it reports the provider cost in dollars, and auth-service debits `cost × exchange rate × (1 + margin %)`, rounded up to a micro-euro.
- The rate and the margin are set by a superadmin in the **Wallets** page. The price of each model and tool is set in LiteLLM.
- A call that finishes after the balance reached zero is still billed: the balance goes **negative** (a debt), blocks further calls, and is repaid by the next top-up.
- Staff and internal accounts can be marked **unlimited**: usage is recorded but never deducted.

## What the operator sets up

Your application needs to be allowed to reach the gateway. The administrator of auth-service does this once:

1. In the application's create / edit dialog, switch on **LiteLLM support**. It adds the gateway URL and the auth-service URL to `allowedResources`, adds the `wallet:self:read` scope, and creates a gateway **team** named after your application's slug.
2. In the LiteLLM admin interface (**Teams**), grant that team the models and MCP servers it may use, and set a budget or rate limits if wanted. A new team is closed: calls answer `403 team_model_access_denied` until models are granted.
3. Grant your users access to the application, as for any other.

The gateway and the audience URLs are described in [LiteLLM gateway](/docs/guides/integration/litellm-gateway).

## Sign users in for three audiences

Your application needs tokens for up to three different audiences:

| Audience (`resource`) | Used for | Scope |
|---|---|---|
| Your application's `url` | Your own API | those you need (`openid`, `roles`…) |
| The gateway URL (`LITELLM_PUBLIC_URL`) | LLM and MCP calls | none in particular |
| The auth-service URL (`BETTER_AUTH_URL`) | Reading the user's wallet | `wallet:self:read` |

The `resource` parameter can be **repeated** on the authorization request. The code exchange then returns a token valid for all of them, and every refresh can **narrow** it to one audience. This is the least-privilege pattern: store one refresh token, and mint a short-lived token per audience.

```typescript
const authorizeUrl = new URL(as.authorization_endpoint!);
authorizeUrl.searchParams.set("client_id", "acme-app");
authorizeUrl.searchParams.set("response_type", "code");
authorizeUrl.searchParams.set("redirect_uri", redirectUri);
authorizeUrl.searchParams.set("scope", "openid profile email roles offline_access wallet:self:read");
authorizeUrl.searchParams.append("resource", "https://app.acme.com");      // your API
authorizeUrl.searchParams.append("resource", "https://llm.example.com");   // the gateway
authorizeUrl.searchParams.append("resource", "https://auth.example.com");  // the wallet API
authorizeUrl.searchParams.set("code_challenge", challenge);
authorizeUrl.searchParams.set("code_challenge_method", "S256");
```

Exchange the code **without** `resource`: the token is then issued for the whole set (`aud` is an array). Then narrow with the refresh grant:

```python
import httpx

TOKEN_URL = "https://auth.example.com/api/auth/oauth2/token"

async def token_for(refresh_token: str, resource: str, scope: str | None = None) -> dict:
    data = {"grant_type": "refresh_token", "refresh_token": refresh_token, "resource": resource}
    if scope:
        data["scope"] = scope
    async with httpx.AsyncClient(timeout=10) as http:
        r = await http.post(TOKEN_URL, data=data, auth=(CLIENT_ID, CLIENT_SECRET))  # HTTP Basic
    r.raise_for_status()
    return r.json()  # keep the new refresh_token it returns

gateway = await token_for(refresh_token, "https://llm.example.com")
wallet = await token_for(gateway["refresh_token"], "https://auth.example.com", "wallet:self:read")
```

A refresh can only narrow what was granted at sign-in. If a token cannot be minted for the gateway or the wallet, the application is not allowed to request that resource (`invalid_target`): ask the operator to switch on **LiteLLM support**.

::callout{icon="i-lucide-triangle-alert" color="warning"}
Gateway tokens live one hour. Mint one per call or per short session; never store them. Do not use `client_credentials` for user calls: the gateway refuses tokens that carry no user, and nothing could be billed.
::

## Call the gateway

The gateway is an OpenAI-compatible endpoint: the access token is the API key.

::tabs
:::tabs-item{label="Python" icon="i-simple-icons-python"}
```python
from openai import OpenAI, APIStatusError

client = OpenAI(base_url="https://llm.example.com/v1", api_key=gateway["access_token"])
try:
    reply = client.chat.completions.create(
        model="gpt-4o-mini",  # a model granted to your application's team
        messages=[{"role": "user", "content": "Summarize this report."}],
    )
except APIStatusError as e:
    if e.status_code == 402:
        ...  # out of credit: send the user to their wallet
    raise
```
:::

:::tabs-item{label="TypeScript" icon="i-simple-icons-typescript"}
```typescript
import OpenAI from "openai";

const client = new OpenAI({ baseURL: "https://llm.example.com/v1", apiKey: gatewayToken });
try {
  const reply = await client.chat.completions.create({
    model: "gpt-4o-mini",
    messages: [{ role: "user", content: "Summarize this report." }],
  });
} catch (e) {
  if (e instanceof OpenAI.APIError && e.status === 402) {
    // out of credit: send the user to their wallet
  }
  throw e;
}
```
:::

:::tabs-item{label="curl" icon="i-lucide-terminal"}
```sh
curl https://llm.example.com/v1/chat/completions \
  -H "Authorization: Bearer $GATEWAY_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"Hello"}]}'
```
:::
::

MCP servers registered in the gateway are reached the same way, at `/mcp` or `/<server>/mcp`, with the same bearer token. Only the servers granted to your team are visible.

Only the **LLM and MCP routes** accept a user token. Administration routes (`/key/generate`, `/team/new`, `/spend/logs`…) answer `403`.

### Handle the answers

| Status | `error.type` | Meaning | What to do |
|---|---|---|---|
| `402` | `insufficient_credit` | The balance is zero or negative | Stop, tell the user, link to their wallet (see [Refill](#refill)) |
| `401` | `auth_error` | Expired or invalid token, or the application's team is blocked | Mint a fresh token; if it persists, ask the operator |
| `403` | `team_model_access_denied` or `auth_error` | Model not granted to the team, application without a team, or a non-client route | Ask the operator to grant the model, or to switch **LiteLLM support** on |
| `429` | `rate_limited` | Per-user ceilings: 120 calls per minute, 5 USD of provider cost per minute, 8 concurrent calls (defaults) | Retry with a delay |
| `503` | `wallet_unavailable` | The wallet cannot be reached and the user's balance was not read in the last minute | Retry shortly: no credit information, no spending |

The error body always has the OpenAI shape, for example:

```json
{ "error": { "message": "Insufficient credit. Top up your account to continue.", "type": "insufficient_credit", "code": "402" } }
```

## Read the wallet

With a token for the auth-service audience and the `wallet:self:read` scope:

```sh
GET https://auth.example.com/api/user/wallet
Authorization: Bearer <wallet token>
```

```json
{ "balance": "5000000", "isUnlimited": false, "canSpend": true, "currency": "eur" }
```

- Use **`canSpend`** to decide, rather than recomputing it: it is true for an unlimited account or a strictly positive balance. Check it before starting an expensive job; a call that fails with 402 in the middle of a long run is a worse experience.
- `balance / 1_000_000` is the amount in euros.
- `GET /api/user/wallet/stats?days=30` returns `{ days, total, calls, series, byApplication, byKind }`: what the user spent, per day, per application and per type (AI models, MCP tools). Use it for a usage bar.
- `GET /api/user/wallet/transactions?limit=50` returns the ledger, newest first, with a `nextCursor`.

Read the wallet on the server, with the user's token, and not more often than needed: the gateway itself caches a balance for 5 seconds, and a page that polls every 15 seconds is plenty. A failure to read the wallet should block the paid action rather than allow it.

## Consumption

Every call that goes through the gateway appears in the wallet ledger as a `usage` transaction carrying the raw quantities (model and tokens, or MCP server and tool), the dollar cost, the exchange rate and margin applied, and the calling application (your `slug`). Users see it in the **Credit** tab of their profile, administrators in the **Wallets** and **Accounting** pages.

![The Credit tab of a user's profile: balance, top-up, consumption by application and type](/screenshots/profile-credit.png)

Things to know when you price your product:

- **A model without a price is free.** LiteLLM computes the cost from its price list: a self-hosted model needs `input_cost_per_token` and `output_cost_per_token` set in LiteLLM.
- **MCP tools are billed only if the server declares a cost** (`mcp_info.mcp_server_cost_info`, in dollars).
- Charges are made **after** the call, so a burst of parallel calls on a small balance can overshoot into debt. The per-user ceilings above bound it.
- If auth-service is briefly unreachable, the gateway keeps the debits on disk and retries them with idempotency keys: a retry never charges twice.
- Your own business metrics (documents processed, seats…) are a different mechanism: [Consumption tracking](/docs/guides/administration/consumption-tracking).

## Refill

Credit is added in one of three ways:

1. **Online, by the user (Stripe).** The **Credit** tab of the profile page shows quick amounts and a free amount within `WALLET_TOPUP_MIN_EUR` and `WALLET_TOPUP_MAX_EUR` (5 to 500 EUR by default). It opens a Stripe Checkout in the customer's currency; the credit granted is the euro amount. It needs `STRIPE_SECRET_KEY` and the webhook, see [Stripe integration](/docs/guides/administration/stripe-integration).
2. **Manually, by a superadmin.** Without Stripe, the user page of the admin interface records a top-up (with the invoice reference), grants credit (with a reason), or adjusts the balance. Everything is audited in the accounting journal.
3. **Refunds and disputes** take credit back automatically, which can leave a wallet in debt.

Opening the Checkout requires the user's **session**, not a bearer token. Your application therefore does not create it: it links the user to the Credit tab, **`<BETTER_AUTH_URL>/profile`**, when `canSpend` is false or a call answers 402. `GET /api/user/wallet/topup-options` tells you whether online top-up is enabled (`{ "enabled": false, "currency": "eur", "minCents": 500, "maxCents": 50000 }`), so you can word the message accordingly: "top up your credit" or "ask your administrator".

The next call after a top-up is accepted within about five seconds.

## Operating it

| Task | Where |
|---|---|
| See credit held, debt, spend and top consumers | Admin → **Wallets** |
| Change the exchange rate and margin | Admin → **Wallets** → **Edit pricing** (superadmin, with a reason; applies to the next call) |
| Give credit, correct a balance, mark an account unlimited | Admin → **Users** → the user's page (superadmin) |
| Audit every top-up, grant and plan change | Admin → **Accounting** |
| Check the gateway's spend logs against the wallet | `pnpm llm:reconcile` |

## Reference implementation

RE:GINE (the `gine` repository) integrates the gateway and the wallet exactly this way: a confidential application behind a BFF, a single login requesting the three audiences, a per-user server-side token vault that mints one narrowed token per audience, a wallet read before each run (`canSpend`) with the run refused up front when the user cannot pay, and a "top up" link to the identity provider's profile page.

## Checklist

- [ ] Application registered, **LiteLLM support** on, models granted to its team in LiteLLM.
- [ ] Authorization request repeats `resource` for your API, the gateway and auth-service, and requests `wallet:self:read` and `offline_access`.
- [ ] Code exchanged without `resource`; one narrowed token minted per audience; refresh tokens stored server-side and replaced at each refresh.
- [ ] 402 handled: user told, wallet link shown, no automatic retry.
- [ ] Wallet read with `canSpend` before expensive work, failing closed.
- [ ] Models used by your application have a price in LiteLLM.
