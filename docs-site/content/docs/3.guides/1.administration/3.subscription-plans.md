---
title: Managing plans
description: Create per-application subscription plans with feature flags and optional Stripe billing.
---

Each application can have one or more **subscription plans**. Plans carry a free-form `features` JSON object that is injected into the `id_token` as the `features` claim when the user completes an OAuth flow for that application.

All endpoints require an `admin` or `superadmin` session.

## Plans

When the application has **LiteLLM support**, each plan also maps to a gateway team (`<applicationSlug>:<planSlug>`) carrying an empty access group: creating a plan creates the team, renaming it replaces the team, deleting it blocks the team, and a plan whose slug would collide with another is refused (`400`). See [Subscription plans](/docs/concepts/subscription-plans#gateway-teams).

### List plans

```sh
GET /api/admin/applications/:appId/plans
```

Returns each plan with its price tiers and the count of active subscribers.

### Create a plan

```sh
POST /api/admin/applications/:appId/plans
Content-Type: application/json

{
  "name": "Pro",
  "description": "Full access",
  "features": {
    "maxProjects": 50,
    "exportEnabled": true,
    "storageGb": 100
  },
  "isDefault": false,
  "stripeProductId": "prod_abc123"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `name` | string | required | Plan name (1–64 chars, unique per application) |
| `description` | string | — | Optional description (max 500 chars) |
| `features` | object | `{}` | Free-form JSON feature flags |
| `isDefault` | boolean | `false` | Auto-assign to new users granted access to the app |
| `stripeProductId` | string | — | Link to a Stripe Product for webhook sync |

### Update a plan

```sh
PATCH /api/admin/applications/:appId/plans/:planId
Content-Type: application/json

{ "features": { "maxProjects": 100 } }
```

### Delete a plan

```sh
DELETE /api/admin/applications/:appId/plans/:planId
```

Returns `400 SUB_003` if any users currently hold an active subscription to this plan.

## Plan prices (Stripe billing)

Price tiers define the amounts charged for a plan and map to Stripe Price objects. They are used for display and for webhook reconciliation — Stripe sends `customer.subscription.updated` events that update the subscription `isActive` flag automatically.

### Add a price tier

```sh
POST /api/admin/applications/:appId/plans/:planId/prices
Content-Type: application/json

{
  "name": "Monthly",
  "amount": 999,
  "currency": "usd",
  "interval": "month",
  "stripePriceId": "price_xyz"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `name` | string | required | Display name (1–64 chars) |
| `amount` | integer | required | Amount in the smallest currency unit (e.g. cents) |
| `currency` | string | `"usd"` | ISO 4217 3-letter currency code |
| `interval` | `"month"` \| `"year"` \| `"one_time"` | `"month"` | Billing cycle |
| `stripePriceId` | string | — | Stripe Price ID for webhook reconciliation |

### Delete a price tier

```sh
DELETE /api/admin/applications/:appId/plans/:planId/prices/:priceId
```

## Assign or change a subscription

A user's subscription is part of their application access record. Set or change it with a `PATCH` on that record — `user_subscriptions` is the source of truth read by the token `features` claim, and the access record's `subscriptionPlanId` is kept in sync automatically. A manual plan change must carry a `reason`, which is written to the subscription journal (see below).

```sh
PATCH /api/admin/applications/:id/users/:userId
Content-Type: application/json

{
  "subscriptionPlanId": "<plan-uuid>",
  "reason": "Customer upgraded after a sales call"
}
```

Expiry. The optional `expiresAt` (ISO-8601) sets or clears the subscription expiry; pass `null` to clear it. When omitted the current expiry is left untouched. An `expiresAt`-only payload (no `subscriptionPlanId`) keeps the current plan and still requires a `reason`.

### Revoke a subscription

Set `subscriptionPlanId` to `null` on the same access record. A reason is still required because the removal is audited:

```sh
PATCH /api/admin/applications/:id/users/:userId
Content-Type: application/json

{
  "subscriptionPlanId": null,
  "reason": "Subscription cancelled"
}
```

### Plan at grant time

`POST /api/admin/applications/:id/users` accepts an optional `subscriptionPlanId`. When provided that plan is assigned; otherwise the application's default plan is used. The bulk endpoint (`POST /api/admin/applications/:id/users/bulk`) accepts the same `subscriptionPlanId` (and optional `reason`) and applies it to every granted user. An unknown or foreign plan is rejected before anything is written.

## Subscription journal

Every effective plan change writes an entry to `user_subscription_events` (`source`, `action`, `from_plan_id`, `to_plan_id`, the acting `actor_user_id`, and the `reason`) and publishes a `subscription.changed` event on the live-event channel so open admin views refresh. A change to the expiry, or a reactivation of a cancelled subscription, is recorded even when the plan id is unchanged; a call that leaves the subscription exactly as it was is a no-op and is not recorded. `subscription.changed` frames are coalesced (at most one per second), so a bulk grant produces a single refresh.

## Self-service plan changes

On the profile **Applications** tab a user can change their own plan, and only when Stripe is configured (without `STRIPE_SECRET_KEY` the selector is hidden and the endpoint refuses with `403 SUB_005`; without a payment provider, only administrators change a user's plan). The selector lists every plan with its price:

- a **free** plan applies at once, and its Stripe subscription follows;
- a **paid** plan is never granted before the payment: a user with a live paid subscription has it changed in place (Stripe prorates it), any other user is sent to Stripe Checkout, and the plan is granted when the checkout completes. A checkout never creates a second paid subscription (`409 SUB_007`).

Administrators can also stop a user's Stripe subscription at the end of its period, and resume it, from the user's page (see the [Stripe integration guide](/docs/guides/administration/stripe-integration)).

## Default plan auto-assignment

When you mark a plan as `isDefault: true`, it is automatically assigned to every user who is granted access to the application (via `POST /api/admin/applications/:id/users`). Only one default plan per application is supported; creating a new default plan does not de-activate the old subscribers — it only affects future grants.
