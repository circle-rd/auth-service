## 1. Goal and scope

auth-service stops configuring LiteLLM's access model. The administrator
registers models, MCP servers and A2A agents in LiteLLM with no team, access
group or per-key restriction. The `custom_auth` hook decides, on every request,
which of those objects the caller may list and call, from entitlements that
auth-service owns.

**In scope**: LiteLLM coverage only, for the three object kinds LiteLLM serves
today: models (`/v1/*`), MCP servers and tools (`/mcp`), and A2A agents
(`/a2a/*`).

**Out of scope** (planned later, see §11):

- files (`file://`), SSH hosts, and HTTP(S) endpoints (`https://`, `smb://`,
  `ftp://`);
- user-declared sharing and its ownership proof (requirements R1 to R4 of the
  resource-sharing discussion);
- registration of models by end users, for example a DGX node (open point LA-R1);
- the wallet, usage ledger and invoicing, which remain unchanged.

## 2. Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| LA-1 | LiteLLM is pinned to `ghcr.io/berriai/litellm:v1.108.8` (LTS patch line). 1.110 is not adopted before its stable release, and then only after re-running the spike matrix. | 1.108.8 keeps the spike results (no regression on T1–T9 versus 1.108.3) and carries the MCP `mcp_all` sign-in fix. 1.110.0-rc.2 is a release candidate only. Patch moves inside 1.108 are allowed by D44. |
| LA-2 | auth-service writes nothing to LiteLLM for access control: no team, no access group, no `models` list on keys it creates. | Removes runtime mutation of LiteLLM state, which is the main source of drift and complexity today. |
| LA-3 | The source of truth for "who may use what" is auth-service: a grant table linking subscription plans to LiteLLM objects. | LiteLLM has no per-user ACL on objects; the decision has to live where the user, plan and subscription live. |
| LA-4 | The custom auth hook returns, per request, `models`, `object_permission.mcp_servers`, `object_permission.mcp_tool_permissions` and `object_permission.agents`. It returns no `team_id`. | Spike v1/v2: this is the only mechanism that filters listings and calls for all three kinds, with clean 403 responses for models and MCP. |
| LA-5 | Fail-closed at the hook. A caller without a plan, or whose resolved entitlements are empty, is refused with 403 by the hook. An empty list is never emitted for a refusal. | Spike v2: `models: []` means "all models"; a sentinel is listed by `/v1/models`. Refusing at the hook avoids both. |
| LA-6 | Entitlements are resolved by a machine-scoped endpoint on auth-service, cached in the hook for 30 seconds per `(subject, application)`. | No LiteLLM-side cache exists (spike: the hook runs on every request). A 30-second bound on revocation is the accepted staleness, as for the other gateway caches. |
| LA-7 | auth-service reads the LiteLLM inventory (models, MCP servers, agents) with a read-only credential, to let administrators pick grant targets. It never writes to LiteLLM. | Administrators need a list of what exists. The inventory is small and bounded; a read-only credential keeps the write surface at zero. |
| LA-8 | The team provisioner key (`auth-service-provisioner`) and the access-group key (`auth-service-resource-sync`) are retired and revoked. | They exist only to create and fill teams and access groups, which LA-2 removes. |
| LA-9 | One cutover, no dual mode. The team-based path is not kept behind a flag. Rollback is restoring the databases and the previous image. | Project doctrine forbids speculative compatibility shims. The deployment is pre-production; no data needs a live coexistence. |
| LA-10 | The new tables live in a new schema file, not in `src/db/schema.ts`. | `schema.ts` is 999 lines, one line under the 1000-line hard ceiling. Any addition breaks the rule. |
| LA-11 | The baseline is regenerated (`drizzle/0000_initial_schema.sql`) with the new tables, as the pre-production rule requires. No delta migration. | AGENTS.md, section 8. |
| LA-12 | Shared-resource enforcement on LiteLLM is re-pointed to the same entitlement source. The sharing team (`resource_routing.authorize_team_fallbacks`, `context.team_id`) and the access-group sync of shared resources are removed. | Keeps one enforcement path. The user-declared sharing model remains a separate plan. |

## 3. Target architecture

```
client ──► LiteLLM (1.108.8)
              │  custom_auth.user_api_key_auth (per request)
              │    1. master key            → admin
              │    2. sk-… virtual key      → LiteLLM native checks (models, object_permission in DB)
              │    3. JWT (auth-service)    → GET entitlements (cached 30 s)
              │         → UserAPIKeyAuth(models, object_permission{mcp_servers,
              │                          mcp_tool_permissions, agents})
              │           with custom_auth_run_common_checks and
              │           enable_post_custom_auth_checks
              ▼
        LiteLLM objects: models, MCP servers, agents — registered by the operator,
        no team, no access group.

auth-service
  gateway_object        mirror of the LiteLLM inventory (read-only sync)
  plan_gateway_grant    plan × gateway_object
  GET /api/internal/gateway/users/:userId/entitlements?applicationSlug=
  admin: inventory view and grant editor per application plan
```

Virtual keys (`sk-…`) keep LiteLLM's native restrictions. They are created by
operators or by the admin UI, and the hook does not decide for them (spike v3).

## 5. Data model

Schema file: `src/db/gateway-schema.ts` (new, LA-10). Re-exported from the
Drizzle schema entry point used by the migration generator.

```
gateway_object
  id                uuid pk
  kind              text not null     -- 'model' | 'mcp_server' | 'agent'
  litellm_id        text not null     -- LiteLLM model name, server_id or agent_id
  display_name      text not null
  is_active         boolean not null default true
  last_seen_at      timestamptz not null
  created_at        timestamptz not null
  unique (kind, litellm_id)
  check (kind in ('model','mcp_server','agent'))

plan_gateway_grant
  id                uuid pk
  plan_id           uuid not null → subscription_plans (on delete cascade)
  gateway_object_id uuid not null → gateway_object (on delete cascade)
  created_by        text not null
  created_at        timestamptz not null
  unique (plan_id, gateway_object_id)
```

Rules:

- Inactive objects (missing from the last inventory) stay in the table and are
  filtered out at resolution. They are never deleted automatically.
- A grant to an inactive object resolves to nothing.
- `plan_id` implies the application: a plan belongs to one application, so no
  application column is needed.
- Per-user grants (for user-declared sharing) are **not** in this table. They
  are a later extension of the entitlement resolver (§11).

Baseline: regenerate `drizzle/0000_initial_schema.sql` with
`pnpm db:generate --name initial_schema` after removing `drizzle/`, review the
diff (only the new tables), and recreate test databases (`docker compose down -v`).

## 8. Cutover and rollback

Pre-production sequence:

1. Back up the auth-service and `litellm` databases.
2. Stop the gateway.
3. Deploy the auth-service release that contains phases 2 and 4, run the baseline regeneration, and apply the new schema.
4. Run `litellm-acl-migrate` (dry run, parity check, apply).
5. Start LiteLLM 1.108.8 with the new `custom_auth` and config.
6. Run `llm:smoke` and the verification matrix V1–V14 (except V12, which runs only on an isolated stack).
7. Revoke the provisioner keys and delete managed teams and access groups (§6.4, §6.5).

Rollback: restore both databases and the previous images
(auth-service and LiteLLM 1.108.3). Because LiteLLM may run Prisma migrations at
startup, the `litellm` database backup is the only reliable rollback for the
LiteLLM side.

## 10. Risks and open points

| ID | Risk or point | Mitigation or owner |
| --- | --- | --- |
| LA-R1 | **Deferred**: end users registering their own model (DGX node). A user cannot register a LiteLLM deployment without an admin credential, and any registration with an arbitrary `api_base` is an SSRF risk. | Deferred by decision. To be revisited with a plugin or equivalent mechanism. Models in this plan are registered by operators in the standard way. |
| LA-R2 | Inventory credential could be over-scoped. | Phase 0.2 and the route allowlist; the credential has no write route. |
| LA-R3 | Keys created by the admin UI carry no `object_permission`, so their MCP and A2A screens are empty or refused (spike v3, risk 1). | Attach `object_permission` at creation for admin UI keys; add to the admin key creation path. |
| LA-R4 | Multi-replica behaviour not tested: revocation delay depends on each replica's cache. | Bounded by the 30 s hook cache. Test with two workers in the integration environment before production. |
| LA-R5 | Enterprise packaging: the custom auth path goes through `litellm_enterprise`, even without a licence. | Pinned version (LA-1) and the phase 5 guard. Re-check on every bump. |
