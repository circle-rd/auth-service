### Deliberately accepted (documented, not defects)

- **M-02 cross-subdomain session cookie** — kept opt-in via `SESSION_DOMAIN`; sharing the IdP cookie across subdomains is a deliberate trade-off.
- **L-08 login IP/UA on OAuth issuance** — BetterAuth's token-issuance callback exposes no request headers; the parent session row carries them.
- **L-10 pin GitHub Actions by SHA** — deferred to Dependabot (Phase 7) instead of hand-pinned SHAs.

### Phase 2 — BetterAuth upgrade (✅, 1.6.23 → 1.7.7)

`latest` (1.7.7) installed for `better-auth`, `@better-auth/oauth-provider`,
`@better-auth/passkey`, `@better-auth/drizzle-adapter` — no fallback needed.

- **Schema**: `src/db/auth-schema.ts` hand-aligned with the 1.7 schema (`jwks.alg/crv`, new `oauth_client` columns, new tables `oauth_resource`, `oauth_client_resource`, `oauth_client_assertion`); consolidated `0000_initial_schema.sql` regenerated per the pre-production exception; `migrate.ts` reduced to a plain `migrate()`.
- **Code**: `validAudiences` replaced by RFC 8707 protected resources (`oauth_resource` rows keyed by `applications.url`, linked per client via `oauth_client_resource`); 1.7 client metadata written on application create; M2M verification rewritten on `verifyJwsAccessToken` with a local JWKS read from the `jwks` table, `azp`-bound and fail-closed; JWKS rotation enabled (30-day rotation, 30-day grace).
- **Tests**: end-to-end `client_credentials` → `/api/consumption` (success + cross-application rejection). Deferred: ID-token claims via a full authorization-code flow, end-session E2E (Phase 5).

::callout
**Breaking release** — recreate the database (`docker compose down -v && docker compose pull && docker compose up -d`), then re-register downstream clients. Set `TRUST_PROXY_HOPS=1` when running behind a reverse proxy.
::

Post-review fixes: 2FA guard covers `/sign-in/social`; Stripe handlers filter by `(user_id, application_id, plan_id)`; `stripe_events` purged after 30 days; `requireAdmin` emits `AUTH_011`; last-superadmin demotion is a single conditional UPDATE; bootstrap rejects the shipped `.env.example` password pattern.

### Phase 5 — New features & email delivery hardening (🟡 5a done · 5b partial)

#### 5a — Email delivery hardening (from the delivery audit) — ✅ done

The audit found that an account created by an admin receives no verification
email, because BetterAuth's native `/admin/create-user` endpoint never calls
`sendVerificationEmail` (only `/sign-up/email` consults `sendOnSignUp`). A
configured SMTP therefore still produced no mail. Shipped:

- `POST /api/admin/users` sends the verification email after creation
  (best-effort and detached; a transport failure does not roll back the
  account, and it is skipped when the no-op transport is active).
- No duplicate activation mail: `sendOnSignIn` is intentionally **off** (it
  re-sent on every failed sign-in attempt). The login page now detects
  `EMAIL_NOT_VERIFIED` and offers an explicit, rate-limited "resend" action
  instead.
- Verification links land on `/profile` (BetterAuth's default `callbackURL=/`
  dropped regular users on the admin-only dashboard → 403). The SPA defaults
  `/` to `/profile` and shows a Dashboard entry in the user menu only for
  admins.
- Admin UI: `POST /api/admin/users/:id/send-verification` reverts the account
  to unverified and re-sends (buttons in the user list action menu and the user
  detail page); `POST /api/admin/users/:id/verify-email` marks it verified
  without the link (superadmin-only for admin/superadmin targets).
- `verify-email.html` "Resend" now collects the address and POSTs it (it
  previously sent an empty body).
- Fail loud instead of silent: the no-op transport is no longer reported as
  `sent`; `sendEmail()` logs a `DROPPED` warning instead.
- Rate-limit the added mail senders (`/change-email`,
  `/organization/invite-member`) in the email bucket. `/sign-up/email` stays
  in the auth bucket only: its verification mail is a side effect of account
  creation, and the extra 5/min cap breaks legitimate provisioning.
- `docker-compose.yml`: mail-catcher (`mailpit`) behind the `mail` profile and
  `MAIL_REPLY_TO` passthrough.
- Transactional email design pass across the six built-in `.eml` templates: a
  shared branded shell (table layout, inline styles), the instance logo
  embedded as a CID attachment (`APP_LOGO_URL` resolved to bytes, no external
  image request), and tightened copy. Bundled templates are wrapped;
  tenant/external overrides are left verbatim. Logo resolution is SSRF-guarded
  (private/link-local hosts and redirects are rejected), size-capped (256 KB),
  deduplicated, and warmed in the background so it never blocks a send.

Covered by `src/tests/email-admin-created.integration.test.ts` and
`src/tests/email-verify.integration.test.ts`.

#### 5b — New features (partial)

Shipped:

- Shared rate-limit store (`src/services/rate-limit-store.ts`): in-memory by
  default, Redis-backed when `REDIS_URL` is set (lazy `ioredis`, atomic
  INCR/PEXPIRE; on a Redis error it falls back to per-instance limits rather
  than failing open or blocking all auth). Compose `redis` service behind a
  `redis` profile.
- Opt-in BetterAuth plugins, each gated by env so defaults are unchanged:
  `haveIBeenPwned` (`HAVEIBEENPWNED_ENABLED`), `captcha` (explicit
  `CAPTCHA_ENABLED` plus `CAPTCHA_PROVIDER`/`CAPTCHA_SECRET_KEY`/
  `CAPTCHA_SITE_KEY`/`CAPTCHA_ENDPOINTS`), `lastLoginMethod`
  (`LAST_LOGIN_METHOD_ENABLED`).
- Device authorization grant (`DEVICE_AUTHORIZATION_ENABLED`): plugin, the
  `device_code` table inlined into the consolidated `0000_initial_schema.sql`
  baseline (pre-production: no delta migration), and the `/device` approval page
  (Vue SPA view + server-rendered template).

Remaining in 5b:

- Captcha client side: the plugin rejects `/sign-in/email`, `/sign-up/email`
  and `/request-password-reset` unless the request carries an
  `x-captcha-response` header. Neither the Vue SPA nor the server templates
  render a widget yet, and the site key is not exposed to clients, so leaving
  `CAPTCHA_ENABLED=false` is mandatory until the widget ships.
- Expose back-channel logout (`backchannelLogoutUri`,
  `backchannelLogoutSessionRequired`) and DPoP (`dpopBoundAccessTokens`) in the
  admin application create/update schema. Both are **already supported by
  `@better-auth/oauth-provider` 1.7.7** (the schema columns exist); only the
  admin surface and tests are missing.
- `@better-auth/i18n`: BetterAuth 1.7.7 ships no i18n package, so this needs a
  dedicated design pass (message catalog + locale negotiation) rather than a
  config toggle.
- Evaluate CIMD/DCR and `auth.api.adminCreateOAuthClient` vs. the hand-written
  client insertion.

## Recently shipped

- **Admin real-time channel — event vocabulary widened (WP3 of #60)**: the admin event channel now announces six event types instead of one. `session.created` and `session.revoked` fire from BetterAuth's `databaseHooks.session` create/delete (every session write, including `/api/auth/*` and `internalAdapter` calls). `user.changed` fires from the user `databaseHooks` (create/update/delete) and from the direct Drizzle writes in `bootstrap.ts`, `routes/user.ts` and `routes/admin/users.ts` that bypass the adapter. `application.changed` fires from every application lifecycle route (create, update, delete, user access grant/revoke/role/plan change, provider change). `organization.changed` fires from the BetterAuth organization plugin hooks and from the direct Drizzle writes in `routes/admin/organizations.ts` (create, update, delete, member add/remove/role change, invitation create/cancel). The dashboard composable refreshes the relevant admin view on any event; the stream still carries no payload, only the event type and a timestamp.

- **Admin real-time channel — dashboard consumption (WP2 of #60)**: the admin dashboard now subscribes to `GET /api/admin/events` through `frontend/src/composables/useAdminEvents.ts` and refreshes its logins series and online counter on `login.recorded`. The refresh is debounced: each event restarts a 1 s window that is capped at 1 s from the first event, so a login spike costs exactly one round of requests — run after the spike, so it counts every login in it — and a stream that never falls quiet still refreshes once per window. Only the dashboard subscribes; the composable is inert under `VITE_USE_MOCK`, closes the stream on unmount and leaves reconnection to `EventSource`. The 30 s `active-users` poll is unchanged and remains the safety net. No frontend test runner is introduced — the frontend evidence is observational.

- **Admin real-time channel (SSE, WP1 of #60)**: `GET /api/admin/events` streams Server-Sent Events to the admin dashboard, guarded by the same `requireAdmin` preHandler as the other `/api/admin/*` routes (401 / 403 / 200). A frame names an event type — `login.recorded` today — and carries at most a timestamp; **no payload, no identifier, no count** ever travels on the stream, and the client re-fetches through the REST endpoints it already calls. The event bus is in-process by default and fans out over Redis pub/sub when `REDIS_URL` is set, mirroring the rate-limit store. Keep-alive comment frames hold an idle stream open and every subscriber is unsubscribed on connection close, so `EventSource` reconnections cannot accumulate. Delivery is best effort: the dashboard's 30 s `active-users` poll remains the safety net. Covered by `src/routes/admin/events.test.ts`, `src/services/event-bus.test.ts` and `src/tests/events.integration.test.ts`.

- **Admin password reset**: `POST /api/admin/users/:id/set-password` sets a new password for a **strictly lower-ranked** user and, in the same operation, revokes the target's sessions and OAuth refresh tokens — the credential write and the revocation are one gesture, so a reset on a compromised account actually takes the session away. The native `/api/auth/admin/set-user-password` endpoint is withheld from every role (`set-password` removed from the admin and superadmin permission lists) because it writes the credential and revokes nothing; the custom route is the only path. A distinct `canManageRole` gate (strict rank) drives both the server check and the admin UI action, so the UI never offers a reset the server would refuse. Admin UI: "Set Password" action on the user detail page reusing the WP2 password-strength meter.
- **Phase 5a/5b**: admin-created users now receive a verification email (plus admin resend / mark-verified), no-op transport no longer logs a false `sent`, mail senders rate-limited, `mailpit` catcher; opt-in `haveIBeenPwned` / `captcha` / `lastLoginMethod` plugins, RFC 8628 device authorization with `/device` page, and a shared rate-limit store (in-memory or Redis via `REDIS_URL`).
- **Email follow-up**: removed the sign-in re-send that duplicated activation mails, verification links now land on `/profile` (with an admin-only Dashboard menu entry), admin UI exposes resend / mark-verified, and all six transactional templates share a branded layout with the instance logo embedded as a CID attachment.
- **Admin UX**: verification actions are gated by SMTP/verification readiness and caller rights; Ban/Delete are hidden for self and higher-ranked targets; the OAuth/Integration code block matches the details block height (scrollable + copy button); bulk CSV user import and bulk application access by organization; tenant templates (`mcp-central`, `vandal-app`) converted to Eta and completed with select-org/device pages and transactional emails.

- **Compose / packaging**: single functional `docker-compose.yml`; docs prioritise the published `latest`/`nightly` images; production install fixed (`husky || true` under `--prod`).
- **Phase 3**: 2FA enforced for passwordless/social sign-in, `select-org` XSS fixed, credentialed CORS scoped to the dashboard, request logs token-free, `allowRegister`/`TRUST_PROXY_HOPS` secure defaults, helmet headers, Stripe webhook idempotency, last-superadmin protection, non-root container.
- **Phase 4**: shared `middleware.ts` and `logger.ts`, `AUTH_011` 403 + Zod/BetterAuth error mapping, fail-fast bootstrap, `user_subscriptions` upsert fix.
- **Phase 2**: BetterAuth 1.7.7, regenerated baseline, protected resources, client metadata, native `revokeSession`, local-JWKS M2M verification with E2E test, JWKS rotation.
- **Phase 1**: OAuth client management admin-only, fail-closed access guard, admin hierarchy hook, strict boolean env parsing, provider secrets no longer exposed, OAuth token revocation on ban/revocation/rotation.
- **Phase 0**: ESLint + Prettier + husky/lint-staged, coverage tooling, CI on PR, integration tests on PostgreSQL 17, tracked build artefacts removed.

## Infrastructure

- **Single `docker-compose.yml`** — `postgres` + `auth-service` (prebuilt image or `--build`), healthcheck on `/health`, postgres exposed on 5433 for host-based dev.
- **Images** — published to `ghcr.io/circle-rd/auth-service` as `:nightly` (develop), `:latest` (release) and version tags.
- **Dockerfile** — three-stage (frontend → backend → runtime), runs as `USER node`.
- **Migrations** — `runMigrations()` at startup; the consolidated baseline is regenerated until the first production release, so reinitialised databases must be recreated (`docker compose down -v`).
