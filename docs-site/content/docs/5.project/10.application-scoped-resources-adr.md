Invariants shared by every record:

1. An application's view is the subject's rights intersected with the
   application scope. The scope is the resources the application owns plus the
   ones shared with it.
2. Every identifier that decides an access comes from a verified token or from
   the trusted registry, never from a request body.
3. Fail closed. An unknown, inactive or unscoped caller is refused, not narrowed
   to an empty list.

Schema changes in this work follow the pre-production rule of `AGENTS.md` §8:
they are folded into the regenerated `0000_initial_schema.sql`, with no delta
migration. The test data of the shared test instance is exported and imported
again by hand (see the runbook in the plan).

## ADR-1 — Client identity and caller classes (D6, D8)

**Context.** `POST /authorize` and `POST /usage` took `clientId` from the
request body and never compared it to the verified token.
`GET /resources/accessible` ignored the client. Any client with
`resources:authorize` could read the rights of any subject. The LiteLLM hook
resolves rights for a user whose token was issued to another application, so it
must tell auth-service which application the request came through.

**Decision.**

- `clientId` comes from the verified machine token
  (`requireMachineApplication`) and is removed from the request bodies. The
  client the end user came through is sent as optional `actorClientId` and is
  recorded for audit only; it never decides anything.
- `authorize()` denies `invalid_client` unless the client is an active
  application with resource sharing enabled, and `invalid_audience` unless the
  audience is the issuer (no trailing slash) or an allowed resource of that
  application.
- The gateway does not assert `sub` and `azp`. The hook sends the user's access
  token to a new entitlements route, and auth-service verifies it and derives
  both. The old route that took a user id is removed. There is no delegation
  scope.
- Each decision, from that route and from `/authorize`, carries a signed
  `decisionId` (HMAC-SHA256 over `sub`, application client id, calling machine
  client, `iat` and `exp`, with a key derived for this purpose) and an
  `expiresAt`, 60 seconds by default and never longer than the user token. The
  application and subject of a `/usage` event come from the `decisionId`, which
  only the caller that obtained it can present.

**Rejected.** A delegation scope letting infrastructure claim any application:
a compromised hook could then read the rights of any pair and forge usage.
Accepting a body `clientId` when it equals the token: it keeps a field that must
never be trusted.

**Consequences.** One LiteLLM machine client for now. The user token transits to
auth-service, a component already trusted with it. Revocation delay stays bound
by the hook cache (at most 30 seconds).

**Revisit.** Split the LiteLLM client into a read client and a usage client
before the gateway is exposed more widely.

## ADR-2 — Application grants and scope (D2, D4, D5, D11)

**Context.** Grants named a user, an organization, a plan or everyone. Nothing
expressed which application may use a resource, so the global catalogue was the
only view.

**Decision.**

- New grant subject type `application`. `subject_id` is the application client
  id (its slug, which is immutable) and is mandatory.
- A resource is usable through application `C` for subject `S` when `S` is
  entitled by the existing rules and `C` owns the resource or an unrevoked,
  unexpired application grant names `C`. An application grant widens the
  application dimension only.
- Membership is checked against the calling application, not the owner
  application.
- Plan grants only count inside the owner application, because plans belong to
  an application. Across applications, user, organization and `everyone` grants
  apply, together with the application grant.
- Only built-in schemes cross applications: an application-defined scheme can
  be enabled only for the application that defines it, so an application grant
  for it is refused.
- The owner creates the grant for a user-owned resource, an administrator of the
  application for an application-owned one. The target must be an active
  application with resource sharing enabled and the scheme enabled for it.
  Bulk sharing is supported.
- Responses and webhooks sent to an application that does not own the resource
  carry no owner identity.

**Rejected.** A dedicated table (more joins for the same semantics). A global
grant for every application: no real case yet.

**Revisit.** A resource that must serve every application. Restrict it by scheme
policy (`llm`, `agent`, `mcp`; never `ssh`).

## ADR-3 — Namespaces and auto-declaration (D1, D9)

**Context.** For the `litellm` adapter the first locator segment had to be the
application slug. A relay publishes `{account}/{model}`, so a user's model could
not be declared. A username and an application slug could collide on the same
LiteLLM alias, which is a flat namespace.

**Decision.**

- The namespace follows the owner. An application-owned resource starts with the
  application slug. A user-owned one starts with `u-` followed by the lowercase
  username. Only users are prefixed.
- A database check refuses application slugs starting with `u-`, so the two
  families cannot overlap, on top of the existing unique indexes.
- The relay names its deployments `u-<username>/<model>`. Provenance checks
  compare `clientId` with `u-<username>`.
- A username is mandatory to declare a user-owned resource. The email local part
  fallback for `preferred_username` is removed.
- Renaming a username is refused (409) while the account owns a resource in its
  namespace, on both the self-service and the administrator path.
- A built-in system application `catalogue` (resource sharing on, schemes `llm`,
  `agent`, `mcp`) owns the auto-declared resources. It has no client secret and
  no code. Because the authority rules expect an owner to be a member of the
  resource application, the owner is enrolled in it (no role) when the resource
  is declared; the application is a system one and stays hidden. The mirror declares and validates a user-owned resource for each relay
  object whose provenance is proven and whose owner has a username.

**Rejected.** A `:` or another separator in the URI (it moves the collision
instead of removing it: the gateway alias stays flat). Prefixing both sides
(renames every application alias for no extra guarantee). A
`resource_namespaces` table (heavier, and it would block users who cannot change
a provider-imposed name).

**Revisit.** Username renaming becomes a product need: introduce reserved,
immutable namespaces.

## ADR-4 — Bearer scoping (D7)

**Context.** `/accessible-resources` and `/resource-catalogue` accept any
user-bound token with `resources:self:manage`, whatever client it was issued to.

**Decision.** The bearer's client decides the scope, on every user resource
route (listing, catalogue, reading, changing, deleting, grants and validation
requests), not only on the listings. A client tied to an application with
resource sharing sees and manages that application's resources only: another
application's resource answers as not found, and a resource cannot be created
in another application. A client with no such application is refused (403).
`resources:self:manage` is already owned by the application's Resource sharing
flag, so only an application can hold it. The cookie session of the
auth-service UI keeps the global view.

**Rejected.** Keeping the global view for bearers (a compromised third-party
application would see everything its users own). Refusing every bearer (loses
the user path used by RE:GINE).

## ADR-5 — Permanent deletion and retention (D12)

**Context.** `removeResource` deleted a resource only if it had never been
validated, otherwise it disabled it and the row stayed forever. A grant could
only be revoked. Revoked grants and spent invitations accumulated, and a
username rename could never become possible for an account owning a disabled
resource.

**Decision.**

- `DELETE` on a resource deletes it for good. Grants, invitations and gateway
  links cascade. Access events and usage records keep their rows with a null
  resource id and the `uri`. A `resource.deleted` webhook reaches the owner
  application and every application that held a grant.
- Deletion of an auto-declared relay resource is refused (409) while its relay
  object is active, because the mirror would recreate it.
- Revocation stays soft and immediate. A revoked or expired grant is deleted for
  good with `permanent=true`. The retention sweep also removes revoked or expired
  grants and spent invitations after `RESOURCE_GRANT_RETENTION_DAYS`.
- Application grants naming a deleted application are deleted with it.

**Accepted risk.** A deleted `uri` can be declared again, so events with a null
resource id and the same `uri` can mix two lifetimes. Monitoring keeps its own
retention.

## ADR-6 — Grant permission levels (D13)

**Context.** A grant carried a single, fixed `use` permission. GINE shares jobs
and must separate consultation from action.

**Decision.**

- Closed ordered set `read`, `write`. `write` covers `read`. Default `read`. An
  unknown value is a validation error (400).
- Each scheme declares the levels it supports. Single-action built-in schemes
  (`llm`, `agent`, `mcp`, `ssh`, `https`) support only `read`, which means "use".
  `file` and application schemes support both.
- A level changes in place with `PATCH`, which keeps the grant id and audit
  fields and emits `resource.grant.updated`. Invitations carry the level and
  apply it at acceptance.
- `authorize` accepts the level required (default `read`) and denies with
  `insufficient_permission` when the effective level is lower. The owner has
  `write`. Among several applicable grants the highest wins. For an application
  that does not own the resource, an application grant caps the result. The
  effective level is returned to the recipient.

**Rejected.** Revoke-and-recreate to change a level (loses the id, leaves a
window without access, emits two events). A free-form permission string.
