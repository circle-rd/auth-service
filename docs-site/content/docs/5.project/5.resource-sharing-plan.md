## 1. Goal

One login, one endpoint, many shared resources. An owner application publishes
resources (models, workflows, MCP agents, later HTTPS API endpoints, later
SSH hosts); invited users reach any of them through the gateway they already
use, with a single OAuth client per agent, without owner-specific logins and
without exposing private infrastructure.

The authorization decision is always server-side auth-service policy deriving
from a trusted resource registry — never an OAuth claim. `azp` remains the
calling OAuth client.

## 3. Data model (custom schema, pre-production baseline)

All tables in `src/db/schema.ts`, snake_case columns. Pre-production: every
schema change regenerates the consolidated `drizzle/0000_initial_schema.sql`
(`pnpm db:generate --name initial_schema`, databases recreated from scratch);
no delta migrations before first production deploy.

- `shared_resource { id, owner_application_id, resource_type, key, display_name, upstream_ref, status, visibility, default_plan_id?, created_at, updated_at }`
  - `key` — canonical unique `<applicationSlug>/<slug>` across all types; immutable once published (AC-05).
  - `upstream_ref` — opaque per type: LiteLLM deployment/team reference for gateway-managed types; URL hint for `https_endpoint`. Secrets are never stored here; `https_endpoint` upstream credentials live in type-specific secret storage at provision time.
  - `status ∈ {draft, published, disabled}`, `visibility ∈ {invited_only, public_catalog}`.
- `resource_grant { id, subject_id, owner_application_id, resource_id?, plan_id, allowed_client_ids?, expires_at?, revoked_at?, created_by, created_at }`
  - `resource_id` null = whole owner-application scoping; explicit row only for invited non-members (D10).
- `app_delegation { owner_user_id, application_id, permission, status }` — delegated owner administration; no global admin role involved.
- `usage_record { id, subject_id, client_id, owner_application_id, resource_type, resource_id, plan_id, request_id, tokens, cost, occurred_at }` — gross metering only (D5), delivered by the gateway with retry/backlog reuse.

`resource_grant` and `app_delegation` reuse the existing invitation pipeline
for the "invite" step (bucket `EMAIL_SEND_PATHS` in `src/server.ts`).

## 4. API surface (auth-service)

Machine-to-machine, gateway-scoped (extend `MACHINE_SCOPES` with a dedicated
`resources:authorize` scope; wallet consultation keeps `wallet:read`):

- `POST /api/internal/gateway/authorize` — body `{ resourceType, key, requestId }`; response `{ decision: "allow" | "deny", ownerApplicationSlug, planName, teamId?, resourceId }`. Deny is a boolean decision, no metadata echo.
- `GET /api/internal/gateway/resources/accessible?resourceType=…` — subject-scoped list for `/v1/models`-style filtering; cached 30 s per subject+type.

Owner and user APIs (dashboard session, delegated guard `requireAppDelegation`):

- `GET /api/user/accessible-resources` — what the authenticated subject may reach (portal catalogue).
- `GET|POST|PATCH|DELETE /api/user/apps/:appId/shared-resources` — owner CRUD, Zod-validated, cross-tenant ids rejected.
- `POST /api/user/apps/:appId/invitations` — invite a subject to a plan/grant.
- `PUT|DELETE /api/user/apps/:appId/grants/:grantId` — narrow, expire or revoke (AC-03: effective ≤ 30 s).
- `GET /api/user/apps/:appId/usage?groupBy=user|resource` — owner-attributed usage.

Admin routes and existing single-app flows are untouched.

## 6. Security notes (review before M1/M2/M6)

- Trust: verified JWT (JWKS) + server registry only; every deny path uniform; no token, secret or upstream URL in logs or error `details` (project doctrine §10).
- Gateway: request `model`/resource key parsed before admission; unknown/absent/disabled → `404 RES_004`; other LiteLLM routes explicit allowlist (no unchecked bypass).
- Delegation: least privilege per application; every mutation effective ≤ cache TTL; owner APIs never expose admin keys or the master key.
- Registry sync: dedicated provisioner credential; rotation like `litellm-provision`; reconciliation is idempotent.
- Quota and abuse: machine-scope buckets for the internal authorize API; per-client rate limits at the gateway.
- Egress (`https_endpoint`): deny-by-default URL policy via the outbound guard, no private/metadata ranges, redirects re-validated.

### P0 — recorded baselines and method

Harness: `pnpm bench` (spawns the compiled server twice — a throughput life
and a `LOG_SQL` counting life — then reports rps/latency/SQL per scenario).
Two deployment knobs came out of it: `RATE_LIMIT_GLOBAL_MAX` (the former
hard-coded 600/min per-IP guard, so bigger deployments can raise it) and the
`LOG_SQL` diagnostic echo.

Local build, containerised PostgreSQL on the same host, `--reps 500
--concurrency 25` (bench server runs with the global guard raised):

| Scenario | rps | p50 | p95 | p99 | SQL/req |
|----------|-----|-----|-----|-----|---------|
| `GET /health` | 2376 | 8.0 | 24.4 | 34.7 | — |
| `GET /api/auth/jwks` | 658 | 34.1 | 48.4 | 158.6 | — |
| session (`GET /api/user/sessions`, cookie) | 487 | 50.6 | 59.5 | 63.3 | 3 |
| machine (opaque bearer, default compat profile) | 58 (paced 60) | 5.9 | 28.3 | 35.3 | 4 |

The P0 machine scenario minted **opaque** tokens (client_credentials without a
`resource`): 4 SQL/req = the stored-token lookup, the live client check and
the plan resolution. The gateway-facing JWT path is measured from P1 on (the
bench now sends `resource=<instance url>` so tokens are RFC 8707 JWTs, the
shape `custom_auth.py` verifies).

Test instance replay (`https://auth.circle-cyber.com`, read-only, 8 rps over
the VPN): health p50 25.6 ms, jwks 28.9 ms, session 35.1 ms.

Run details live in `bench/` (untracked results directory).

### P1 — result (2026-11-13)

BetterAuth 1.7.15 already implements process-level JWKS caching inside
`verifyJwsAccessToken` (5 min TTL, 30 s refetch cooldown, unknown-`kid`
refetch) — but only when the caller passes a stable `jwksCacheKey`, so the
verification call now supplies one. The protected-resource (audience) list has
no upstream cache and is cached here (`RESOURCE_CACHE_TTL_SECONDS`, 30 s,
`0` disables) and invalidated by `replaceClientResource`. Key rotation needs
no local hook: the upstream unknown-`kid` refetch picks up a new key within
one request.

Measured on the JWT path (5 counted requests after warm-up, cache on):

| SQL statement per machine request | P0 | P1 |
|-----------------------------------|----|----|
| `select … from "jwks"` | 1 | **0** |
| `select … from "oauth_resource"` (audiences) | 1 | **0** |
| `select … from "oauth_client"` (live client check) | 1 | 1 (locked decision) |
| plan resolution (user_subscriptions + applications) | 2 | 2 |
| **total** | **5** | **3** |

Throughput on the machine scenario is paced (60 rps) so latency is not
comparable; the session path (3 SQL/req) is P2's target. Remaining known
reduction candidates, deliberately out of P1 scope: the plan resolver's two
queries can merge into one join, and the plan/authorize endpoint of M1 will
extend this path anyway.

### P2 — session mirror on Redis (2026-11-13)

**Spike (BetterAuth 1.7.15 source + executed against PostgreSQL 17 and Redis 7).**
The spike ran three configurations of the product's `auth` shape:

| Check | Pure `secondaryStorage` | Mirror (`storeSessionInDatabase: true`) |
|-------|-------------------------|------------------------------------------|
| Read after single-session revocation is refused | pass | pass |
| `deleteUserSessions` clears every session and Redis key | pass | pass |
| Ban through the adapter reaches a live session | pass | pass |
| Role change by direct SQL reaches a live session | **fail** | **fail** |
| Role change through `internalAdapter.updateUser` reaches a live session | pass | pass |
| Session rows remain in PostgreSQL (admin listings) | **no** | yes |

Decision: mirror mode. Pure mode would hide every session from the
admin screens that query the `session` table. The role defect is a
prerequisite fix, not a cache problem: the admin role change bypassed the
adapter (see `admin/users.ts`), so Redis would have served the old role
until the session expired.

**Implementation.**

- `services/redis-client.ts`: one lazily loaded `ioredis` connection shared by
  the rate-limit store and the session store; closed once on shutdown.
- `services/session-store.ts`: the BetterAuth `SecondaryStorage` contract
  (`get`, `getAndDelete`, `increment`, `set`, `delete`) under the
  `auth:session:` namespace.
- `auth.ts`: `secondaryStorage` and `session.storeSessionInDatabase: true`,
  enabled only when `REDIS_URL` is set.
- `services/session-snapshot.ts`: `refreshUserSessionSnapshots` writes the
  committed user row through the adapter, which refreshes each live session's
  user copy. Called after every direct write to the `user` table that reaches
  the session: role and profile PATCH, reset-MFA, resend and admin
  verification, self-service profile, and the passkey / 2FA hook. Calls sit
  after the transaction commits, never inside it, so the adapter cannot block
  on the transaction's row lock.

**Measured (same machine, `--reps 500 --concurrency 25`, bench-owned server,
fresh per run):**

| Scenario | Without Redis (p50 / rps / SQL per request) | With `REDIS_URL` (p50 / rps / SQL per request) |
|----------|---------------------------------------------|-------------------------------------------------|
| session (`GET /api/user/sessions`, cookie) | 51.4 ms / 476 / 3 | 34.8 ms / 694 / 1 |
| machine (bearer JWT, gateway plan) | 8.7 ms / 58 (paced) / 3.4 | 8.7 ms / 58 (paced) / 3.4 |

The remaining session statement is the route's own query (`from "session"`
listing the user's sessions), not authentication: the cookie lookup now runs
no SQL. The machine path does not use sessions, so it is unchanged, as
expected.

**Fail-closed check.** Session request with Redis up: `200`. With Redis
stopped: `500 FAILED_TO_GET_SESSION`. No access is granted; the status is
`500`, not `503`. Mapping it to `503` is a follow-up.

**Tests.**

- `session-redis.integration.test.ts` (own Redis testcontainer, real BetterAuth
  with `REDIS_URL` set): namespace, revocation of one and of all sessions,
  role change visible only after refresh, ban visible through the adapter.
- Unit: `session-store.test.ts` (namespace, TTL, `increment` window),
  `session-snapshot.test.ts`.
- Full suites green: 897 unit, 533 integration.

**Known limits.**

- `lastLoginAt` is written on every login and is not pushed to live
  snapshots. It is display-only and deliberately excluded to avoid an extra
  write and billing sync on each login.
- Bootstrap writes happen before the server listens; no live session exists
  then.
- A Redis outage refuses sessions rather than falling back to the database
  (fail closed). Resilience would need an explicit degraded mode, decided
  separately.

### P3 — result (2026-11-13)

- `GET /api/auth/jwks` now answers `Cache-Control: public, max-age=60`. Before,
  the header was absent. Verified over HTTP and by a unit test.
- Periphery audit: the gateway (`litellm/custom_auth.py`) caches the key set
  and the plan; the ioserver guide prescribes an in-process JWKS cache; the
  JWT guides say not to call `/userinfo` or introspection per request. No
  per-request call to `get-session` or introspection exists in the repository
  or the documented integrations. Downstream SDK repositories were not
  inspected from this repository.
