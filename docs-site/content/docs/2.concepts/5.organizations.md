Auth Service includes first-class support for **organizations** (companies / tenants) powered by BetterAuth's `organization()` plugin. Organizations are designed for a two-tier distribution model:

| Tier | Actor | Typical role |
|---|---|---|
| 1 | Reseller / distributor | Creates and owns organizations representing their end-clients |
| 2 | Integrator | Member of one or more organizations; manages IT resources scoped to those organizations |

![Organizations in the admin interface](/screenshots/organizations.png)

## Organization schema

| Field | Type | Description |
|---|---|---|
| `id` | string | Primary key |
| `name` | string | Display name (max 100 chars) |
| `slug` | string | Unique URL-safe identifier (lowercase alphanumeric + hyphens, max 50 chars) |
| `logo` | string | Optional logo URL |
| `domain` | string | Optional bare hostname used for domain verification and auto-enrollment |
| `domainVerifiedAt` | timestamp | When the DNS TXT proof was last accepted |
| `domainLastCheckedAt` | timestamp | Last automatic re-check of the DNS proof |
| `team` | boolean | `true` for a team created through the user API (see [Teams](#teams)). Set at creation and never changed; a team never carries a domain |
| `autoEnrollEnabled` | boolean | Whether new accounts with this verified email domain join automatically |
| `metadata` | JSON object | Arbitrary key-value metadata |
| `createdAt` | timestamp | Creation date |
| `createdBy` | string | Creator of a team; `null` for organizations created by administrators |

## Member roles

Every member of an organization holds one of three roles. They are BetterAuth's default organization roles and govern the native `/api/auth/organization/*` endpoints; the admin API below is gated by the global `admin` / `superadmin` role instead.

| Role | BetterAuth default permissions |
|---|---|
| `owner` | Update and delete the organization, create, update and delete members, create and cancel invitations |
| `admin` | Update the organization, create, update and delete members, create and cancel invitations |
| `member` | No organization, member or invitation permissions |

## The `org_id` claim

When a client requests the `org` scope during an OAuth 2.0 authorization flow, the **access token** (a JWT, so the request needs a `resource`) includes an `org_id` claim set to the ID of the organization the authorization is bound to:

```json
{
  "org_id": "org_01hwxyz..."
}
```

Which organization is used:

- A user who belongs to exactly one organization is bound to it implicitly.
- A user who belongs to several is redirected to `/select-org` during authorization and picks one; the page sets it as the session's active organization (`/api/auth/organization/set-active`) and the authorization resumes with that organization.
- A user who belongs to none gets no `org_id`.

The claim is not added to the ID token or to `userinfo`. Teams never bind an authorization: a user whose only organizations are teams gets no `org_id`.

Backend services can use this claim to:

- Scope database queries to the organization's data.
- Enforce CASL abilities with `{ org_id }` conditions.
- Isolate resources between tenants without additional requests to auth-service.

## Access control

Only users with the global role `admin` or `superadmin` can create organizations (BetterAuth's `allowUserToCreateOrganization` is restricted to them), and every admin API route below requires one of these roles. Regular `user`-role accounts can belong to organizations as members and can create teams through the user API (see [Teams](#teams)), but cannot create other organizations.

## Teams

A **team** is an organization a user creates for themselves through the SDK, for example to group the members of a third-party application. A team never carries a domain and never auto-enrolls anyone.

| Rule | Behaviour |
| --- | --- |
| Creation | `POST /api/user/organizations` with `{ name, logo? }`. The creator becomes its `owner`. `logo` must be `https`. The server generates the slug from the name and a random suffix; clients never choose it. `slug`, `domain`, `verifyDomain`, `autoEnrollEnabled`, `metadata` and `team` are refused with `ORG_003` |
| Quota | Each creator may own `TEAM_MAX_PER_USER` teams (default `10`). Beyond that, `ORG_013` |
| Invitation | An owner issues a token with `POST /api/user/organizations/:id/invitation-token`: `{ token, expiresAt }`, valid for 7 days and usable any number of times. The token is shown once and stored as a hash. Issuing a new one revokes the previous one; `DELETE` revokes it |
| Members | Any member lists the team with `GET /api/user/organizations/:id/members`: `{ username, displayName, role, joinedAt }` per member. The answer never contains an e-mail or a user id. A caller outside the team is `ORG_004`; a non-team organization is `ORG_012` |
| Joining | Any authenticated user redeems the token with `POST /api/user/organizations/join` and joins as `member`. An unknown, expired or revoked token is `ORG_014`; a user already in the team is `ORG_005` |
| Leaving | `POST /api/user/organizations/:id/leave`. The last owner of a team cannot leave (`ORG_011`), and companies cannot be left this way (`ORG_012`) |
| Authorization | The `organizations:self:manage` scope, granted to an application by its **Teams** option. Teams never bind `org_id` |

The listing `GET /api/user/organizations?team=true|false` filters the caller's memberships; without the parameter both kinds are returned, each with its `team` flag.

## Admin API endpoints

### List organizations

```
GET /api/admin/organizations
```

Supports pagination and filtering:

| Query parameter | Default | Description |
|---|---|---|
| `page` | `1` | Page number |
| `limit` | `20` | Results per page (max 100) |
| `search` | — | Filter by name or slug (case-insensitive, partial match) |
| `sortBy` | `name` | Sort field: `name`, `slug`, or `createdAt` |
| `sortOrder` | `asc` | `asc` or `desc` |
| `team` | — | `true` for teams only, `false` for organizations created by administrators only. Absent, both. Another value is refused with `ORG_003` |

Response includes a `memberCount` for each organization, plus `total`, `page` and `limit`.

### Create an organization

```
POST /api/admin/organizations
```

```json
{
  "name": "Acme Corp",
  "slug": "acme-corp",
  "logo": "https://example.com/logo.png",
  "metadata": { "region": "eu-west" }
}
```

`logo`, when given, must be a URL. Answers `201 { organization }`; a taken slug is refused with `ORG_002`.

### Get an organization

```
GET /api/admin/organizations/:id
```

Returns the organization with its full member list.

### Update an organization

```
PATCH /api/admin/organizations/:id
```

Accepts `name`, `slug`, `logo`, `domain`, `verifyDomain`, `autoEnrollEnabled`
and `metadata` (at least one). Changing `domain` clears its proof, disables
auto-enrollment and returns a fresh `domainVerification` challenge unless
`verifyDomain` is `false`. Setting `verifyDomain: false` on an unchanged domain
also clears its challenge and proof. Enabling auto-enrollment on an unverified
domain is refused with `ORG_009`.

### Request a domain challenge

```
POST /api/admin/organizations/:id/domain/verification
```

Returns `{ organization, domainVerification: { recordName, recordValue } }`.
Publishing the record is the administrator's responsibility.

### Verify a domain

```
POST /api/admin/organizations/:id/domain/verify
```

Checks the TXT record. A missing or mismatched record is refused with `ORG_007`;
a domain already verified by another organization with `ORG_008`.

### Delete an organization

```
DELETE /api/admin/organizations/:id
```

### List members

```
GET /api/admin/organizations/:id/members
```

Query parameters: `limit` (default 50, max 100), `offset` and `search` (user name or email). Returns `{ members, total }`.

### Add a member

```
POST /api/admin/organizations/:id/members
```

```json
{
  "userId": "...",
  "role": "member"
}
```

`role` is `owner`, `admin` or `member` (default `member`). A user who is already a member is refused with `ORG_005`.

### Update a member's role

```
PATCH /api/admin/organizations/:id/members/:memberId/role
```

```json
{
  "role": "admin"
}
```

`:memberId` is the membership id (the `id` of the member entry), not the user id. Answers `204`.

### Remove a member

```
DELETE /api/admin/organizations/:id/members/:userId
```

A user who is not a member is refused with `ORG_004`. Answers `204`.

### List invitations

```
GET /api/admin/organizations/:id/invitations
```

### Send an invitation

```
POST /api/admin/organizations/:id/invitations
```

```json
{
  "email": "newmember@example.com",
  "role": "member"
}
```

Sends an invitation email via BetterAuth's invitation flow. Requires SMTP to be configured for the email to be delivered.

### Cancel an invitation

```
DELETE /api/admin/organizations/:id/invitations/:invitationId
```

## Invitation acceptance

Organization invitations are created through the BetterAuth organization plugin
and emailed as a link to:

```
https://<auth-host>/accept-invitation?id=<invitation-id>
```

The page is always server-rendered from the template system (built-in
fallback), because it has no equivalent in the Vue SPA. It supports three
paths:

| Situation | Behaviour |
|---|---|
| The invitee has no account | Email/password registration is allowed even when registration is closed. The account is created verified, added to the invited organization and the invitation is marked accepted in one transaction. Social providers configured globally are also offered. |
| The invitee has an account | The page asks them to sign in. After sign-in, the invitation is accepted if the session email matches the invited address (`AUTH_014` otherwise) and is verified (`AUTH_015` otherwise). |
| A social provider callback returns a session | The provider account is accepted only when its verified email equals the invited address. The `user.create.before` hook aborts account creation otherwise. |

Acceptance never depends on a default organization: the organization is the
one carried by the invitation row. Application invitations are separate and
grant application access only; they do not create or assign an organization.

## Social profile company and domain auto-enrollment

`auth-service` **does not** use a social profile's `company` (or any equivalent
provider field) to assign an organization. Social profile fields are
self-declared and untrusted: a user can type any company name in a provider
profile, so treating it as membership would let them claim access to a tenant.

Membership is granted by an explicit action or by a verified email domain:

- an organization invitation accepted by the matching email address;
- an administrator adding the member through the admin API or UI;
- **domain auto-enrollment**, when the organization enabled it on a domain it
  proved ownership of.

### Domain verification

Only global `admin` / `superadmin` accounts can manage domains. Setting a
domain gives it no power: the organization must publish a TXT record supplied
by the service:

```
_circle-auth.example.com.  TXT  "circle-auth-verification=<token>"
```

`POST /api/admin/organizations/:id/domain/verify` resolves the record through
the system resolver. On success the domain is marked verified and may be
attached to one organization only (a partial unique index enforces this). A
new challenge can be issued at any time; it invalidates the previous proof and
disables auto-enrollment.

The published proof is re-checked at most once every 24 hours when a matching
sign-up is evaluated, and a background monitor re-validates every enabled
organization every 6 hours. If it disappears or changes, auto-enrollment is
disabled and the organization owners receive an email. Existing members are not
removed.

### Auto-enrollment rules

When `autoEnrollEnabled` is on and the email domain matches **exactly**:

- the account must have been created through self-service sign-up
  (email/password or a social provider); admin-created accounts, imports and
  invitation-backed registrations are excluded;
- the email must be verified; email/password sign-ups are enrolled after the
  verification link is clicked, social sign-ups immediately because the
  provider already verified the address;
- a user who already belongs to any organization is left untouched;
- the default organization role is `member`.

Matching is case-insensitive and IDN-normalised, but subdomains are not
matched: `dev.example.com` does not join `example.com`. There is no special
handling for public domains; they simply cannot be verified by a real domain
owner.
