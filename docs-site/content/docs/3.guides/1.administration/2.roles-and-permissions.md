title: Roles and permissions
description: Define per-application roles and permissions, assign them to users, and consume them in tokens.
---

Auth Service implements a per-application RBAC model. Each application has its own independent set of roles and permissions — a role named `editor` in App A is completely separate from a role named `editor` in App B.

All endpoints below require an `admin` or `superadmin` session. The admin interface shows an application's roles, permissions and the matrix between them. In the matrix every cell toggles one assignment, rows are grouped by resource, the headers stay in view while scrolling and are turned sideways when there are many roles. Two filters narrow the roles and permissions on screen, and **Print** produces a black-and-white, landscape copy of the **whole** matrix (the filters are ignored) for audits.

## Concepts

- **Role** — a named group (e.g. `editor`, `beta-tester`) that can be assigned to users within a specific application. Each role has an optional `isDefault` flag; when `true`, new users granted access to the application receive this role automatically.
- **Permission** — a `resource` + `action` pair (e.g. `articles` + `read`, or `comments` + `write`). Permissions are attached to roles, not to users directly.
- When the `roles` and `permissions` scopes are requested in an OAuth flow, Auth Service resolves the user's roles for the application, then flattens all permissions across those roles into the token.

## Roles

### List roles

```sh
GET /api/admin/applications/:appId/roles
```

Returns each role with its `permissionIds` array.

### Create a role

```sh
POST /api/admin/applications/:appId/roles
Content-Type: application/json

{
  "name": "editor",
  "description": "Can create and edit content",
  "isDefault": false
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `name` | string | required | Role name (1–64 chars, unique per application) |
| `description` | string | — | Optional description (max 250 chars) |
| `isDefault` | boolean | `false` | Auto-assign when granting user access to the app |

### Update a role

```sh
PATCH /api/admin/applications/:appId/roles/:roleId
{ "description": "Can edit content", "isDefault": false }
```

Only `description` (`null` clears it) and `isDefault` can change, and at least one must be sent. The **name is immutable**: downstream applications authorise against it, so a payload containing `name` (or any other field) is rejected with `400 APP_001`. To rename a role, create the new one and move the users over. Making a role the default demotes the previous default.

### Delete a role

```sh
DELETE /api/admin/applications/:appId/roles/:roleId
```

Returns `400 PERM_006` if any users currently hold this role within the application.

## Permissions

### List permissions

```sh
GET /api/admin/applications/:appId/permissions
```

### Create a permission

```sh
POST /api/admin/applications/:appId/permissions
Content-Type: application/json

{
  "resource": "articles",
  "action": "write"
}
```

| Field | Type | Default | Description |
|---|---|---|---|
| `resource` | string | required | Resource name — alphanumeric, dots, underscores, hyphens (1–128 chars) |
| `action` | `"read"` \| `"write"` | `"read"` | Access level |

The pair (`resource`, `action`) must be unique per application. Returns `409 PERM_005` on conflict.

### Delete a permission

```sh
DELETE /api/admin/applications/:appId/permissions/:permissionId
```

### Assign / unassign permissions to a role

```sh
# Assign — permissionId is sent in the request body
POST /api/admin/applications/:appId/roles/:roleId/permissions
{ "permissionId": "<permission-id>" }

# Unassign
DELETE /api/admin/applications/:appId/roles/:roleId/permissions/:permissionId
```

The role and the permission must both belong to `:appId`, otherwise the call fails with `404 PERM_002` / `404 PERM_003`. Assigning twice is not an error.

## Assign a role to a user

A user's role for an application is part of their access record. Set it when
granting access, or update it afterwards — there is no separate role-assignment
endpoint.

```sh
# When granting access
POST /api/admin/applications/:id/users
{ "userId": "<user-id>", "roleId": "<role-id>" }

# Update an existing access record
PATCH /api/admin/applications/:id/users/:userId
{ "roleId": "<role-id>" }
```

## Token claim format

When the `roles` and `permissions` scopes are included, the id_token carries:

```json
{
  "roles": ["editor"],
  "permissions": ["articles", "comments.write"]
}
```

Permission strings use the format `"resource"` for read actions and `"resource.write"` for write actions. Permissions are deduplicated across all roles the user holds.
