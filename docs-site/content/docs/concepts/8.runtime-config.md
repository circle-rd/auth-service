# Dynamic audience and CORS

Auth Service manages OAuth audiences and CORS origins dynamically at runtime. When an application is created or updated, the service automatically updates the valid audiences and CORS origins — no server restart is required.

## How it works

### Seeding

At startup, auth-service seeds the runtime state from two sources:

1. **Environment variables** — `OAUTH_VALID_AUDIENCES` and `CORS_ORIGINS` provide the initial values.
2. **Database** — the `applications.url` column is queried and each application's URL is added to the valid audiences list.

### Runtime updates

Every time an application is created, updated, or deleted via the admin API:

1. The application's `url` is added to (or removed from) the valid audiences list.
2. The application's `redirectUris` are added to (or removed from) the CORS origins set.
3. These changes take effect **immediately** — no restart needed.

### Why mutable arrays work

- `@better-auth/oauth-provider` spreads `validAudiences` into a new `Set` on every token request (`new Set([...opts.validAudiences])`), so mutations are picked up immediately.
- BetterAuth reads `trustedOrigins` on every request for CSRF checks.
- Fastify CORS uses an `origin` function that closes over `corsOrigins`.

## Configuration

### Via environment variables (initial values)

```sh
# Comma-separated list of valid OAuth audiences
OAUTH_VALID_AUDIENCES=https://api.example.com,https://mcp.example.com

# Comma-separated list of allowed CORS origins
CORS_ORIGINS=https://app.example.com,https://admin.example.com
```

### Via application creation (runtime)

When you create an application with a `url` field, that URL is automatically added to the valid audiences:

```sh
POST /api/admin/applications
Content-Type: application/json

{
  "name": "My API",
  "slug": "my-api",
  "url": "https://api.example.com",
  "redirectUris": ["https://app.example.com/callback"]
}
```

After this request:
- `https://api.example.com` is a valid `aud` for JWT access tokens.
- `https://app.example.com` is a valid CORS origin.
- Clients can include `resource=https://api.example.com` in authorization requests to receive JWTs.

## Runtime state

The runtime state is exposed via the admin services endpoint:

```sh
GET /api/admin/services
Authorization: Bearer <admin_session>
```

## MCP server example

For MCP servers, the audience URL is critical — it tells auth-service to issue a JWT instead of an opaque token:

```sh
# 1. Register the MCP server with its audience URL
POST /api/admin/applications
Content-Type: application/json

{
  "name": "My MCP Server",
  "slug": "my-mcp-server",
  "isPublic": true,
  "url": "https://mcp.example.com",
  "allowedScopes": ["openid", "profile", "email", "roles", "permissions", "features", "org"],
  "redirectUris": ["https://mcp.example.com/callback"]
}

# 2. The MCP server URL is now a valid audience
# 3. Clients can request JWTs by including resource=https://mcp.example.com
```

## Security considerations

1. **Audience validation** — Always validate the `aud` claim in received JWTs to ensure the token was intended for your service.
2. **CORS origins** — Only include origins you trust. Wildcard `*` is not supported.
3. **Cross-subdomain cookies** — Set `SESSION_DOMAIN` to enable cross-subdomain session cookies (e.g., `SESSION_DOMAIN=example.com` allows `auth.example.com` to set cookies readable by `app.example.com`).
