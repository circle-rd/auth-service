title: LiteLLM gateway
description: Run a LiteLLM proxy (LLMs and MCP servers) authenticated with auth-service access tokens.
---

auth-service ships an optional [LiteLLM](https://docs.litellm.ai/) proxy behind
the Docker Compose profile `llm`. Applications obtain an auth-service access
token for the gateway and call LiteLLM with it; no per-user API key is issued.

> Usage is billed against the user's [wallet](/docs/reference/api-reference):
> see [Credit and billing](#credit-and-billing) below and the
> [programme plan](/docs/project/litellm-wallet-plan).

## How authentication works

LiteLLM's built-in JWT auth is an Enterprise feature, so the gateway validates
tokens in `litellm/custom_auth.py` (wired through `general_settings.custom_auth`):

- the signature is checked against the auth-service JWKS (`/api/auth/jwks`, EdDSA or RS256 depending on `JWT_PRIMARY_ALG`);
  an unknown `kid` triggers one refetch per 30 seconds, so key rotation is picked up;
- `iss` must equal `BETTER_AUTH_URL` and `aud` must contain `LITELLM_PUBLIC_URL`;
- `client_credentials` tokens are rejected (they carry no user: `sub` equals `azp`);
- the user is the token `sub`, the calling application is `azp`, and the request
  runs under the **team** of that application (see below): a token whose
  application has no team is refused with `403`;
- a user token only reaches the **LLM and MCP routes** (`/v1/chat/completions`,
  `/v1/models`, `/mcp`, `/{server}/mcp`…): administration routes such as
  `/key/generate`, `/user/new`, `/team/new` or `/spend/logs` answer `403`.
  Without this, any signed-in user could mint LiteLLM virtual keys that outlive
  their auth-service access, or create users and teams;
- `LITELLM_MASTER_KEY` still works for administration.

The gateway is registered as an application (`litellm`) whose `url` is the
resource identifier (RFC 8707). A client application receives a JWT only when it
sends `resource=<LITELLM_PUBLIC_URL>` **and** lists that URL in its
[`allowedResources`](/docs/concepts/runtime-config). Public (PKCE) and
confidential applications are both supported.

## Setup

Nothing has to be generated or registered by hand: the `litellm-setup` service
of the compose file does it at every start. The only setting to provide is the
public URL of the gateway (the token audience), in `.env`:

```sh
LITELLM_PUBLIC_URL=https://llm.example.com
COMPOSE_PROFILES=llm
```

Then start the stack:

```sh
docker compose up -d
```

- `litellm-setup` (the auth-service image, a one-shot container) waits for
  auth-service to be healthy, then
  - creates the `litellm` database next to the auth one if it is missing
    (`LITELLM_DB_ADMIN_URL`, set by the compose file);
  - copies the gateway config (`litellm/config.yaml`, `custom_auth.py`,
    `circle_wallet.py`, shipped inside the image) into a shared volume, so the
    config always matches the auth-service version whose tokens it validates;
  - generates `LITELLM_MASTER_KEY` and `LITELLM_SALT_KEY` once, unless you
    supplied them in `.env` (a supplied value wins and is stored);
  - signs in with `ADMIN_EMAIL` / `ADMIN_PASSWORD` and registers the `litellm`
    application (whose `url` is the token audience) and the `litellm-wallet`
    machine client with the `wallet:debit` and `wallet:read` scopes, and keeps
    that client's secret; a missing or rejected secret (for example after
    recreating the database) is rotated;
  - stores the three secrets in `secrets.env` on the shared volume, which only
    `litellm` reads.
- `litellm` starts once the setup succeeded.

It is safe to re-run and never regenerates a stored secret. Never change the
salt key once models have been added: it encrypts the provider credentials.
After the secret of `litellm-wallet` was rotated, recreate `litellm`
(`docker compose up -d --force-recreate litellm`) so it picks up the new one.

The setup signs in as the administrator, so that account must not require MFA
the first time it runs; it fails with a clear message otherwise (`docker compose
logs litellm-setup`). Once a run has completed (keys, wallet secret and, with the
sign-in on, the SSO secret are stored), enabling MFA on that account no longer
blocks the gateway: the next runs detect it, log a warning and exit successfully
without provisioning anything. A new `LITELLM_PUBLIC_URL` or `--grant` is only
applied by a run that can sign in, so use an administrator without MFA for those.

**Signing in to the LiteLLM admin interface.** `litellm-setup` also registers the
private application `litellm-ui` and turns on SSO in LiteLLM: the login page
sends you to auth-service, and your account there is your LiteLLM account (no
more `admin` and master key: with the sign-in on, no username/password login
reaches the interface, so an auth-service outage does not open a way in). Access is managed in auth-service,
on the application's user list:

- a user without access to `litellm-ui` cannot sign in;
- the application role `admin` becomes LiteLLM `proxy_admin`; `user`, or no
  role, becomes the read-only `proxy_admin_viewer`;
- the administrator who ran the setup holds `admin` from the start; give the
  others access with the role you want in the application's page of the admin
  interface.

The whole sign-in configuration (authorize, token and userinfo endpoints, PKCE,
role mapping, `PROXY_BASE_URL` and `AUTO_REDIRECT_UI_LOGIN_TO_SSO`) is written by
`litellm-setup` into `secrets.env`, next to the client id and secret, and is
refreshed at every start: the `litellm` service of your compose file needs none of
those `GENERIC_*` variables, and a copy of an older definition cannot leave the
gateway half-configured.

The configuration shows in LiteLLM under Settings → Admin Settings → SSO
Settings. The interface is only reachable from the administration network (see
[Keeping the admin interface private](#keeping-the-admin-interface-private)),
so the sign-in is too. LiteLLM limits free SSO to 5 users. Set
`LITELLM_SSO_ENABLED=false` to turn it off: the master-key login of the
interface then comes back (`disable_password_login_when_sso_enabled` only acts
while SSO is configured). The master key keeps working on the API
(`Authorization: Bearer`), which is how `pnpm llm:smoke` and administration
scripts use it.

**Allowing applications.** A client application receives a LiteLLM token only if
the gateway URL is in its `allowedResources`. In the create / edit dialog of the
application, switch on **LiteLLM support**: it adds the gateway URL (the `url` of
the `litellm` application), the Auth Service URL (the `url` of the `auth-service`
application, needed to read the user's credit) and the `wallet:self:read` scope,
and hides them from the resource list and the scope chips; any other resource is
still entered by hand. Switching it off removes the three. The switch is disabled
when the two system applications are missing. From a checkout,
`pnpm llm:setup -- --grant=my-app,my-other-app` still adds the gateway URL.

**Who must be assigned.** Users are granted access to the *client* application
(for example `reverse-box`), which is what the token policy checks. The system
applications need no assignment: `litellm` and `auth-service` are only token
audiences and `litellm-wallet` is the gateway's own machine client. Only
`litellm-ui` takes users: the administrators of the LiteLLM interface. System
applications are hidden from the Applications tab of a user's profile; in the
admin Users pages they are hidden too, except that a user assigned to
`litellm-ui` shows a single **LiteLLM** entry (its role tells administrator from
viewer).

**Reading the keys.** You normally do not need them. The master key signs you in
to the LiteLLM admin interface and is what `pnpm llm:smoke` uses:

```sh
docker compose exec litellm sh -c '. /app/gateway/secrets.env; echo $LITELLM_MASTER_KEY'
```

**Running from a checkout instead.** `pnpm llm:setup` does the same work against
a running auth-service and writes the secrets to `.env` (or to `LITELLM_STATE_FILE`
when set); it is the path used by development setups that run the compose file
with a hand-written `.env`.

### Verify the whole chain

```sh
pnpm llm:smoke
```

It needs `LITELLM_MASTER_KEY` and `LITELLM_WALLET_CLIENT_SECRET` in the
environment (both are in `secrets.env`; `pnpm llm:setup` from a checkout puts
them in `.env`). The smoke test creates two temporary applications (public and
confidential) and a mock model, then checks that user tokens are accepted and
that `client_credentials`, wrong-audience, tampered, malformed and missing tokens
are rejected, exercises the wallet API with the gateway credentials and the
billing path, and deletes what it created.

## Production deployment

Deployments that consume the published image only need the compose file and a
`.env`; no file from the repository has to be copied to the server and no
command has to be run: `docker compose up -d` provisions the gateway (see
[Setup](#setup)).

- **Profiles.** `litellm*` services belong to the `llm` profile and `redis` to
  the `redis` profile, so a plain `docker compose up` ignores them. Activate them
  durably in the `.env` next to the compose file:

  ```sh
  COMPOSE_PROFILES=llm,redis
  ```

- **Health check.** `litellm-setup` and `litellm` wait for `auth-service` to be
  `healthy`: the auth-service container must define a `healthcheck` (as in
  `docker-compose.yml`), otherwise compose stops with `has no healthcheck
  configured`.
- **Setup service.** Give `litellm-setup` the variables it needs: `BETTER_AUTH_URL`,
  `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `LITELLM_PUBLIC_URL`, `AUTH_SERVICE_URL` (the
  internal address of auth-service, for example `http://auth:3001`) and
  `LITELLM_STATE_FILE=/config/secrets.env`, with the shared volume mounted on
  `/config`. Copy the `litellm-setup` and `litellm` definitions of
  `docker-compose.yml`; `litellm`'s entrypoint reads `secrets.env`.
- **Routing.** Expose `litellm` through the reverse proxy on the host used as
  `LITELLM_PUBLIC_URL` (with Traefik: router and TLS labels, service port
  `4000`) and do not publish port `4000` on the host. Fetch the signing keys over
  the Docker network (`JWT_PUBLIC_KEY_URL=http://<auth-service>:3001/api/auth/jwks`)
  and keep the public URLs for `JWT_ISSUER` and `JWT_AUDIENCE`.
- **Secrets.** Nothing to invent: they are generated on first start and kept on
  the shared volume. To choose them yourself, set `LITELLM_MASTER_KEY` and
  `LITELLM_SALT_KEY` in `.env`: `sk-` followed by 64 hex characters (LiteLLM
  requires the `sk-` prefix on the master key), for example
  `echo "sk-$(openssl rand -hex 32)"`. The wallet client secret is always issued
  by auth-service.

## Credit and billing

`litellm/circle_wallet.py` ties the gateway to the user's wallet. It only
concerns requests authenticated with an auth-service user token; the master key,
the admin UI and LiteLLM virtual keys are service traffic and are not billed.

**Before a call**, the hook asks the wallet API whether the user can spend. With
no credit (a zero or negative balance) the call is refused with **HTTP 402**
(`insufficient_credit`). The answer is kept for 5 seconds
(`WALLET_BALANCE_TTL_S`), so a top-up is seen within that delay.

**After a successful call** (LLM completion, embedding… or MCP tool call), the
hook reports the provider cost to the wallet API, which prices it and debits the
user: `cost in USD × exchange rate × (1 + margin / 100)`, rounded up to a
micro-euro, never free. The gateway holds no pricing rule: a superadmin changes the
rate and the margin in the **Wallets** page of auth-service (saved changes apply to
the next call, keep their author and reason, and charges already made are not
touched; `WALLET_USD_TO_EUR_RATE` and `WALLET_MARGIN_PERCENT` only provide the
starting values). The price of each model and tool is LiteLLM's: set it there, and
keep any margin in one place, preferably auth-service, since LiteLLM's own
provider margin would add up with it unseen. The ledger row records the raw quantities
(model, tokens, or MCP server and tool), the dollar cost, the rate and the margin,
and the calling application, so a charge can be audited and re-priced.

- **Models without a price are free.** LiteLLM computes the cost from its price
  list; a local vLLM model has none. Give it one in its model settings
  (`input_cost_per_token`, `output_cost_per_token`), or its calls cost nothing.
- **MCP tools.** LiteLLM bills a tool call only if the server declares a cost:
  `mcp_info.mcp_server_cost_info.default_cost_per_query` (and
  `tool_name_to_cost_per_query` for specific tools), in dollars.
- **MCP access.** An application reaches only the MCP servers allowed to its team
  in the LiteLLM admin interface (see above); with none, no server is reachable.
- **Debt.** Usage reported after a call is always recorded, even beyond the
  balance: the balance goes negative, blocks the next calls, and is repaid by the
  next top-up.

**When auth-service is unreachable**, calls continue for a user whose balance was
read in the last minute (`WALLET_STALE_BALANCE_S`) and are refused with 503
otherwise: no credit information, no spending. Debits are written to disk
(`/var/lib/circle-wallet/pending`, a volume) *before* being sent and retried with
a growing delay, also after a restart and without any new traffic. Each debit has
its own generated idempotency key, so a retry can never charge twice, and nothing
the client sends (such as an `x-litellm-call-id` header) can make two calls share
one. A debit the wallet
rejects for good (unknown user, conflicting replay) is set aside in `dead/` with an
error in the logs: look there if a balance seems too high.

Per-application plans and subscriptions are unchanged: the wallet covers the
LLM and MCP usage only.

### Limits per user

The credit is checked before a call and billed after it, so a burst of calls on a
small balance can overshoot into debt. Two ceilings per user, enforced by the hook
in each gateway process, bound it (HTTP `429` beyond them):

- `WALLET_MAX_REQUESTS_PER_MINUTE` (default `120`): billable calls, MCP included;
- `WALLET_MAX_SPEND_PER_MINUTE_USD` (default `5`): provider cost, in dollars as
  LiteLLM reports it, billed over the last minute. It caps how fast a burst of
  expensive calls can run up a debt; raise it if your users legitimately run
  costly models in quick succession;
- `WALLET_MAX_CONCURRENT_CALLS` (default `8`): model calls in progress. A slot is
  released when the call completes, so keep it at `2` or more: the completion
  event can arrive just after the response.

A debt stays small, then blocks every further call until the next top-up. It is
not strictly bounded: calls already running when the balance reaches zero still
complete and are billed in full (see decision D33 of the plan).

### Checking the gateway against the wallet

```bash
pnpm llm:reconcile        # the last 24 hours
pnpm llm:reconcile 72     # the last 72 hours
```

The script compares the gateway's spend logs with the wallet's usage debits and
exits non-zero on any difference:

- `UNBILLED`: a billable call the wallet never charged (look in the gateway's
  `dead/` spool directory and its logs);
- `MISMATCH`: the same call with another user or provider cost;
- `ORPHAN`: a charge with no gateway call behind it;
- `DUPLICATE`: several charges share one call id: a double charge, or a client
  reusing the `x-litellm-call-id` header (each call is still billed, but someone
  is probing). The smoke test does it on purpose.

Anything from the last 10 minutes is left out: a debit may still be waiting in the
retry spool and the gateway writes its spend logs in delayed batches. Only calls
authenticated with a user token are compared; a LiteLLM virtual key tied to a
user would show up as `UNBILLED`.

The gateway also logs, at every retry pass, how many debits are stuck or were
refused for good (`dead/`); watch for these lines. Administrator balance changes
and every usage debit are logged by auth-service without any token or secret.

## Calling the gateway from an application

An application signs the user in through auth-service, then calls LiteLLM with the
access token as a bearer, like any OpenAI-compatible endpoint:

1. Allow the application to request the gateway: add the gateway URL to its
   `allowedResources` (or `pnpm llm:setup --grant=<slug>`).
2. Run the authorization-code flow (PKCE for a public application) with
   `resource=<LITELLM_PUBLIC_URL>` so that the access token is a JWT for the gateway.
3. Call `POST <gateway>/v1/chat/completions` with the access token in the
   `Authorization` header. Handle `402` (no credit) by sending the user to
   their wallet.
4. To read the wallet server-side with the same user, request a second
   user-bound token for auth-service itself: keep the application linked to
   `resource=<BETTER_AUTH_URL>`, request the scope `wallet:self:read`, and
   call `GET /api/user/wallet`, `/transactions`, `/stats` or `/topup-options`
   with that bearer token. The token must be a JWT whose `aud` contains
   `BETTER_AUTH_URL`; a JWT minted for LiteLLM is rejected there.
5. When using refresh tokens, keep sending `resource=<BETTER_AUTH_URL>` on the
   refresh grant that should keep wallet API access.

Users top up their own credit from the **Credit** tab of their profile page (Stripe, when `STRIPE_SECRET_KEY` is set); otherwise a superadmin records the credit with `POST /api/admin/wallets/users/:userId/topups` (with the invoice reference). The full application-side walkthrough, error handling included, is in [LiteLLM gateway and credit wallet in an application](/docs/guides/integration/litellm-app).

## Keeping the admin interface private

The admin UI (`/ui`), the management API (`/key`, `/model`, `/team`…), `/docs`
and `/health` should not be reachable from the Internet. With Traefik, publish
two routers on the gateway host: a high-priority one for the client routes, and
a catch-all restricted to the administration network. Anything not listed in the
client router stays private by default, including routes added by a future
LiteLLM version.

```yaml
labels:
  - traefik.enable=true
  - traefik.http.services.litellm.loadbalancer.server.port=4000

  # Client routes (LLM API + MCP): open.
  - traefik.http.routers.litellm.rule=Host(`llm.example.com`) && PathRegexp(`^/(v1|chat|completions|embeddings|models|responses|images|audio|rerank|moderations|files|batches|anthropic|mcp|mcp-rest)(/.*)?$$|^/[^/]+/mcp(/.*)?$$`)
  - traefik.http.routers.litellm.priority=100

  # Everything else (UI, management API, docs, health): administration network only.
  - traefik.http.routers.litellm-admin.rule=Host(`llm.example.com`)
  - traefik.http.routers.litellm-admin.priority=1
  - traefik.http.routers.litellm-admin.middlewares=litellm-admin
  - traefik.http.middlewares.litellm-admin.ipallowlist.sourcerange=10.1.0.0/24
```

(Add the `entrypoints` and `tls` labels of your setup to both routers. `$$` is
the compose escape for a literal `$`.)

Notes:

- The allow list uses the connection address, never `X-Forwarded-For`. Behind a
  load balancer, enable the PROXY protocol on the entrypoint so that address is
  the real client's: a forged `X-Forwarded-For` is then ignored.
- The client list is an allow list: add a prefix to the first regular expression
  when a new client route has to be public.
- The master key still works on the client routes: it is a secret, not a
  network-scoped credential, so keep it out of applications.
- Do not publish port `4000` on the host (the `docker-compose.yml` example
  publishes it for local use only).
- Behind the proxy, LiteLLM only sees the proxy's address. The shipped
  `config.yaml` therefore sets `general_settings.trusted_proxy_ranges` to the
  private address ranges (`10/8`, `172.16/12`, `192.168/16`), so the Admin UI
  sign-in throttle (6 failed attempts, then a 5 minute block) counts each visitor
  separately instead of locking everyone out together. It also removes LiteLLM's
  startup warning about it. If other private clients can reach port `4000`
  directly, narrow the list to your proxy's network.

Tested with Traefik 3.6 on two networks: from the administration subnet every
route answers; from another subnet the client routes answer and everything else
returns `403`, including with a forged `X-Forwarded-For`, dot segments and
encoded characters (LiteLLM answers `404` to those anyway).

## One gateway team per application

Turning on **LiteLLM support** for an application creates a **team** on the gateway
named after the application (team id = application slug). The team is what
carries everything specific to that application: the models it may call, its MCP
servers, its budget and its rate limits. auth-service only makes the team
*exist*; **all of that is configured in the LiteLLM admin interface** (Teams),
by a gateway administrator, and is never overwritten by auth-service.

- A new team is **closed**: it has no model (`no-default-models`), so a call
  answers `403 team_model_access_denied` until an administrator grants models.
  The same holds for MCP servers (a team with no MCP permission reaches none).
- The team is created **before** the application is saved: if the gateway cannot
  do it, the save fails with `SRV_004` and nothing changes. Enabling the support
  on a team that already exists (made by hand, or by an earlier activation) adopts
  it as is; a block placed by an administrator is kept.
- **Turning the support off blocks the team** (calls answer `401`, its
  configuration is kept so that turning it back on restores it). **Deleting the
  application deletes the team.** A team made by hand is never touched unless it
  carries the `managed_by: auth-service` marker in its metadata.
- auth-service reconciles at startup and every five minutes (missing teams are
  created, teams of applications that lost the support are blocked), so a gateway
  that was down during a change catches up.
- The gateway reads a team at most once a minute: a model granted, a limit changed
  or a team blocked or unblocked applies within about a minute.

The one-shot `litellm-provision` service issues auth-service a gateway key that
may only call the team routes (`/team/new`, `/info`, `/list`, `/update`, `/block`,
`/unblock`, `/delete`): it cannot add models, mint keys or serve LLM calls. It is
written to the `litellm_provisioner` volume, which only `litellm-provision` can
write and auth-service reads (`LITELLM_PROVISIONER_KEY_FILE`). It runs at every
start, keeps a key that still works and replaces one that does not (the previous
one is revoked, a single key exists). Without a deployed gateway (no `litellm`
application, or no `LITELLM_URL`) none of this is active.

## Adding models

Models are stored in the LiteLLM database, so no provider key lives in the
repository. Use the LiteLLM admin UI or `POST /model/new` with the master key,
then grant them to the teams of the applications that may use them.

## Variables

| Variable | Default | Description |
|---|---|---|
| `LITELLM_PUBLIC_URL` | — | Public URL of the gateway; access-token audience and `url` of the `litellm` application |
| `LITELLM_URL` | `LITELLM_PUBLIC_URL` | URL the smoke test calls, when different from the public one |
| `AUTH_SERVICE_URL` | `BETTER_AUTH_URL` | URL the scripts use to reach auth-service |
| `LITELLM_MASTER_KEY` | generated | LiteLLM admin key. Optional: a value set here is used instead of a generated one |
| `LITELLM_SALT_KEY` | generated | Encrypts provider credentials in the LiteLLM database. Optional, never change it once models exist |
| `LITELLM_WALLET_CLIENT_SECRET` | generated | Secret of the `litellm-wallet` machine client (client id `litellm-wallet`) the gateway hook uses to call the wallet API. Issued by auth-service and kept in `secrets.env`; only needed in the environment of `pnpm llm:smoke` |
| `LITELLM_DB_ADMIN_URL` | — | On `litellm-setup`: connection to any database of the postgres server, with a role allowed to create databases; used to create the `litellm` one. Set by the compose file, unset from a checkout |
| `LITELLM_SSO_ENABLED` | `true` | On `litellm-setup`: sign in to the LiteLLM admin interface through auth-service. `false` turns it off |
| `LITELLM_STATE_FILE` | `.env` | File where `pnpm llm:setup` stores the secrets; `/config/secrets.env` in the `litellm-setup` container |
| `WALLET_USD_TO_EUR_RATE` / `WALLET_MARGIN_PERCENT` | — / `0` | Starting values on **auth-service**, see the environment reference; edited afterwards in the Wallets page. An exchange rate must exist somewhere for billing to work |
| `WALLET_BALANCE_TTL_S`, `WALLET_STALE_BALANCE_S`, `WALLET_RETRY_INTERVAL_S` | `5`, `60`, `15` | Optional, on the gateway: balance cache, tolerance when the wallet is unreachable, base retry delay for spooled debits |
| `WALLET_MAX_REQUESTS_PER_MINUTE`, `WALLET_MAX_SPEND_PER_MINUTE_USD`, `WALLET_MAX_CONCURRENT_CALLS` | `120`, `5`, `8` | Optional, on the gateway: per-user ceilings on billable calls per minute, spend per minute (USD) and model calls in progress |
| `LITELLM_URL` (auth-service) | — | Internal URL of the gateway (`http://litellm:4000` in the compose file). Enables the team management; unset, applications get no team |
| `LITELLM_PROVISIONER_KEY_FILE` | `/run/litellm-provisioner/key` | Where auth-service reads the gateway key issued by `litellm-provision` |
| `LITELLM_PORT` | `4000` | Host port published by the `litellm` service |
| `LITELLM_IMAGE` | `ghcr.io/berriai/litellm:v1.105.0` | Pinned image; re-run `pnpm llm:smoke` before bumping it |

## Troubleshooting

| Symptom | Cause |
|---|---|
| `/authorize` redirects with `invalid_target` | The application does not list the gateway URL in `allowedResources` |
| Access token is opaque (not a JWT) | The authorization request omitted `resource` |
| `401 Invalid or expired access token` | Wrong `iss`/`aud` (check `BETTER_AUTH_URL` and `LITELLM_PUBLIC_URL`), expired token, or JWKS unreachable from the container |
| `litellm` does not start, `litellm-setup` exited with an error | Read `docker compose logs litellm-setup`: a missing `LITELLM_PUBLIC_URL`, `ADMIN_EMAIL` or `ADMIN_PASSWORD`, an administrator who requires MFA, or auth-service unreachable at `AUTH_SERVICE_URL` |
| `litellm` exits at start with `WALLET_CLIENT_SECRET must be set` | The deployment does not run `litellm-setup`, or its `litellm` service does not read `secrets.env`: use the definitions of `docker-compose.yml` |
| `GENERIC_AUTHORIZATION_ENDPOINT not set` when signing in to the admin interface, or no redirect to the SSO | The gateway started with a `secrets.env` written by an older `litellm-setup`, or `litellm-setup` did not run since the update: re-run it (`docker compose up -d litellm-setup`) and recreate `litellm`; check with `docker compose exec litellm sh -c '. /app/gateway/secrets.env; echo $GENERIC_AUTHORIZATION_ENDPOINT'` |
| Saving an application with LiteLLM support fails with `SRV_004` | The gateway is down, or `litellm-provision` has not delivered the key yet: `docker compose up -d litellm-provision`, then save again |
| `403 Application '…' has no team on this gateway` | The application has no team: enable LiteLLM support in its form (or wait for the reconciliation) |
| `403 team_model_access_denied` | The application's team has no access to that model yet: grant it in the LiteLLM admin interface (Teams) |
| `litellm-setup` reports HTTP 429 | auth-service rate-limits the token endpoint: wait a minute and re-run |
