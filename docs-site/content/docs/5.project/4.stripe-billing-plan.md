## 1. Goal

An installation is owned by **one company** and exposes **several
applications**. It uses **one Stripe token** (one Stripe account), configured
through the environment exactly like the other providers (Google, GitHub, …) —
see D2. Two billing mechanics coexist, deliberately (D1):

1. **Prepaid credit wallet** (already shipped, see the
   [LiteLLM gateway & credit wallet plan](/docs/project/litellm-wallet-plan)) —
   the user tops up a euro balance and spends it across applications. This is
   the **multi-application token-usage** mechanic, metered by the LiteLLM
   gateway.
2. **Paid subscription** (this programme) — a paid product plan opens access on
   month **N**; its **metered** features are billed at the end of the billing
   period, i.e. month **N+1**. This is the **per-product** mechanic.

An application can **delegate the whole billing surface to auth-service**
(subscription, invoices, usage) through the server-rendered
[templates](/docs/guides/administration/custom-templates) mechanism, or
**present the billing itself** by calling auth-service: it reports billable
usage through a callback and reads a user's subscription, consumption and
invoices through an API scoped to its own application.

Operator and user never touch the Stripe dashboard: the admin interface creates,
updates and deletes the Stripe objects (products, prices, meters, subscriptions)
and the user pays on Stripe's own Checkout / Billing Portal pages (D4).

## 2. Architecture

```
                 admin UI                          user (profile / app page)
                    │                                        │
             plans + prices + meters                 subscribe / invoices / usage
                    ▼                                        ▼
   ┌────────────────────────────── auth-service ──────────────────────────────┐
   │  services/billing/  ── Stripe API ──►  Products · Prices · Meters          │
   │        ▲                                Customers · Subscriptions         │
   │        │                                Invoices · Checkout · Portal       │
   │        │                                                                  │
   │  subscription_plan_prices (fixed | metered)                               │
   │  user_subscriptions (+ stripe_subscription_id, status, period)            │
   │  billing_customers · billing_usage_* · stripe_invoices (cache)            │
   └───────────────▲───────────────────────────▲──────────────────────────────┘
                   │ webhook (invoice.*, subscription.*)     │ usage callback
                   │                                        │ (POST /api/consumption, metered key)
              Stripe webhooks                         application backend
```

- **auth-service is the source of truth for entitlements** (`features` claim,
  `user_subscriptions`) and for the **catalogue** (which feature is metered,
  its unit, its price, its hard cap).
- **Stripe is the source of truth for money** for subscriptions: it aggregates
  the reported usage and issues the invoice at the end of the period.
- **The wallet stays separate**: it is not a Stripe subscription. Its top-ups
  remain a Stripe Checkout in `payment` mode.

## 3. Data model (frozen)

> This model is **frozen** here (D3). It is applied **incrementally**, each
> table/column landing in the same PR as the code that first uses it: until the
> first production deploy the consolidated `0000_initial_schema.sql` baseline is
> regenerated from `src/db/schema.ts` (AGENTS.md §8), so there is no delta
> migration to write. The "introduced in" column names the lot that first adds it.

| Object | Change | Introduced in |
| --- | --- | --- |
| `billing_customers` | **New table.** `owner_type` (`user`\|`org`), `owner_id` (polymorphic, no FK), `stripe_customer_id` (unique), unique `(owner_type, owner_id)`. Maps an owner to its lazily-created Stripe Customer. | Lot 0 ✅ |
| `subscription_plan_prices` | **Extended.** Add `billing_type` (`fixed`\|`metered`, default `fixed`), `feature_key` (nullable, metered only), `unit` (nullable, metered only), `usage_limit` (integer, nullable, metered only; `-1` = unlimited), `stripe_meter_id` (nullable, metered only). Unique `(plan_id, feature_key)` (NULLs distinct for fixed rows). A row is a **Stripe Price**; a metered row also owns a **Stripe Meter**. | Lot 2 |
| `user_subscriptions` | **Extended.** Add `stripe_subscription_id` (unique, nullable), `stripe_status` (nullable), `current_period_start`, `current_period_end` (nullable), `cancel_at_period_end` (bool, default false), `canceled_at` (nullable). `expires_at` stays the entitlement end (manual or Stripe period end). | Lot 1 ✅ |
| `applications` | **Extended.** Add `billing_mode` (`none`\|`external`\|`delegated`, default `none`): `external` = the app shows billing itself through the read APIs; `delegated` = the app uses the auth-service template pages. | Lot 6 |
| `billing_usage_events` | **New table.** Raw append-only metered reports: `application_id`, `user_id`, `feature_key`, `quantity` (numeric), `billing_period_start`, `idempotency_key`, `stripe_meter_event_identifier`, `created_at`. Unique `(application_id, idempotency_key)`. Idempotency + audit for the usage callback. | Lot 4 |
| `billing_usage_periods` | **New table.** Aggregate per period, authoritative for the **hard cap** and for display: `(user_id, application_id, feature_key, billing_period_start)` PK, `quantity` (numeric), `updated_at`. | Lot 4 |
| `stripe_invoices` | **New table.** Read cache filled by webhooks: `stripe_invoice_id` (unique), owner, `application_id` (nullable), `status`, `currency`, `amount_due`, `amount_paid`, `amount_remaining`, `period_start`, `period_end`, `hosted_invoice_url`, `invoice_pdf`, timestamps. Powers the profile page and the delegated invoice page without a Stripe round-trip. | Lot 5 |

**Plan `features` JSON.** With D3 frozen as "prices are the source of truth",
metered definitions move out of the plan `features` JSON into
`subscription_plan_prices`. The JSON keeps **only static feature flags**, so the
token `features` claim carries entitlements (booleans, quotas) and never a
mutable usage counter. A metered feature's cap and price are read from the
prices table, not the claim.

## 4. Decisions

| ID | Decision | Date |
| -- | -------- | ---- |
| D1 | Two billing mechanics are assumed and independent: the **wallet** (prepaid euro credit, multi-application token usage, metered by LiteLLM) and the **subscription** (per-product, paid via Stripe, usage billed at period end). They do not share a balance. | 2026-10-26 |
| D2 | The Stripe token is configured **env-only** (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`), like the social providers. No admin UI for the secret. | 2026-10-26 |
| D3 | The **prices table is the source of truth** for metered features (meter + price + cap). The plan `features` JSON keeps only static flags. Frozen model in §3, applied incrementally per lot. | 2026-10-26 |
| D4 | Stripe's own **Checkout** and **Billing Portal** pages handle payment and payment-method management. Auth-service templates are used **only** for exposure and tracking (subscribe summary, invoices, usage), never for entering card data. | 2026-10-26 |
| D5 | A metered feature's `usage_limit` is a **hard cap**: consumption beyond it is refused. `-1` means unlimited. `pricePerUnit` is charged at the end of the Stripe billing period (month N+1); units consumed up to the cap are the billable quantity. | 2026-10-26 |
| D6 | Billable usage is reported through the **existing `POST /api/consumption`** endpoint: the route detects that the `key` is a metered feature of the user's active plan for the calling application and routes it to metering instead of the free metric tables. A new endpoint is opened only if this proves too complex. | 2026-10-26 |
| D7 | Billing pages use **Eta, fail-closed** (D-D): a broken billing template returns a static 500, never the Vue SPA, because a missing payment page is worse than an explicit error. | 2026-10-26 |
| D8 | Billing owners are **user-only** for this programme (`billing_customers.owner_type` already accepts `org` for later). The gap is tracked by **D11**. | 2026-10-26 |
| D9 | Stripe objects are created/updated/deleted **only** through auth-service; the operator never opens the Stripe dashboard. Product/prices/meters are reconciled (create, update, archive) and subscriptions are driven by Checkout + webhooks. | 2026-10-26 |

## 7. Open questions

| ID | Question | Blocks |
| -- | -------- | ------ |
| D11 | **Org billing.** Wallets and billing customers already carry a polymorphic `owner_type` (`user`/`org`), but this programme is user-only (D8). Open: who tops up / pays for an organization, which owner a token with `org_id` charges, and how a plan attaches to an org membership. ## 8. Risks

- **auth-service on the payment critical path**: Stripe meters and subscriptions
  must tolerate retries; every mutation carries an idempotency key.
- **Two money models** (wallet EUR vs Stripe subscription): keep them visibly
  separate in the UI and in the ledger; never debit the wallet for a
  subscription or bill Stripe for wallet token usage.
- **Meter lag**: our `billing_usage_periods` aggregate is authoritative for the
  hard cap; Stripe's summaries are only for invoicing, so a cap decision never
  waits on a Stripe round-trip.
- **Delegated pages**: fail-closed, and never render card fields (Stripe
  handles payment, D4).
