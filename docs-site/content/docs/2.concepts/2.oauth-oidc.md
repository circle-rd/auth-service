---
title: OAuth 2.1 / OIDC endpoints
description: Authorization, token, userinfo, JWKS, and OIDC discovery endpoints provided by auth-service.
---

Auth Service exposes a standards-compliant OAuth 2.1 / OIDC authorization server powered by `@better-auth/oauth-provider`. The OAuth endpoints are served under the `/api/auth/` prefix; the two discovery documents are served at the **issuer root**.

## Discovery

### OIDC discovery document

```
GET /.well-known/openid-configuration
```

Returns the OIDC Provider Metadata document (OIDC Discovery 1.0). Clients and libraries should auto-configure themselves from this endpoint: it lists every endpoint below, the supported scopes and signing algorithms. It is **not** served under `/api/auth/`.

### Authorization server metadata (RFC 8414)

```
GET /.well-known/oauth-authorization-server
```

Equivalent OAuth 2.0 authorization server metadata document.

### JSON Web Key Set

```
GET /api/auth/jwks
```

The public key set used to verify JWT access tokens and ID tokens. Keys are Ed25519 (`kty: OKP`, `alg: EdDSA`): configure your JWT library for `EdDSA`, an RS256-only verifier rejects every token. Keys rotate monthly and the previous key stays published for a further month, so cache the set by `kid` and refetch when a `kid` is unknown.

## Core endpoints

### Authorization endpoint

```
GET/POST /api/auth/oauth2/authorize
```

Initiates the authorization code flow. Required parameters:

| Parameter | Description |
|---|---|
| `client_id` | Application slug |
| `response_type` | Must be `code` |
| `redirect_uri` | Must match one of the application's `redirectUris` |
| `scope` | Space-separated scope list |
| `code_challenge` | PKCE code challenge (required for public clients) |
| `code_challenge_method` | Must be `S256` |
| `resource` | RFC 8707 resource indicator — set to a configured audience URL to receive a JWT |

When `resource` is included and matches a registered protected resource (an application URL) the client is allowed to access (its own URL or an entry of its `allowedResources`), the issued access token is a signed JWT containing custom claims. Without `resource`, an opaque token is issued.

After authentication, BetterAuth redirects to `/login` (the login page) carrying the complete signed OAuth parameters in the query string.

### Token endpoint

```
POST /api/auth/oauth2/token
```

Exchanges an authorization code or refresh token for access/ID tokens.

**Authorization code grant:**

```http
POST /api/auth/oauth2/token
Content-Type: application/x-www-form-urlencoded
Authorization: Basic <base64(client_id:client_secret)>   # confidential clients

grant_type=authorization_code
&code=<authorization_code>
&redirect_uri=<redirect_uri>
&client_id=<slug>             # public clients (no Authorization header)
&code_verifier=<verifier>     # PKCE, required for public clients
```

Confidential clients authenticate with **HTTP Basic** (`client_secret_basic`); sending the secret in the body is refused. Add `resource=<audience_url>` to get a JWT when the authorization request carried several resources and you want one of them.

**Client credentials grant:**

```http
POST /api/auth/oauth2/token
Content-Type: application/x-www-form-urlencoded
Authorization: Basic <base64(client_id:client_secret)>

grant_type=client_credentials
&resource=<audience_url>
```

The default scope is `m2m`. Without `resource` the token is opaque.

### UserInfo endpoint

```
GET /api/auth/oauth2/userinfo
Authorization: Bearer <access_token>
```

Returns claims about the authenticated user. The response includes the scopes requested during authorization.

### Introspection and revocation

```
POST /api/auth/oauth2/introspect
POST /api/auth/oauth2/revoke
```

Both authenticate the client with `client_secret_basic`, `client_secret_post` or `private_key_jwt`, as advertised in the discovery document. Prefer local JWT verification against the JWKS for access tokens; introspect only opaque tokens or when you need an immediate revocation check.

### End-session endpoint (RP-initiated logout)

```
GET /api/auth/oauth2/end-session?id_token_hint=<id_token>&post_logout_redirect_uri=<url>
```

Ends the central SSO session, **for every application**: there is no per-application logout. `GET` and `POST` are accepted. The calling application must have `enableEndSession` turned on, and `post_logout_redirect_uri` must match one of its `postLogoutRedirectUris` exactly. Without a usable `id_token_hint`, the user is asked to confirm on an auth-service page. Applications that only want to sign their own user out should clear their local session and not call this endpoint.

## Supported scopes

| Scope | Claims added to token |
|---|---|
| `openid` | Required for OIDC. Adds `sub`. |
| `profile` | `name`, `company` |
| `email` | `email` |
| `offline_access` | Issues a refresh token |
| `roles` | `roles` — array of the user's role names in the application |
| `permissions` | `permissions` — array of permission strings |
| `features` | `features` — JSON object from the user's subscription plan; also `plan`, the plan's name |
| `wallet:self:read` | No extra claim; authorizes the signed-in user's wallet read API when `resource=<BETTER_AUTH_URL>` |
| `org` | `org_id` — the user's active organization ID |

## JWT token structure

When `resource` is included in the authorization request and matches a configured audience, the access token is a signed JWT:

```json
{
  "iss": "https://auth.example.com",
  "sub": "<user_id>",
  "aud": ["https://api.example.com", "https://auth.example.com/api/auth/oauth2/userinfo"],
  "azp": "my-app",
  "client_id": "my-app",
  "sid": "<session_id>",
  "jti": "<token_id>",
  "exp": 1234567890,
  "iat": 1234567890,
  "email": "user@example.com",
  "email_verified": true,
  "name": "Alice Smith",
  "roles": ["editor"],
  "permissions": ["documents", "documents.write"],
  "features": { "maxProjects": 50, "apiAccess": true },
  "plan": "pro",
  "scope": "openid profile email roles permissions features wallet:self:read org",
  "org_id": "org_01hwxyz..."
}
```

The header is `{"typ":"at+jwt","alg":"EdDSA","kid":"…"}` and the lifetime is one hour. `aud` is an array: the requested resource, plus the userinfo endpoint when the `openid` scope is present, so check that it **contains** your resource URL (JOSE libraries do this when you pass `audience`). `azp` is the `client_id` of the application that obtained the token. `plan` is the name of the user's active subscription plan for that application.

## Consent page

When `skipConsent` is `false` for an application, BetterAuth redirects to `/oauth2/consent` after authentication. The Vue admin SPA handles this route when the embedded frontend is present.

## Login pages

BetterAuth redirects to `/login` after calling the authorization endpoint. Auth Service serves either:

1. A custom HTML template from `TEMPLATES_DIR/<appSlug>/login.html`
2. A custom HTML template from `TEMPLATES_DIR/default/login.html`
3. The built-in template shipped with auth-service
4. The Vue SPA `index.html` (when no template matches)

The login page receives the full OAuth query string so the authorization flow can be resumed after authentication.
