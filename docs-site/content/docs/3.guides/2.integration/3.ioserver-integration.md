description: Protect an IOServer application with auth-service access tokens, and use the LiteLLM gateway and credit wallet from the backend.

[`ioserver-oidc`](https://docs.circle-cyber.com/ioserver-oidc/) is a set of
[IOServer](https://docs.circle-cyber.com/ioserver/) middlewares that verify
auth-service JWT access tokens on HTTP controllers and Socket.IO services. The
native auth-service format is the default; other OIDC/OAuth2 providers remain
supported through the generic provider. The backend only needs the public JWKS
endpoint: no client secret is shared between the two services.

::callout{icon="i-lucide-info"}
This page describes `ioserver-oidc` 0.3.0 (the version its API was checked
against). The package is maintained in its own repository; refer to its
documentation for later versions.
::

## Prerequisites

- A running auth-service instance with a public `BETTER_AUTH_URL`.
- An IOServer backend with `ioserver-oidc` installed (`ioserver` 2.2.1 or later,
  Node.js 22 or later).
- An application registered in auth-service, as described below.

## Application setup in auth-service

The middleware accepts a token only when all of these hold:

| Check | Value it expects |
|---|---|
| Signature | A key of `<AUTH_SERVICE_URL>/api/auth/jwks` and an asymmetric algorithm (`RS*`, `PS*` or `ES*`) |
| `iss` | `AUTH_SERVICE_URL` without a trailing slash (or `AUTH_SERVICE_ISSUER`) |
| `aud` | `AUTH_SERVICE_AUDIENCE`. When it is not set, `AUTH_SERVICE_APP_SLUG` is used for legacy deployments, which does not match the resource URL auth-service issues |
| `azp` | `AUTH_SERVICE_APP_SLUG`. The `client_id` claim is used when `azp` is absent. In resource-audience mode the claim must be present |
| Token kind | A user token. `client_credentials` tokens (`sub === azp`) are refused by default |

Two consequences for the registration:

1. `AUTH_SERVICE_APP_SLUG` must be the `client_id` of the application that
   **signs the users in**, because that is what auth-service puts in `azp`. The
   `roles`, `permissions` and `features` claims are also computed for that
   application.
2. `AUTH_SERVICE_AUDIENCE` must be the resource the token is issued for: the
   `url` of an application that the signing-in application is allowed to
   request. The authorization request must carry `resource=<that url>`; without
   it the access token is opaque and the middleware refuses it.

The simplest setup is one application. Create it in the admin interface
(**Applications → Create Application**), or with the admin API:

```sh
POST /api/admin/applications
Content-Type: application/json

{
  "name": "My App",
  "slug": "my-app",
  "url": "https://api.example.com",
  "isPublic": true,
  "redirectUris": ["https://app.example.com/callback"],
  "allowedScopes": ["openid", "profile", "email", "roles", "permissions", "features", "offline_access"]
}
```

Here `AUTH_SERVICE_APP_SLUG=my-app` and
`AUTH_SERVICE_AUDIENCE=https://api.example.com`. A public application
(`isPublic: true`) suits a browser frontend: it has no secret and uses PKCE,
which every application requires. It is also open to every account (see
[Integrating a third-party application](/docs/guides/integration/third-party-app#2-give-users-access-roles-and-plans));
use `isPublic: false` and grant users explicitly if only some accounts may sign
in. A confidential application returns its `clientSecret` once, at creation.

::callout{icon="i-lucide-info"}
The browser origin of the frontend must be allowed to call auth-service: the
origin of an application `url`, or an entry of `CORS_ORIGINS`. In the setup above
the frontend runs on `https://app.example.com`, which is not the application
`url`, so add it to `CORS_ORIGINS` — or give the frontend its own application
and let it request the API as a resource, as follows.
::

### Separate frontend and API applications

You can also register the API as an application of its own (`slug: my-api`,
`url: https://api.example.com`) and the frontend as another one
(`slug: my-frontend`, `url: https://app.example.com`) whose `allowedResources`
contains `https://api.example.com`. The API's `url` must be registered before it
can be listed. The frontend then requests `resource=https://api.example.com`, the
tokens carry `azp: my-frontend`, and the backend runs with
`AUTH_SERVICE_APP_SLUG=my-frontend` and
`AUTH_SERVICE_AUDIENCE=https://api.example.com`. The roles of `my-frontend` are
the ones in the tokens.

## Frontend — authorize and obtain tokens

Sign users in with any OIDC library, as described in
[Integrating a third-party application](/docs/guides/integration/third-party-app#3-sign-users-in).
The values specific to this setup:

| Parameter | Value |
|---|---|
| `client_id` | The slug of the signing-in application (`AUTH_SERVICE_APP_SLUG`) |
| `scope` | `openid profile email roles permissions features offline_access` (add `org` for `org_id`, `wallet:self:read` for the wallet). `offline_access` is required for the refresh token the audience-minting flow needs. |
| `resource` | The audience the backend expects (`AUTH_SERVICE_AUDIENCE`) |
| `code_challenge_method` | `S256`, with a `code_challenge`: PKCE is required |

Then send the access token to the backend:

```ts
const response = await fetch("https://api.example.com/documents", {
  headers: { Authorization: `Bearer ${accessToken}` },
});
```

## Backend — verify tokens

Configuration comes from environment variables, read once at startup by
`OidcConfigManager`:

| Variable | Required | Default | Description |
|---|---|---|---|
| `AUTH_SERVICE_URL` | Yes | — | Public base URL of auth-service (`BETTER_AUTH_URL`) |
| `AUTH_SERVICE_APP_SLUG` | Yes | — | `client_id` of the application that signs users in |
| `AUTH_SERVICE_AUDIENCE` | No | `AUTH_SERVICE_APP_SLUG` | Expected `aud`. Set it to the resource URL |
| `AUTH_SERVICE_JWKS_URI` | No | `<AUTH_SERVICE_URL>/api/auth/jwks` | Override the JWKS location |
| `AUTH_SERVICE_ISSUER` | No | `AUTH_SERVICE_URL` | Override the expected `iss` |
| `AUTH_SERVICE_GATEWAY_URL` | No | — | LiteLLM gateway URL, enables the gateway helper |
| `AUTH_SERVICE_ALLOW_MACHINE_TOKENS` | No | `false` | Accept `client_credentials` tokens on user routes |
| `AUTH_SERVICE_ADMIN_ROLES` | No | `admin` | Comma-separated roles for `OidcSocketAdminMiddleware` |

```sh
AUTH_SERVICE_URL=https://auth.example.com
AUTH_SERVICE_APP_SLUG=my-app
AUTH_SERVICE_AUDIENCE=https://api.example.com
AUTH_SERVICE_GATEWAY_URL=https://llm.example.com
```

```ts
import { IOServer } from "ioserver";
import { OidcConfigManager, OidcHttpMiddleware } from "ioserver-oidc";
import { DocumentsController } from "./DocumentsController.js";

const server = new IOServer({ /* your IOServer options */ });

// The manager name must be "oidcConfig": the middlewares look it up by that name.
server.addManager({ name: "oidcConfig", manager: OidcConfigManager });

server.addController({
  name: "documents",
  controller: DocumentsController,
  middlewares: [OidcHttpMiddleware],
  prefix: "/documents",
});

await server.start();
```

The middleware reads the `Authorization: Bearer` header and verifies the token
against the JWKS. The key set is fetched from
`<AUTH_SERVICE_URL>/api/auth/jwks` and cached in the process. It answers:

| Status | `code` | Meaning |
|---|---|---|
| `401` | `ERR_AUTH_TOKEN_REQUIRED` | No `Bearer` token |
| `401` | `ERR_AUTH_TOKEN_INVALID` | Bad signature, wrong `iss`, `aud` or `azp`, or expired |
| `403` | `ERR_MACHINE_TOKEN_FORBIDDEN` | `client_credentials` token on a user route |
| `403` | `ERR_ACCOUNT_DISABLED` | The local user record returned by your `users` manager is disabled |
| `500` | `ERR_USER_PROVISION_FAILED` | Your `users` manager threw |

If your application registers a manager named `users` with a
`findOrCreate(sub, { email, name })` method, the middleware calls it on each
request and uses the returned record's `id` and `role` as `request.userId` and
`request.userRole`. Without it, `request.userId` is the token's `sub`.

## Reading claims in a controller

After a successful check the middleware sets these properties on the Fastify
request:

| Property | Source |
|---|---|
| `sub` | `sub` claim |
| `userId` | `id` of your `users.findOrCreate` record, else `sub` |
| `userRole` | `role` of your `users.findOrCreate` record, else the first entry of `roles`, else `"user"` |
| `roles` | `roles` claim (an empty array without the `roles` scope) |
| `permissions` | `permissions` claim (an empty array without the `permissions` scope) |
| `features` | `features` claim (an empty object without the `features` scope or an active plan) |
| `plan` | `plan` claim, when present |
| `org_id` | `org_id` claim, only when present (needs the `org` scope) |
| `sid` | Provider session id, used by back-channel logout |
| `clientId` | `azp` / `client_id` |
| `scopes` | `scope` claim split on spaces |
| `auth` | The complete `OidcUserContext` |
| `authToken` | The raw bearer token; never log it |

```ts
import { BaseController } from "ioserver";
import type { FastifyReply, FastifyRequest } from "fastify";
import type { OidcUserContext } from "ioserver-oidc";

interface OidcRequest extends FastifyRequest {
  sub: string;
  roles: string[];
  permissions: string[];
  features: Record<string, unknown>;
  plan?: string;
  org_id?: string;
  auth: OidcUserContext;
  authToken: string;
}

export class DocumentsController extends BaseController {
  async list(request: FastifyRequest, reply: FastifyReply) {
    const { roles, features, org_id: orgId, plan } = request as OidcRequest;

    if (!roles.includes("editor")) {
      return reply.code(403).send({ statusCode: 403, error: "Forbidden", message: "Requires the editor role" });
    }

    // Gate on a feature flag from the user's subscription plan.
    if (features.apiAccess !== true) {
      return reply.code(403).send({ statusCode: 403, error: "Forbidden", message: "API access is not part of your plan" });
    }

    reply.send({ orgId, plan });
  }
}
```

The auth-ai entitlement helpers are re-exported by `ioserver-oidc`:
`hasRole`, `hasPermission` (write implies read), `hasFeature` and `getFeature`.
Use them instead of re-implementing the permission format.

How controller methods are mapped to routes is described in the
[IOServer documentation](https://docs.circle-cyber.com/ioserver/).

## Socket.IO services

`OidcSocketMiddleware` applies the same checks to a Socket.IO connection. It
reads the token from `socket.handshake.auth.token`, or else from the
`Authorization: Bearer` handshake header, and sets the same properties on the
`socket`. A failed check rejects the connection with the error message
`ERR_AUTH_TOKEN_REQUIRED`, `ERR_AUTH_TOKEN_INVALID`,
`ERR_MACHINE_TOKEN_FORBIDDEN` or `ERR_ACCOUNT_DISABLED`.
`OidcSocketAdminMiddleware`, placed after it, rejects with `ERR_FORBIDDEN`
unless `roles` contains one of the configured admin roles (default `admin`).

```ts
import { OidcSocketAdminMiddleware, OidcSocketMiddleware } from "ioserver-oidc";

server.addService({
  name: "users",
  service: UserService,
  middlewares: [OidcSocketMiddleware, OidcSocketAdminMiddleware],
});
```

## LiteLLM gateway and credit wallet

When the application's **LiteLLM support** is enabled, auth-service adds the
gateway URL and the auth-service URL to `allowedResources` and the
`wallet:self:read` scope. The frontend requests all three audiences at sign-in
(`resource` repeated). The backend stores the refresh token and mints one
short-lived token per audience.

`ioserver-oidc` wraps the auth-ai SDK for the two backend operations:

```ts
import { createRequestGatewayClient, createWalletClient } from "ioserver-oidc";

// 1. The token minted for the auth-service audience can read the wallet.
const wallet = createWalletClient({
  authServiceUrl: config.authServiceUrl,
  token: walletToken,
});
const account = await wallet.getAccount();
if (!account.canSpend) {
  return reply.code(402).send({ topupUrl: wallet.topupUrl() });
}

// 2. The token minted for the gateway audience calls LiteLLM.
const gateway = createRequestGatewayClient(
  { authToken: gatewayToken },
  config,
);
const models = await gateway.listModels();
```

- `canSpend` is authoritative: it is true for an unlimited account or a strictly
  positive balance.
- Gateway `402` becomes `GW_001` (`isInsufficientCredit` is re-exported).
- `429` becomes `GW_002`, `401`/`403` become `GW_003`, `503` becomes `GW_004`.
- The application never debits the wallet: the gateway bills after each call.
- Amounts are `bigint` micro-euros (`MICRO_PER_EUR = 1_000_000n`).

The full application-side walkthrough is in
[LiteLLM gateway and credit wallet in an application](/docs/guides/integration/litellm-app).

## Back-channel logout

An application that registers a `backchannelLogoutUri` receives a signed logout
token whenever the central session ends. Store the `sid` from the verified token
at sign-in, then mount the endpoint on the IOServer Fastify instance:

```ts
import { registerBackchannelLogout } from "ioserver-oidc";

registerBackchannelLogout(server.getApp(), {
  config: server.getManager("oidcConfig").getConfig(),
  onLogout: async ({ sid, sub }) => {
    await sessions.endBySid(sid, sub);
  },
});
```

Call `registerBackchannelLogout()` before `server.start()`. The handler validates
the logout token signature, `typ`, audience, event, lifetime and replay, then
calls `onLogout`. It answers `204` and never carries
error detail. With several replicas, provide a shared replay store; the default
is per-process.

## Other OIDC providers

To keep using another issuer, set the generic provider instead of the native
one:

```sh
OIDC_PROVIDER=oidc
OIDC_ISSUER=https://issuer.example.com
OIDC_JWKS_URI=https://issuer.example.com/.well-known/jwks.json
OIDC_AUDIENCE=api://my-api
OIDC_CLIENT_ID=my-client
```

Claim names are configurable (`OIDC_ROLES_CLAIM`, `OIDC_PERMISSIONS_CLAIM`,
`OIDC_AUTHORIZED_PARTY_CLAIMS`, …). See the
[ioserver-oidc providers documentation](https://docs.circle-cyber.com/ioserver-oidc/docs/getting-started/providers).

## OIDC discovery

Auth-service publishes its configuration at the issuer root:

```
GET https://auth.example.com/.well-known/openid-configuration
```

`ioserver-oidc` does not use discovery in native mode: it derives the JWKS
location and the issuer from `AUTH_SERVICE_URL`. Other OIDC clients, such as the
frontend library, can configure themselves from that document. For a
framework-agnostic walkthrough, see
[Integrating a third-party application](/docs/guides/integration/third-party-app).
