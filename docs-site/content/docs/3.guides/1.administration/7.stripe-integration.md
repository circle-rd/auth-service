Auth Service uses the Stripe API version **`2026-05-27.dahlia`** (`src/services/stripe.ts`). Two billing mechanics coexist and are deliberately independent:

- **Prepaid credit wallet** — a euro balance the user tops up and spends through the LiteLLM gateway. Top-ups are one-off Stripe Checkout sessions in `payment` mode.
- **Paid subscription plans** — per-product plans; a metered feature's usage is billed by Stripe at the end of the billing period.

Auth-service owns the Stripe catalogue: Products, Prices and Meters are created, updated and archived from the admin API (decision D9), never by hand in the Dashboard. An explicit `stripeProductId` may still be supplied when creating a plan (advanced/legacy override); a plan created without one gets its Product provisioned automatically. The sections below state what is wired **today** and what is still planned.

## Configuration

```sh
STRIPE_SECRET_KEY=sk_live_...        # Secret API key (sk_test_… in test mode)
STRIPE_WEBHOOK_SECRET=whsec_...      # Signing secret of THIS webhook endpoint
```

- Only these two values are needed. The **publishable key** (`pk_…`) is not used: payments happen on Stripe's own Checkout page, there is no Stripe.js in the frontend.
- Both are **environment-only** (decision D2); there is no admin UI for them.
- Without `STRIPE_SECRET_KEY`, Stripe is silently disabled: the catalogue calls become no-ops (the plan rows still exist, without Stripe ids) and the wallet falls back to manual top-ups.
- The signing secret is **per endpoint and per mode** (test/live). A `whsec_…` from a test endpoint does not validate live events.

## What is synced today

| Stripe object | Trigger in auth-service | Behaviour | Status |
|---|---|---|---|
| **Product** (one per plan) | Plan created through `POST /api/admin/applications/:appId/plans` | Created, named `<AppName> — <PlanName>`, `metadata.applicationId` | ✅ |
| | Plan updated (name/description) | Renamed / re-described | ✅ |
| | Plan deleted | **Archived** (`active: false`), never deleted | ✅ |
| | Application created | Its default `free` plan gets its Product too (best-effort) | ✅ |
| | Application renamed | Its plans' Products are renamed | ✅ |
| | Application deleted | Its plans' Products/Prices are archived and its Meters deactivated | ✅ |
| **Price** (one per price tier) | Price created (`POST …/plans/:planId/prices`) | Created on the plan's Product; a `metered` price also gets a Meter | ✅ |
| | Price renamed | Stripe `nickname` updated (amount/currency/interval/feature are immutable: a change archives and creates a new row) | ✅ |
| | Price deleted | **Archived** (`active: false`) | ✅ |
| **Meter** (one per application + feature) | First `metered` price of a feature | Created (`event_name` = `app_<slug>__<featureKey>`, aggregation `sum`, mapped by `stripe_customer_id`) | ✅ |
| | Last price of that feature removed | **Deactivated** | ✅ |
| | Metered usage reported by an application | Recorded idempotently, aggregated per UTC month and **capped** (`403 BIL_003` past the limit), then pushed as a Stripe meter event; a failed push stays pending and is retried | ✅ |
| **Customer** | User registers, or first paid flow | Created **eagerly, best-effort, idempotent** (a Stripe incident never blocks sign-up); `pnpm billing:reconcile` creates the missing ones | ✅ |
| **Subscription** | Plan assigned (admin grant, default plan, self-service) | Created or updated for **every** plan, the free one included: a plan with no price gets a 0 EUR monthly Price, and a plan change swaps the subscription item. Stripe Checkout in `subscription` mode and the Billing Portal are opened from the profile | ✅ |
| **Invoice** | Invoice events | Entitlement is updated, but invoices are **not cached** for display | ❌ gap (Lot 5) |
| **Wallet top-up** | `POST /api/user/wallet/checkout` | One-off Checkout **payment**; the webhook credits the wallet. No Stripe-issued invoice | ✅ |

## Stripe webhook endpoint

```
POST /api/webhooks/stripe
```

The route receives the raw body and verifies the `Stripe-Signature` header before processing. Do not put authentication middleware in front of it: Stripe sends no session cookie.

## Required endpoint settings

| Setting | Value | Why |
|---|---|---|
| **Payload format** | **Snapshot** | The handlers read fields of `event.data.object` (subscription status/items, invoice parent/lines/periods, checkout/charge amounts) and never call `stripe.*.retrieve`. A **thin** payload would carry only ids and the handlers would silently ignore the event. |
| **API version** | **`2026-05-27.dahlia`** | The webhook payload is shaped by the **endpoint's** version, not by the SDK's `apiVersion`. The handlers rely on dahlia shapes (e.g. current-period bounds on the subscription item, `invoice.parent.subscription_details`). Picking a newer version without aligning the code can move or rename fields. |
| **Signing secret** | `whsec_…` → `STRIPE_WEBHOOK_SECRET` | Verified on every delivery. |

## Events to subscribe

**Required today** (the wallet and the subscription entitlement):

| Event | Effect |
|---|---|
| `customer.subscription.created` | Sets `isActive = true` for the matching user subscription |
| `customer.subscription.updated` | Re-derives `isActive` from the Stripe status (`active`/`trialing` → true, every other status → false) |
| `customer.subscription.deleted` | Sets `isActive = false` |
| `invoice.paid` | Reactivates the subscription and stores the period bounds |
| `invoice.payment_succeeded` | Same as `invoice.paid` (legacy alias; subscribing to one of the two is enough) |
| `invoice.payment_failed` | Dunning failure (`subscription_create`/`subscription_cycle` only) → `isActive = false` |
| `checkout.session.completed` | Credits a paid wallet top-up |
| `checkout.session.async_payment_succeeded` | Same, for delayed payment methods |
| `charge.refunded` | Takes back the refunded share of a wallet top-up |
| `charge.dispute.created` | Takes back the remaining credit of a disputed top-up |

**Planned** (add them when the corresponding lot ships; harmless to select now since unhandled types are acknowledged `200`):

| Event | Needed for |
|---|---|
| `invoice.finalized` | Invoice cache shown in the profile / delegated invoice page (Lot 5) |
| `customer.updated` | Keeping the cached customer in sync, once customers are wired |

Selecting **all events** also works (unhandled types are acknowledged with `200`), at the cost of noise.

## Stripe Dashboard setup

1. **Developers → API keys** → copy the **secret key** into `STRIPE_SECRET_KEY` (`sk_test_…` in test mode, `sk_live_…` in live mode).
2. **Developers → Webhooks → Add endpoint**.
3. Endpoint URL: `https://auth.example.com/api/webhooks/stripe`.
4. **Payload format: Snapshot**; **API version: `2026-05-27.dahlia`** (if the dropdown only offers a newer one, align `src/services/stripe.ts` and this page first).
5. Select the events from the table above (or "all events").
6. Open the endpoint → **Signing secret** → `whsec_…` → set `STRIPE_WEBHOOK_SECRET`, then restart auth-service.
7. Send a test event from the endpoint page and check the `stripe-webhook: received event` log line.

In local development, `stripe listen --forward-to localhost:<port>/api/webhooks/stripe` prints a CLI-specific `whsec_…`: use that one locally, not the Dashboard endpoint secret.

### Metered billing

An application reports usage with `POST /api/consumption` (`{ applicationId, userId, key, value, idempotencyKey? }`). When `key` prices a **metered** feature of the user's active plan (a `metered` price on that plan), auth-service:

1. enforces the **hard cap** (`usage_limit`, `-1` = unlimited) on the per-UTC-month aggregate — over it the call is refused with `403 BIL_003` and nothing is recorded;
2. records the report **idempotently** (`(applicationId, idempotencyKey)`) and increments the period aggregate;
3. pushes a Stripe **meter event** (`billing.meterEvents.create`) so Stripe bills the quantity on the next invoice. A push that fails (Stripe down, subscription not ready) leaves the event pending; `pnpm billing:reconcile` and the background retry push it later, and the event id makes the push idempotent.

Keys that are not metered fall through to the free consumption counters, unchanged.

`pnpm billing:reconcile` creates the missing Customers, Products, Prices and **Stripe subscriptions**, and pushes pending meter events (after an outage, a restore or an upgrade); it only creates, never archives.

## Credit top-ups

The same Stripe account can sell prepaid credit for the [wallet](/docs/reference/api-reference). Two modes:

**Online (Stripe configured).** `POST /api/user/wallet/checkout` with `{ "amountCents": 1000 }` returns a Stripe Checkout URL. The amount must be within `WALLET_TOPUP_MIN_EUR` / `WALLET_TOPUP_MAX_EUR`. The checkout is created in euros with Stripe **Adaptive Pricing** enabled: the customer sees and pays in their local currency, Stripe converts, and the credit granted is always the euro amount. The webhook then credits the wallet, and a refund or a dispute takes the credit back (a reversal may leave the wallet in debt; a dispute later won is not restored automatically — give the credit back with an administrator grant).

**Manual (no `STRIPE_SECRET_KEY`).** `GET /api/user/wallet/topup-options` reports `enabled: false` and `POST …/checkout` answers `503 WAL_006`. The administrator issues an invoice outside Stripe, then records the credit with `POST /api/admin/wallets/users/:userId/topups` (superadmin), giving the invoice number as `reference`.

Not handled: tax collection, Stripe-issued invoices (Stripe Tax, `invoice_creation`) and automatic re-charging.
