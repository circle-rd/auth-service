---
title: reverse-agent device enrolment
description: Enrol a reverse-agent through the OAuth device flow and accept its relay token in LiteLLM.
---

`reverse-agent` opens an outbound tunnel to `reverse-relay` and needs no
inbound port. It enrols a human account once through the OAuth 2.0 device
authorization grant (RFC 8628), then keeps a rotating refresh token on disk.

## Configure the provider

Enable the OAuth device grant and name the relay's public origin:

```dotenv
OAUTH_DEVICE_GRANT_ENABLED=true
REVERSE_AGENT_CLIENT_ID=reverse-agent
REVERSE_AGENT_RESOURCE=https://relay.example.com
# Optional; defaults to reverse-relay and 900 seconds.
REVERSE_AGENT_RESOURCE_NAME=reverse-relay
REVERSE_AGENT_ACCESS_TOKEN_TTL_SECONDS=900
```

`REVERSE_AGENT_RESOURCE` must be an origin, not a path. At startup auth-service
provisions:

- the public OAuth client `reverse-agent` (no secret, device + refresh grants);
- the protected resource `reverse-relay` whose identifier is that origin;
- the client-to-resource link used by RFC 8707 validation.

`DEVICE_AUTHORIZATION_ENABLED` and `OAUTH_DEVICE_GRANT_ENABLED` are mutually
exclusive: both install the same device-authorization plugin. The first
variant issues a session, the second issues OAuth tokens.

## Contract seen by the agent

Discovery at `{BETTER_AUTH_URL}/.well-known/openid-configuration` advertises
`issuer`, `jwks_uri`, `token_endpoint` and `device_authorization_endpoint`.

1. `POST /api/auth/device/code` with `client_id`, `scope` and `resource`
   returns `device_code`, `user_code`, `verification_uri`,
   `verification_uri_complete`, `interval` and `expires_in`.
2. The operator opens `verification_uri`, signs in and approves the code; the
   approving account supplies `preferred_username`.
3. `POST /api/auth/oauth2/token` with
   `grant_type=urn:ietf:params:oauth:grant-type:device_code` returns
   `access_token`, `refresh_token`, `expires_in` and `scope`.
4. `grant_type=refresh_token` rotates the refresh token. Reusing the previous
   token, or any revoked token, answers `invalid_grant`; the agent then deletes
   its local credential and starts a new enrolment.

The access token is a JWT signed with `JWT_PRIMARY_ALG` (`EdDSA` is supported;
`ES256` remains the default). Its audience is the relay origin, its scope is
`tunnel:serve` and `preferred_username` is present when `profile` was granted.
Usernames are globally unique, so two accounts can never map to the same agent
namespace.

## Accept the token in LiteLLM

Point the existing custom-auth hook at the same issuer and keep the relay token
audience available:

```dotenv
JWT_PUBLIC_KEY_URL=https://auth.example.com/api/auth/jwks
JWT_ISSUER=https://auth.example.com
JWT_AUDIENCE=https://llm.example.com,https://relay.example.com
```

`JWT_AUDIENCE` is comma-separated so the gateway keeps accepting its own
application tokens while also accepting relay-bound tokens. A token is accepted
when one of its audiences matches. `litellm/custom_auth.py` accepts `EdDSA`,
`ES256` and `RS256` and exposes the
claim `preferred_username` as `preferredUsername` in the request metadata,
alongside `sub` and `azp`. Existing application tokens are unchanged.
