> Living document, not committed yet. The SSH gateway is delivered by a
> separate repository and is **not** implemented in auth-service. This document
> is the contract both sides must honour. The auth-service side is implemented
> in Lot 4; the gateway side is handed to its own repository with the prompt at
> the end of this page.

## 1. Purpose

The gateway lets a member of a resource application open an SSH session to a
host that another member shared with them. It is a system component:

- auth-service decides who may use which resource;
- the gateway authenticates the human, enforces the decision, relays the
  session and reports accounting;
- the target host only sees the gateway identity key.

The gateway is a **separate Docker deployable**. Its image is published from
its own repository and consumed by auth-service through the `ssh` Compose
profile and the `SSH_GATEWAY_IMAGE` variable.

## 2. Scope

In scope:

- SSH listener with public-key client authentication;
- auth-service device approval before any session;
- meta-user target resolution and per-connection authorization;
- resource ownership validation by logging in with the resource identity key;
- host key pinning and invalidation on change;
- PTY session relay to the target;
- session accounting and audit events;
- minimal, hardened container image.

Out of scope:

- user interface, admin UI, database, web API;
- password authentication, SFTP, SCP, port forwarding, agent forwarding, X11,
  reverse tunnels, dynamic forwarding;
- resource creation, grants, invitations, catalogue, membership (auth-service);
- LiteLLM, HTTP or file resources;
- an OpenSSH server on the gateway container.

## 3. Architecture

```
SSH client ──key──> gateway ──device approval──> auth-service
                       │
                       ├── authorize(resourceUri, subject)
                       ├── target detail + identity key
                       ├── host key pinning
                       └── SSH session ──identity key──> target host
```

The gateway is stateless. All state lives in auth-service:

- `resources` and `resource_grants`;
- `ssh_resource_details` (host, port, account, host key fingerprint);
- `ssh_resource_identities` (public key, encrypted private key, key version);
- `ssh_share_details` (meta-user per grant);
- `ssh_recipient_keys` (recipient public key → user);
- `ssh_sessions` (session accounting).

The gateway may cache target detail for at most 30 seconds. It must never write
its own authorization state.

## 4. Auth-service contract

All machine calls use OAuth 2.0 `client_credentials` tokens issued by
auth-service. The gateway client id is `ssh-gateway`; its scopes are:

- `resources:authorize`
- `resources:usage:write`
- `resources:validate`
- `ssh:target:read`
- `ssh:resource:read`
- `device:session:validate`

The gateway must treat every non-2xx response as a deny and fail closed. It must
never retry a deny with a different identity.

### 4.1 Device approval

1. The gateway starts a BetterAuth device authorization with the public client
   id from `SSH_GATEWAY_DEVICE_CLIENT_ID`:
   `POST /api/auth/device-authorization`.
2. It displays `verification_uri` and `user_code` to the SSH client and polls
   the BetterAuth device token endpoint at the advertised interval.
3. The browser approval page requires an authenticated auth-service session and
   the `Origin` header; the gateway never approves on behalf of the user.
4. Once the token is issued, the gateway validates it once:
   `POST /api/internal/gateway/device/session`
   body `{ "sessionToken": "<better-auth-session-token>" }`
   response `{ "userId": "...", "email": "...", "expiresAt": "..." }`.
   The endpoint is implemented by auth-service in Lot 4. The gateway must not
   keep the session token after this call.
5. A public key alone never authenticates. A valid device approval without a
   registered recipient key is also rejected.

### 4.2 Recipient key

The gateway accepts a client public key only if it matches
`ssh_recipient_keys.public_key` for an active key. Unknown, revoked or
non-matching keys are rejected uniformly after device approval. The gateway
must not reveal whether the key or the user exists.

### 4.3 Meta-user lookup

The SSH username is the **meta-user** of a share. Before authorization:

`GET /api/internal/gateway/ssh/targets?metaUser=<metaUser>`

Response:

```json
{
  "grantId": "uuid",
  "resourceId": "uuid",
  "resourceUri": "ssh://<resourceId>",
  "applicationId": "uuid"
}
```

`404` for unknown, revoked, expired or disabled shares. The response never
contains the host, account or identity key. Implemented in Lot 4.

### 4.4 Authorization

`POST /api/internal/gateway/authorize`

```json
{
  "subjectId": "<device-approved user id>",
  "clientId": "ssh-gateway",
  "resourceUri": "ssh://<resourceId>",
  "audience": "ssh-gateway",
  "requestId": "<ssh connection id>",
  "source": "ssh"
}
```

Response on allow is the generic decision:

```json
{
  "decision": "allow",
  "resourceId": "uuid",
  "resourceUri": "ssh://...",
  "applicationSlug": "share-app",
  "ownerType": "user",
  "ownerId": "...",
  "accessKind": "grant"
}
```

Any deny is `{ "decision": "deny" }`. The gateway closes the connection with a
generic failure. `source` is added to the authorize schema in Lot 4.

### 4.5 Target detail

`GET /api/internal/gateway/ssh/resources/:resourceId`

Only after an allow decision, or for the validation flow:

```json
{
  "resourceId": "uuid",
  "uri": "ssh://...",
  "status": "validated",
  "applicationId": "uuid",
  "ownerType": "user",
  "ownerId": "...",
  "target": { "host": "nuk.local", "port": 22, "account": "test" },
  "hostKeyFingerprint": "SHA256:...",
  "identity": {
    "publicKey": "ssh-ed25519 AAAA...",
    "privateKeyCiphertext": "v1:base64...",
    "keyVersion": 1
  }
}
```

- `privateKeyCiphertext` is AES-256-GCM encrypted by auth-service with the
  envelope key. Format: `v1:<base64(nonce || ciphertext || tag)>`.
- The gateway decrypts only in memory and zeroizes the buffer after use.
- `hostKeyFingerprint` may be `null` before the first validation (TOFU).
- `404` for unknown, foreign or disabled resources.
- Implemented in Lot 4.

### 4.6 Resource validation

The user clicks **Validate** in the catalogue. auth-service returns the scheme's
`validatorUrl`; the catalogue opens:

```
<SSH_GATEWAY_VALIDATION_URL>?resourceId=<resourceId>
```

The gateway:

1. authenticates the user with device approval (or an existing browser session
   on its validation page);
2. fetches the target detail;
3. connects with the identity key and a strict host key check;
4. records the observed host key fingerprint;
5. calls back:

`POST /api/internal/gateway/resources/:resourceId/validate`

```json
{
  "result": "validated",
  "reason": null,
  "evidence": {
    "hostKeyFingerprint": "SHA256:..."
  }
}
```

or `{ "result": "validation_failed", "reason": "<generic reason>" }`.

The gateway must be the validator client bound to the `ssh` scheme. A callback
from another client is rejected by auth-service.

### 4.7 Invalidation

On every later connection, the gateway compares the target host key with the
pinned fingerprint. On mismatch, or when the target rejects the identity key:

`POST /api/internal/gateway/resources/:resourceId/invalidate`

```json
{ "reason": "host-key-changed" }
```

Auth-service disables the resource, keeps the audit trail and stops new
sessions. The gateway must also close live sessions of that resource.

### 4.8 Session accounting

`POST /api/internal/gateway/ssh/sessions`

```json
{
  "resourceId": "uuid",
  "resourceUri": "ssh://...",
  "subjectId": "uuid",
  "clientId": "ssh-gateway",
  "sessionId": "uuid",
  "startedAt": "2026-11-15T12:00:00.000Z",
  "endedAt": "2026-11-15T12:34:56.000Z",
  "bytesIn": 12345,
  "bytesOut": 67890,
  "endReason": "client"
}
```

`endReason` is one of `client`, `idle`, `error`, `revoked`, `target`.
Auth-service stores the session row and one idempotent usage record with
`usageSource = "provider"`, `costUsd = "0"` and `requestId = sessionId`.
Implemented in Lot 4.

## 5. SSH resource lifecycle

1. A member of `share-app` creates an SSH resource in auth-service. Auth-service
   generates an identity key pair, stores the private key encrypted and returns
   the `authorized_keys` line.
2. The owner installs the public key line on the target, for example:
   `restrict,pty,from=<gateway egress IP> ssh-ed25519 AAAA... auth-service:<resourceId>`
3. The owner clicks Validate. The gateway logs in with the identity key, pins
   the host key and calls back.
4. The owner creates grants (`user`, `organization`, `plan`, `everyone`) and
   optional meta-users. Only an application admin can invite non-members.
5. A recipient registers their SSH public key in auth-service.
6. The recipient connects: `ssh -p 2222 <meta-user>@<gateway-host>`.
7. The gateway runs device approval, resolves the meta-user, authorizes, fetches
   the target detail and relays the session.
8. On revocation, disabled resource, host key change or expiry, the gateway
   denies new sessions and closes live ones.

The target line should use `restrict,pty` and `from=`. The gateway must not
require or accept password authentication, and must not modify the target's
`/etc/ssh`.

## 6. Deployment contract

### Image

- Repository: separate Git repository, Rust `russh` baseline.
- Registry: `ghcr.io/<org>/ssh-gateway`.
- Tags: `nightly` and `latest` (plus semver tags on `v*`).
- auth-service consumes it through `SSH_GATEWAY_IMAGE`; it never builds the
  gateway source.
- Multi-stage build; non-root user; read-only root filesystem; no shell in the
  runtime image; `cap_drop: ALL`; `security_opt: no-new-privileges:true`.
- Healthcheck: TCP connect to the SSH port; no HTTP server.

### Workflows

The external repository must copy the auth-service image workflow patterns:

- `nightly.yml`: manual `workflow_dispatch` with a branch input, Buildx, GHCR
  login with `GITHUB_TOKEN`, `nightly` tag, provenance disabled, GHA cache,
  deletion of the superseded nightly version.
- `release.yml`: trigger on `v*` tags, semver tags and `latest`, GHCR login,
  Buildx, GHA cache.
- `ci.yml`: format, lint, unit tests, dependency audit (`cargo audit` or
  `cargo deny`), Docker build.
- SBOM and image signing are recommended, not required for the first release.

### Configuration

| Variable | Required | Description |
|---|---|---|
| `AUTH_SERVICE_URL` | yes | Internal auth-service base URL. |
| `SSH_GATEWAY_MACHINE_CLIENT_ID` | yes | `client_credentials` client id (`ssh-gateway`). |
| `SSH_GATEWAY_MACHINE_CLIENT_SECRET` | yes | Machine client secret, from a secret store. |
| `SSH_GATEWAY_DEVICE_CLIENT_ID` | yes | Public client id used for the device flow. |
| `SSH_GATEWAY_ENVELOPE_KEY` | yes | Base64 32-byte AES-256-GCM key. |
| `SSH_LISTEN_ADDRESS` | no | Default `0.0.0.0`. |
| `SSH_LISTEN_PORT` | no | Default `2222`. |
| `SSH_HOST_KEY_PATH` | yes | Ed25519 host key file mounted read-only. |
| `SSH_GATEWAY_VALIDATION_URL` | no | Public validation page URL shown to users. |
| `SSH_TARGET_CONNECT_TIMEOUT_MS` | no | Default 10000. |
| `SSH_IDLE_TIMEOUT_MS` | no | Default 900000. |
| `SSH_MAX_SESSIONS` | no | Global and per-user cap. |
| `LOG_LEVEL` | no | `info` by default. |

Secrets must never be baked into the image, logged, or returned in errors.

### Network

- Ingress: SSH port only.
- Egress: auth-service and the declared target hosts.
- No Internet access beyond these.
- No admin port, metrics port or debug port exposed.

## 7. Security requirements

- Public-key authentication only; no passwords, no keyboard-interactive on the
  gateway side.
- Device approval is mandatory for every new session; a key alone is not enough.
- Recipient key must be registered and active.
- Uniform failure after device approval: do not disclose whether the key, user,
  meta-user, resource or grant exists.
- Host key pinning is strict. First validation is TOFU; later changes invalidate
  the resource and close sessions.
- Private keys are decrypted in memory, never written to disk, never logged,
  zeroized after use. Disable core dumps.
- No shell, no SFTP, no SCP, no forwarding, no agent forwarding, no X11, no
  reverse tunnels, no dynamic forwarding.
- Enforce idle timeout, maximum session duration, concurrent session limits and
  per-IP/per-user rate limits.
- Bind the host key and envelope key from Docker secrets or read-only mounts.
- Rate-limit device authorization and failed attempts.
- Audit events: connection accepted/rejected, device approval result, key
  result, target resolution, authorization decision, target connect, session
  start/end, invalidation. Never log tokens, OTPs, passwords or private keys.
- Dependency pinning, CVE scanning and reproducible builds.

## 8. Acceptance tests

The external repository must cover at least:

| ID | Test |
|---|---|
| V-1 | Registered key + device approval + valid grant opens a PTY session. |
| V-2 | Registered key without device approval is rejected. |
| V-3 | Device approval without a registered key is rejected. |
| V-4 | Unknown, revoked or expired meta-user is denied uniformly. |
| V-5 | Revoked grant denies new sessions and closes live sessions. |
| V-6 | Disabled resource or disabled scheme denies access. |
| V-7 | Host key change invalidates the resource and denies the session. |
| V-8 | Target `restrict,pty,from=` line is verified on `test@nuk.local`. |
| V-9 | SFTP, SCP, port forwarding, agent forwarding and X11 are refused. |
| V-10 | Idle timeout and maximum session duration close the session. |
| V-11 | Concurrent session limit is enforced. |
| V-12 | Session accounting is idempotent by `sessionId`. |
| V-13 | No secret appears in logs or error responses. |
| V-14 | Device approval requires an authenticated session and `Origin`. |
| V-15 | Device authorization and failed attempts are rate-limited. |
| S-3 | `restrict,pty,from=` is accepted on the target. |
| S-4 | The device code is requested before keyboard-interactive; a key alone fails. |

## 9. auth-service work required in Lot 4

The gateway cannot ship before auth-service provides:

- `src/db/ssh-schema.ts` with `ssh_resource_details`,
  `ssh_resource_identities`, `ssh_share_details`, `ssh_recipient_keys`,
  `ssh_sessions`;
- `POST /api/internal/gateway/device/session` (`device:session:validate`);
- `GET /api/internal/gateway/ssh/targets` (`ssh:target:read`);
- `GET /api/internal/gateway/ssh/resources/:id` (`ssh:resource:read`);
- `evidence` support on `POST /api/internal/gateway/resources/:id/validate`;
- `POST /api/internal/gateway/ssh/sessions` (`resources:usage:write`);
- `source` support on the generic authorize body;
- SSH scheme enabled through `RESOURCE_SCHEMES_ENABLED=ssh` and
  `application_schemes`;
- `ssh` Compose profile using `SSH_GATEWAY_IMAGE`, with no build context;
- contract tests that run against a fake gateway client.

## 10. Implementation prompt for the external repository

Copy this prompt into the new repository's initial session:

> Build a minimal, production-grade SSH gateway as a standalone service in a new
> repository. Use Rust with `russh`/`russh-keys` (Warpgate is a reference, not a
> dependency). The service is a system component of the CIRCLE auth-service
> resource-sharing platform and must implement the contract in
> `9.ssh-gateway-external-spec.md` from the auth-service repository.
>
> Non-negotiable constraints:
> - public-key client authentication only, plus mandatory auth-service device
>   approval; a key alone must never authenticate;
> - no password auth, no SFTP, SCP, forwarding, agent forwarding, X11, reverse
>   or dynamic tunnels;
> - no admin UI, no database, no HTTP server; SSH listener plus a TCP
>   healthcheck only;
> - strict host key pinning, invalidation on change, in-memory key decryption
>   with zeroization, no secret logging;
> - uniform failure messages and rate limits;
> - non-root, read-only root filesystem, `cap_drop: ALL`,
>   `no-new-privileges`, multi-stage build, SBOM and dependency audit in CI.
>
> Deliverables:
> - Rust workspace with unit/integration tests and a fake auth-service for
>   contract tests;
> - Dockerfile and Compose example;
> - `nightly.yml` and `release.yml` mirroring the auth-service image workflows
>   (GHCR, Buildx, `nightly`, `latest`, semver tags, GHA cache);
> - README with configuration, threat model, runbook and the V-1..V-15 matrix;
> - no changes to the auth-service repository.
>
> Acceptance: the V-1..V-15 matrix in the contract, plus S-3 and S-4, must pass.
> The image must be consumable by auth-service as
> `ghcr.io/<org>/ssh-gateway:nightly` and `:latest`.
