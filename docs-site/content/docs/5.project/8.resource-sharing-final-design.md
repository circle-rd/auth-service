## 1. Three layers

The model keeps three separate concepts. Mixing them is what made the previous
implementation hard to extend.

| Layer | Purpose | Examples |
|---|---|---|
| Resource application | Tenant, membership, grants, plans, catalogue | `share-app`, `re-gine`, `acme` |
| Owner | Who may declare and share the resource | a user or the resource application |
| Adapter service | Validation and enforcement | LiteLLM, SSH gateway, Re:gine backend |

`litellm` and `ssh-gateway` are **system applications**. They carry machine
clients, audiences and validators, never user memberships. Users are members of
the resource application that offers the resource, not of the adapter service.

```
resource
  id
  application_id        -> resource application (share-app, re-gine, acme)
  scheme                -> llm, agent, mcp, ssh, gine...
  locator
  uri                   -> ssh://<id>, gine://project_db_id, llm://acme/gpt-x
  owner_type            -> user | application
  owner_id
  status                -> pending_validation | validation_failed | validated | disabled
  listed
  created_at, updated_at
```

## 2. URI and scheme registry

### Identity

- Canonical URI: `<scheme>://<locator>`.
- `scheme` is lowercase alphanumeric, starts with a letter, at most 50
  characters (`^[a-z][a-z0-9]{0,49}$`).
- `locator` is validated by the scheme adapter. The default opaque grammar is
  `[A-Za-z0-9._~-]{1,255}`; adapters may be stricter or allow structure such as
  `/tool/<name>`.
- `uri` is unique, at most 512 characters. `(scheme, locator)` is unique.
- Ownership is stored on the resource row, never inferred from the URI.

Examples:

| Scheme | Resource | Example |
|---|---|---|
| `llm` | Model | `llm://acme/gpt-x` |
| `agent` | A2A agent | `agent://acme/analyst` |
| `mcp` | MCP server | `mcp://acme/server-x` |
| `mcp` + `/tool/` | MCP tool | `mcp://acme/server-x/tool/search` |
| `ssh` | Opaque SSH resource | `ssh://<resourceId>` |
| `gine` | Re:gine project | `gine://project_db_id` |
| `https` | Reserved HTTP endpoint | `https://...` |
| `file` | Reserved file | `file:///...` |

`workflow` and `mcp_agent` are removed. A LiteLLM workflow is an `agent`; an
MCP agent is an `mcp` server.

### Built-in schemes

Built-in schemes are defined in code, not created by admins:

```
llm    -> adapter litellm, validator litellm,        LITELLM_* profile
agent  -> adapter litellm, validator litellm,        LITELLM_* profile
mcp    -> adapter litellm, validator litellm,        LITELLM_* profile
ssh    -> adapter ssh,     validator ssh-gateway,    profile ssh
https  -> adapter http,    validator http-proxy,     later
file   -> adapter file,    validator file-service,   later
```

They are mirrored into `resource_scheme` with `source = 'builtin'` for
referential integrity. Their metadata and validator come from code. Global
availability follows the environment flag or Compose profile; per-application
availability follows `application_scheme`.

### Application schemes

An application admin registers an application scheme from the application's
`Sharing` tab (AuthService admins and superadmins may also do it). The row is
`source = 'application'`, `owner_type = 'application'`, `owner_id = <app>`.
The validator is the application's backend or a designated service client. The
UI shows the display name, description and icon, not the raw scheme.

### Per-application activation

```
application_scheme
  application_id
  scheme
  enabled
  created_at
```

An application scheme is auto-enabled for its owner application. A built-in
scheme must be enabled by the application admin. The catalogue only shows
schemes enabled for the selected application context.

## 3. Ownership and grants

### Ownership

- `owner_type ∈ {user, application}`, `owner_id`.
- The owner may always access and create grants for the resource, provided the
  owner is still an active member of the resource application.
- Application-owned resources represent operator or application assets.
- User-owned resources represent personal assets such as an SSH account.

### Membership gate

Access requires an **active membership in `resource.application_id`**, plus one
of:

- ownership,
- an explicit grant.

An administrator (application or platform) and a `grants:manage` delegate are
not recipients: they receive nothing implicitly, so a resource that is not
theirs and not shared with them is denied like for any other member. They
supervise (lists, usage, access log, disabling a resource) without being able
to use it. A `guest` member (see below) receives shares and creates nothing.

A grant never bypasses application membership. Sharing a Re:gine project
without access to Re:gine would be useless, and the OIDC flow expects the
recipient to be active in the application.

### Grant subjects

```
resource_grant
  id
  resource_id
  subject_type      -> user | organization | plan | everyone
  subject_id        -> null for everyone
  permission        -> use
  expires_at
  revoked_at
  created_by
  created_at
```

- `user`: any active AuthService account for a personal resource (access still requires membership of the application the recipient calls through); an active member of the resource application for an application-owned resource.
- `organization`: active members of the organisation **and** of the resource
  application.
- `plan`: users with an active subscription to the plan, which implies
  membership in the resource application.
- `everyone`: every active member of the resource application. It is not every
  AuthService account.

Grants are resource-by-resource. Sub-resources are the adapter's concern.

### Authority matrix

| Actor | Personal resource (`user` owner) | Application-owned resource |
|---|---|---|
| Owner (active, not `guest`) | Grants to any existing account, one by one; invites | n/a |
| Application admin | Sees it; may disable it; never grants or invites on it | Grants to any subject; invites; adds members |
| Delegate `grants:manage` | Never | Grants to existing members |
| Delegate `resources:manage` | Never | Manages the resource, no grant |
| AuthService admin / superadmin | Same as an application admin | Same as an application admin |

Granting to an organisation, a plan or everyone is reserved to application
admins and only applies to application-owned resources: those groups would
include the administrator, so a personal resource is shared only with named
members by its owner. For a personal resource, the owner names any existing account; the recipient
still needs membership of the application they call through at access time.

## 4. Invitations and application membership

- Non-active account: `resource_invitation` email-bound, then registration,
  default application access and the grant at acceptance.
- Active AuthService account but not an application member: an application
  admin adds the user (`user_applications`), assigns default role and plan
  through the existing application-access path, sends a notification email,
  then creates the grant.
- Active member: direct grant, no invitation.
- Organisation / plan / everyone: direct grant, no email.

Only application admins may invite or add users to the application.

## 5. Validation protocol

```
pending_validation
  -> validated
  -> validation_failed -> pending_validation

any state -> disabled (manual disable or invalidation)
```

1. The owner creates a self-service resource. For SSH, auth-service generates
   the identity key pair and returns the `authorized_keys` line to install.
2. The resource stays `pending_validation`.
3. The owner clicks "Validate". Auth-service marks the request and returns the
   validator instructions: a validator URL for external schemes, or an SSH
   command to run against the target.
4. The validator proves ownership:
   - SSH: login with the identity key on the target account, pinned host key.
   - Re:gine: the project belongs to the caller.
   - LiteLLM: the model, agent, server or tool exists in the inventory and is
     in the application's scope.
5. The validator calls
   `POST /api/internal/gateway/resources/:id/validate` with `validated` or
   `validation_failed`.
6. Auth-service checks that the caller is the validator bound to the scheme and
   transitions the resource.

No polling. If the validator is unavailable, the resource stays pending and the
owner retries manually. A validator may later call
`POST /api/internal/gateway/resources/:id/invalidate` on access when ownership is lost
(SSH host key changed, project deleted, object removed from inventory). The
resource is disabled, the owner is warned and live sessions are closed by the
gateway.

## 6. Accounting and monitoring

Two append-only surfaces:

**`resource_access_event`** for the RSSI / system administrator:

```
occurred_at, resource_id, uri, scheme,
owner_type, owner_id,
subject_type, subject_id, actor_user_id,
client_id, application_id,
decision (allow | deny), reason_class,
request_id, source, metadata
```

**`resource_usage_record`** for the sales / billing view:

```
occurred_at, resource_id, uri, scheme,
owner_type, owner_id,
subject_type, subject_id,
client_id, application_id,
request_id,
prompt_tokens, completion_tokens, total_tokens,
cost_usd, usage_source
unique (resource_id, request_id)
```

Retention:

| Data | Default | Environment variable |
|---|---:|---|
| Access events | 90 days | `RESOURCE_ACCESS_EVENT_RETENTION_DAYS` |
| Usage records | 400 days | `RESOURCE_USAGE_RECORD_RETENTION_DAYS` |
| Sweep interval | 24 hours | `RESOURCE_RETENTION_SWEEP_HOURS` |

No source IP by default. Denials are logged with a generic reason class. The
purge runs in batches at startup and periodically.

Views:

- Admin/RSSI: effective grant matrix, last access, denials, resources by owner
  and scheme.
- Sales: usage by resource, owner, scheme, organisation, plan, client and
  period; call counts, tokens, gross cost, number and types of shared resources.

## 7. LiteLLM mapping

- `gateway_object` is a read-only inventory projection of LiteLLM objects. It
  is not the ownership model.
- A resource references a `gateway_object` when applicable. Several
  application-scoped resources may reference the same inventory object.
- The entitlement resolver returns the union of resources the subject can
  reach through all its application memberships and grants, not only the
  resources of `azp`. `azp` remains the calling client for audit and optional
  `allowed_client_ids`.
- `custom_auth` receives `models`, `object_permission.mcp_servers`,
  `mcp_tool_permissions` and `agents`, and denies closed.
- No teams, access groups or ACL writes into LiteLLM. The provisioner only
  holds read access to the inventory and a machine client for entitlements.

## 8. SSH gateway

The SSH gateway is an **external project in its own repository**. Its source,
tests, release workflow and Docker image are out of scope for the auth-service
implementation lots. auth-service integrates the published image under the
`ssh` Compose profile and implements the auth-service side of the contract.
The full specification and the implementation prompt live in
[9. SSH gateway — external contract](./9.ssh-gateway-external-spec).

- Separate Docker deployable under the `ssh` profile, built from the external
  repository; Rust `russh` is the baseline (Warpgate is the reference, not a
  dependency).
- Only the SSH listener, client authentication, device approval, authorization
  call, session relay, resource validation and accounting. No admin UI, no
  database, no shell.
- Private identity keys are decrypted in memory with an envelope key mounted as
  a secret.
- A `share-app` admin enables `ssh`; users of `share-app` create and share
  `ssh://<id>` resources; the gateway is a system application and never a
  membership application.
- Device approval uses auth-service. The gateway validates the resulting
  session proof through a machine-scoped endpoint; a BetterAuth session token
  is not a machine credential.

### Warpgate spike (2026-11-15)

Warpgate is Apache-2.0, written in Rust, uses `russh`, and is actively
maintained. It provides SSH, OIDC SSO, public keys, keyboard-interactive, web
approval, session recording and brute-force protection.

It is **not a drop-in fit** for this design:

- its authorization is its own database of users, roles and targets
  (`ConfigProviderEnum` only has `Database`; no external provider or webhook);
- using it directly would duplicate grants into Warpgate roles and targets, and
  turn auth-service into a sync source rather than the per-request PDP;
- its web approval is its own UI, not the auth-service device flow.

Decision: do not adopt Warpgate as the gateway. Reuse it as a reference for the
SSH state machine and PTY relay, and build the minimal gateway with `russh`
(Rust) unless the lot-4 spike shows a blocker. This is the case where Rust is
justified: single binary, memory safety, no Node runtime, production-proven
`russh`.

## 9. Test-server migration

The test server has no sharing data to preserve, only applications, users,
OAuth clients, plans and related rows.

1. `pg_dump --data-only` excluding `shared_resource`, `resource_grant`,
   `resource_invitation` and `usage_record`.
2. Recreate the database and apply the new consolidated baseline.
3. Restore the data-only dump.
4. Verify the existing OIDC applications.

Fresh installations use the regenerated `drizzle/0000_initial_schema.sql`. No
`0001_*.sql` is committed.

## 10. Supersession

- Plan 5: D7 (fixed resource types), D10 (`plan_id` mandatory on grants),
  D14 (static scheme registry), D17 (`upstream_ref` as the gateway identity),
  D20 (application-owned only) are refined by this document.
- Plan 6: `gateway_object` becomes inventory only; `plan_gateway_grant` is
  replaced by `resource_grant` with `subject_type = 'plan'`; teams and access
  groups are removed as planned.
- Plan 7: `owner_user_id` and separate share tables become the generic
  `resource` + `resource_grant` model plus SSH adapter detail tables. The
  gateway remains separate, but Warpgate is rejected as a drop-in.

## 11. Implementation order

1. Lot 1 — cleanup and decoupling (no schema change).
2. Lot 2 — generic core: URI registry, ownership, grants, invitations,
   validation, accounting.
3. Lot 3 — LiteLLM cutover: inventory, entitlements, hook, removal of teams and
   access groups.
4. Lot 4 — SSH integration: auth-service-side schema and endpoints, Compose
   profile for the published external image, contract tests. The gateway
   implementation itself is delivered by the external repository described in
   [9. SSH gateway — external contract](./9.ssh-gateway-external-spec).
5. Lot 5 — consolidation, documentation and gates.

- Image pin moved to `v1.108.8` in Compose, package.json, `.env.example` and the
  gateway guide.

  discovery and usage.

Still to validate with a live gateway:

- the `proxy_admin_viewer` role is allowed to read `/v1/agents` and

- an end-to-end token receives the expected model/agent/MCP lists and a

- the LiteLLM admin UI still signs in through auth-service and virtual keys

## 15. Lot 4 status — auth-service side (2026-11-15)

Implemented in auth-service:

- `src/db/ssh-schema.ts`: target detail, identity, meta-user, recipient key and
  session tables.
- Ed25519 identity generation without a third-party SSH library; the private key
  is stored as AES-256-GCM ciphertext under `SSH_GATEWAY_ENVELOPE_KEY`, and the
  owner receives the `authorized_keys` line.
- User routes: SSH target setup/detail, meta-user CRUD, recipient key CRUD.
- Gateway routes: meta-user resolution, recipient-key resolution, target detail
  (with an owner check when `subjectId` is supplied), session accounting and
  device-session validation.
- Validation callback accepts `evidence.hostKeyFingerprint` and pins it on the
  SSH resource. The authorize route accepts the `source` field.
- `ssh` Compose profile consumes the external image through
  `SSH_GATEWAY_IMAGE`; auth-service never builds the gateway.
- Catalogue UI: SSH target dialog, `authorized_keys` line, meta-user selectors,
  validation command and recipient key management.

Validation no longer uses an HTTP page: the owner runs
`ssh -p <port> validate-<resourceId>@<gateway-host>`, the gateway device-approves
the owner, fetches the target detail with the subject, logs in with the
identity key and calls back. The external contract was updated accordingly.

Still external/operator-owned:

- the gateway repository, Rust `russh` implementation and `nightly`/`latest`
  image workflows;
- registration of the `ssh-gateway` machine client, the device client and the
  shared envelope key;
- a live end-to-end test against the published image and `test@nuk.local`.
