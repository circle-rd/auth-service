## 1. Goal

One login, one endpoint, many shared resources. An owner application publishes
resources (models, workflows, MCP agents, later HTTPS API endpoints, later
SSH hosts); invited users reach any of them through the gateway they already
use, with a single OAuth client per agent, without owner-specific logins and
without exposing private infrastructure.

The authorization decision is always server-side auth-service policy deriving
from a trusted resource registry — never an OAuth claim. `azp` remains the
calling OAuth client.

Reconciliation runs at startup and every 5 minutes; transient network/5xx/429 errors retry three times with bounded backoff, while permanent 4xx and schema errors fail loudly. Disable removes the entity from the owner plan groups; the stale-grant bound is one reconciliation interval plus one bounded attempt (M2 policy already denies within 30 s). | Least privilege and idempotent convergence without a distributed lock; the sync never creates or deletes an access group. |
| D19 | Owner authority for M3 is the application's existing built-in `admin` role membership (the creator and every superadmin receive it at application creation). A new `app_delegation` table adds explicit, least-privilege permissions for non-members: `resources:read`, `resources:manage`, `grants:manage`; `resources:manage` also satisfies reads. | D20 | Resource invitations use a dedicated `resource_invitation` table following the registration-invitation pattern: token stored only as SHA-256, 72 h default expiry (1–168 h allowed), consumed/revoked timestamps, email-bound redemption. | D21 | M3 owner `DELETE /shared-resources/:id` is a soft delete: it transitions `status` to `disabled` through `updateSharedResource`, queues the owner-scoped M1.6 reconciliation, and returns the row. No physical delete endpoint is exposed. | M1.6 derives access-group membership from rows still present; physical deletion would leave stale LiteLLM access. Disabling is already denied by policy and removed by sync. |
| D22 | Deviation from D13's initial 60 s JWKS target: BetterAuth 1.7.15 hard-codes a 5 min process-level JWKS cache (with an unknown-`kid` refetch cooldown of 30 s) and exposes no supported TTL override. The service activates that cache with a stable `jwksCacheKey`; it does not add a second/leaky JWKS cache or an unused `JWKS_CACHE_TTL_SECONDS` knob. | Bounded impact: a rotated-out key can verify for up to 5 min, and a newly rotated-in key is fetched on an unknown-`kid` request once the 30 s refetch cooldown permits it (no refetch is forced inside that window). Accepted alternative: keep `/api/auth/jwks` on `Cache-Control: public, max-age=60` for consumers and revisit if BetterAuth exposes a TTL option. |
| D23 | M5 precedes M4 because the owner portal's usage view must read real owner-attributed ledger data; the UI must not fabricate usage or imply settlement. M5 must finish the usage ingestion/read API and verify the owner/app/invitation data surfaces needed by M4. | Keeps the portal on a stable, tested API contract. If an owner-scoped discovery/read surface is missing, implement the minimal scoped API prerequisite before presenting that data in M4. |
| D24 | `usage_record` is a gross provider-usage ledger with idempotency on `(resource_id, request_id)`. `request_id` is generated by the gateway from trusted LiteLLM call data (trace id, call id, start time, resource key), never from a client header or request metadata. A replay with the same payload is idempotent; a conflicting payload is rejected. | Separates accounting from the prepaid wallet (D5), prevents retry duplication and keeps genuinely distinct provider attempts (retries/fallbacks) as separate rows. |
| D25 | Usage ingestion uses a dedicated `resources:usage:write` machine scope. auth-service derives the owner application from the resource row, resolves the plan from the owner's plans, and verifies the subject -> owner relation (membership or any grant) plus the grant's client allow-list. The gateway's verified `sub`/`azp` and M1 decision are the only identity source. | Least privilege and a server-side trust boundary: no caller-supplied owner, plan or cost authority is accepted, and admission's `resources:authorize` scope is not widened. |
| D26 | The gateway emits one usage event per executed resource/provider attempt. Successful calls with positive cost/tokens are `provider`; partial-stream/error usage is recorded only when actual cost/tokens exist; zero-usage failures and denied/discovery calls create no row; a successful non-model call without telemetry is stored as `unsupported` with null cost/tokens. Delivery is spooled to a separate durable directory with bounded retry and dead-lettering, so an auth-service outage never fails a completed response. | Preserves exactly the work that executed, avoids invented zeros/tokens and prevents lost or duplicated owner accounting without co-mingling it with wallet debits. |
| D27 | M5 adds the minimal M4 prerequisites that M3 did not expose: session-scoped owner application discovery (`GET /api/user/apps`), owner member listing, and invitation listing/revocation. Everything remains behind the existing session + `app_delegation` guards; no platform-admin route is reused and no free-form application id is accepted. | Lets a normal owner UI enumerate only authorized applications and render members/access/invitations without weakening tenant isolation or expanding M5 into frontend work. |
| D28 | No admin aggregated sharing-usage API is added in M5. The owner usage API is the distinct, tested read surface; platform-admin accounting already has its own aggregates and would not add a new contract for M4. | Avoids a speculative admin surface; revisit only if an operator reporting requirement is defined. |
| D29 | M4 adds two minimal owner-read contract additions found by the precondition audit: `GET /api/user/apps/:appId/plans` (`grants:manage`) exposes the owner application's plan ids/names for grant and invitation selection, and the usage groups/totals expose `unsupportedCalls` so telemetry-less ledger rows render as not available instead of a fabricated zero. The subject catalogue/model selector remains deferred: the portal has no server-provided OAuth `clientId`, and no free-form client or audience input is accepted. | Plan ids cannot be guessed from grant display names, and invitation creation requires one. `unsupportedCalls` is additive; provider sums are unchanged. The residual O-D browser-context gap is reported rather than papered over. |

## 3. Data model (custom schema, pre-production baseline)

All tables in `src/db/schema.ts`, snake_case columns. Pre-production: every
schema change regenerates the consolidated `drizzle/0000_initial_schema.sql`
(`pnpm db:generate --name initial_schema`, databases recreated from scratch);
no delta migrations before first production deploy.

- `shared_resource { id, owner_application_id, resource_type, key, display_name, upstream_ref, status, visibility, default_plan_id?, created_at, updated_at }`
  - `key` — canonical unique `<applicationSlug>/<slug>` across all types; immutable once published (AC-05).
  - `upstream_ref` — opaque per type: LiteLLM deployment/team reference for gateway-managed types; URL hint for `https_endpoint`. Secrets are never stored here; `https_endpoint` upstream credentials live in type-specific secret storage at provision time.
  - `status ∈ {draft, published, disabled}`, `visibility ∈ {invited_only, public_catalog}`.
- `resource_grant { id, subject_id, owner_application_id, resource_id?, plan_id, allowed_client_ids?, expires_at?, revoked_at?, created_by, created_at }`
  - `resource_id` null = whole owner-application scoping; explicit row only for invited non-members (D10).
- `app_delegation { id, user_id, application_id, permission, status, created_at, updated_at }` — delegated owner administration; no platform role involved. Unique per `(user_id, application_id, permission)`.
- `resource_invitation { id, token_hash, email, owner_application_id, resource_id?, plan_id, allowed_client_ids?, expires_at, consumed_at?, revoked_at?, created_by, created_at }` — one-shot, email-bound invitation redeemed into a `resource_grant`.
- `usage_record { id, subject_id, client_id, owner_application_id, resource_type, resource_id, resource_key, plan_id, request_id, prompt_tokens, completion_tokens, total_tokens, cost_usd, usage_source, occurred_at, created_at }` — gross metering only (D5), delivered by the gateway with retry/backlog reuse. `(resource_id, request_id)` is unique; `usage_source ∈ {provider, unsupported}` and unsupported rows keep cost/tokens null (D24/D26). Resource rows are soft-disabled, so their usage survives.

`resource_grant` and `app_delegation` reuse the existing invitation pipeline
for the "invite" step (bucket `EMAIL_SEND_PATHS` in `src/server.ts`).

## 4. API surface (auth-service)

Machine-to-machine, gateway-scoped (extend `MACHINE_SCOPES` with a dedicated
`resources:authorize` scope; wallet consultation keeps `wallet:read`):

- `POST /api/internal/gateway/authorize` — Zod-validated body `{ subjectId, clientId, resourceType, key, audience, requestId }`; the gateway derives `subjectId` from the verified JWT `sub`, `clientId` from `azp`, audience from its configured/verified OIDC audience, and `requestId` server-side. Allow response is `{ decision: "allow", ownerApplicationSlug, planName, teamId, resourceId }`; deny is exactly `{ decision: "deny" }` with no metadata echo.
- `GET /api/internal/gateway/resources/accessible?subjectId=…&clientId=…&resourceType=…&audience=…` — machine-scoped list used to filter discovery. M2 caches it for 30 s by subject/client/type/audience.

Owner and user APIs (dashboard session, delegated guard `requireAppDelegation`):

- `GET /api/user/accessible-resources?clientId=…&resourceType=?&audience=?` — what the authenticated subject may reach (portal catalogue). The subject is the session user; `clientId` is required because explicit grants may narrow clients.
- `GET|POST /api/user/apps/:appId/shared-resources`, `GET|PATCH|DELETE /api/user/apps/:appId/shared-resources/:resourceId` — owner CRUD, Zod-validated, cross-tenant ids rejected. `DELETE` soft-deletes (`status: disabled`) and queues M1.6 reconciliation; it never removes the row.
- `GET /api/user/apps/:appId/grants` and `PUT|DELETE /api/user/apps/:appId/grants/:grantId` — list, narrow, expire or revoke (AC-03: effective ≤ 30 s).
- `POST /api/user/apps/:appId/invitations` — invite an email to a plan/resource; the response carries the one-time acceptance URL.
- `POST /api/user/resource-invitations/accept` — redeem the token for the authenticated, email-matched subject and create the explicit grant.
- `GET /api/user/apps/:appId/usage?groupBy=user|resource` — owner-attributed usage (M5), guarded by `resources:read`, with time filters, pagination and `unsupportedCalls` so telemetry-less rows are never rendered as zero.
- `GET /api/user/apps` — owner-scoped application discovery (M5, M4 prerequisite); `GET /api/user/apps/:appId/members`, `GET /api/user/apps/:appId/plans` and `GET|DELETE /api/user/apps/:appId/invitations[/:invitationId]` expose the minimal member/plan/access/invitation data the portal needs.
- `POST /api/internal/gateway/usage` — machine-scoped (`resources:usage:write`) idempotent gross-usage ingestion used by the gateway (M5).

Admin routes and existing single-app flows are untouched.

## 5. Milestones, workstreams and commit cadence

Each implementation milestone is developed in an isolated worktree/branch based
on the last validated `feature/resource-sharing` head, with small commits and
quality gates at each logical boundary. Once reviewed and validated, its branch
is integrated into the long-lived `feature/resource-sharing` branch. The PR to
`develop` is opened when the maintainer considers the planned work ready; an
intermediate PR may be used when a foundation needs an independent review or
test deployment. Never merge directly to `develop`/`main` or build/deploy CI
images from an agent session; the maintainer owns those steps.

Phase P0–P3 (performance chain) — see the wave below; commits:

1. `perf: bench harness + baseline report (P0)` — measurement scripts + report, no runtime change.
2. `perf(res): cache signer keys and accepted audiences (P1)` + tests.
3. `perf: unify session resolution + cache (P2)` — spike ADR first, then implementation + `session.*` invalidation tests.
4. `docs: jwks cache-control + periphery audit notes (P3)`.

Deviations and deferrals recorded for M2:

  `litellm-setup`; provisioning is a documented operator step. The gateway

Deviations and deferrals recorded for M3:

- Catalogue listing requires the calling agent's `clientId` (optional `audience`,
  defaulting to the issuer URL) because explicit grants may be narrowed by
  `allowed_client_ids`; omitting it would claim access the policy cannot verify.
  The subject always comes from the session, never from input.
- Explicit delegation rows are data-model/guard only in M3: there is no API to
  create them, so deployment owners seed them deliberately (or use the app
  `admin` role). Delegation administration is deferred until the portal needs it.
- The M1.6 LiteLLM caveat remains unresolved: v1.108.3 matches `allowed_routes`
  by path, so the dedicated sync credential is method-restricted by the client,
  not by the gateway. It stays an internal service credential and is never
  exposed to owner routes.

  M1.6 gateway sync until M6.

## 6. Security notes (review before M1/M2/M6)

- Trust: verified JWT (JWKS) + server registry only; every deny path uniform; no token, secret or upstream URL in logs or error `details` (project doctrine §10).
- Gateway: request `model`/resource key parsed before admission; unknown/absent/disabled → `404 RES_004`; other LiteLLM routes explicit allowlist (no unchecked bypass).
- Delegation: least privilege per application; every mutation effective ≤ cache TTL; owner APIs never expose admin keys or the master key.
- Registry sync: dedicated provisioner credential; rotation like `litellm-provision`; reconciliation is idempotent.
- Quota and abuse: machine-scope buckets for the internal authorize API; per-client rate limits at the gateway.
- Egress (`https_endpoint`): deny-by-default URL policy via the outbound guard, no private/metadata ranges, redirects re-validated.

### P1 — result (2026-11-13)

BetterAuth 1.7.15 already implements process-level JWKS caching inside
`verifyJwsAccessToken` (5 min TTL, 30 s refetch cooldown, unknown-`kid`
refetch) — but only when the caller passes a stable `jwksCacheKey`, so the
verification call now supplies one. D22 records the deviation from D13's
locked 60 s TTL: the installed upstream version has no supported TTL override,
so no misleading configuration knob is exposed. The protected-resource
(audience) list has
no upstream cache and is cached here (`RESOURCE_CACHE_TTL_SECONDS`, 30 s,
`0` disables) and invalidated by `replaceClientResource`. Key rotation needs
no local hook: the upstream unknown-`kid` refetch picks up a new key within
one request.

Measured on the JWT path (5 counted requests after warm-up, cache on):

| SQL statement per machine request | P0 | P1 |
|-----------------------------------|----|----|
| `select … from "jwks"` | 1 | **0** |
| `select … from "oauth_resource"` (audiences) | 1 | **0** |
| `select … from "oauth_client"` (live client check) | 1 | 1 (locked decision) |
| plan resolution (user_subscriptions + applications) | 2 | 2 |
| **total** | **5** | **3** |

Throughput on the machine scenario is paced (60 rps) so latency is not
comparable; the session path (3 SQL/req) is P2's target. Remaining known
reduction candidates, deliberately out of P1 scope: the plan resolver's two
queries can merge into one join, and the plan/authorize endpoint of M1 will
extend this path anyway.

### P2 — session mirror on Redis (2026-11-13)

**Spike (BetterAuth 1.7.15 source + executed against PostgreSQL 17 and Redis 7).**
The spike ran three configurations of the product's `auth` shape:

| Check | Pure `secondaryStorage` | Mirror (`storeSessionInDatabase: true`) |
|-------|-------------------------|------------------------------------------|
| Read after single-session revocation is refused | pass | pass |
| `deleteUserSessions` clears every session and Redis key | pass | pass |
| Ban through the adapter reaches a live session | pass | pass |
| Role change by direct SQL reaches a live session | **fail** | **fail** |
| Role change through `internalAdapter.updateUser` reaches a live session | pass | pass |
| Session rows remain in PostgreSQL (admin listings) | **no** | yes |

Decision: mirror mode. Pure mode would hide every session from the
admin screens that query the `session` table. The role defect is a
prerequisite fix, not a cache problem: the admin role change bypassed the
adapter (see `admin/users.ts`), so Redis would have served the old role
until the session expired.

**Implementation.**

- `services/redis-client.ts`: one lazily loaded `ioredis` connection shared by
  the rate-limit store and the session store; closed once on shutdown.
- `services/session-store.ts`: the BetterAuth `SecondaryStorage` contract
  (`get`, `getAndDelete`, `increment`, `set`, `delete`) under the
  `auth:session:` namespace.
- `auth.ts`: `secondaryStorage` and `session.storeSessionInDatabase: true`,
  enabled only when `REDIS_URL` is set.
- `services/session-snapshot.ts`: `refreshUserSessionSnapshots` uses the
  hook-free adapter snapshot refresh API with an explicit user projection.
  Authorization-sensitive admin/profile mutations use
  `mutateUserAndRefreshSnapshots`: a per-user transaction-scoped advisory lock
  serializes writers, the Redis snapshot is published before DB commit, a Redis
  failure rolls back the mutation, and a failed DB commit reconciles the mirror
  from the committed row. No `user.update` side effects are replayed.

**Measured (same machine, `--reps 500 --concurrency 25`, bench-owned server,
fresh per run):**

| Scenario | Without Redis (p50 / rps / SQL per request) | With `REDIS_URL` (p50 / rps / SQL per request) |
|----------|---------------------------------------------|-------------------------------------------------|
| session (`GET /api/user/sessions`, cookie) | 51.4 ms / 476 / 3 | 34.8 ms / 694 / 1 |
| machine (bearer JWT, gateway plan) | 8.7 ms / 58 (paced) / 3.4 | 8.7 ms / 58 (paced) / 3.4 |

The remaining session statement is the route's own query (`from "session"`
listing the user's sessions), not authentication: the cookie lookup now runs
no SQL. The machine path does not use sessions, so it is unchanged, as
expected.

**Fail-closed check.** Session request with Redis up: `200`. With Redis
stopped: `503 SRV_002` (mapped in `services/session-store.ts`; BetterAuth
endpoints and Fastify routes both answer it). No access is granted.

**Tests.**

- `session-redis.integration.test.ts` (own Redis testcontainer, real BetterAuth
  with `REDIS_URL` set): namespace, revocation of one and of all sessions,
  role change visible only after refresh, ban visible through the adapter,
  rollback when Redis cannot publish a role/verification change, concurrent
  refreshes serialising to the committed row, and a shared Redis client
  surviving server close/rebuild.
- Unit: `session-store.test.ts` (namespace, TTL, atomic `increment` window),
  `session-snapshot.test.ts` (hook-free refresh).
- Full suites green: 913 unit, 541 integration.

**Known limits.**

- `lastLoginAt` is written on every login and is not pushed to live
  snapshots. It is display-only and deliberately excluded to avoid an extra
  write and billing sync on each login.
- Bootstrap writes happen before the server listens; no live session exists
  then.
- A Redis outage refuses sessions (`503 SRV_002`) rather than falling back to
  the database (fail closed). Resilience would need an explicit degraded mode,
  decided separately.

### P3 — result (2026-11-13)

- `GET /api/auth/jwks` now answers `Cache-Control: public, max-age=60`. Before,
  the header was absent. Verified over HTTP and by a unit test.
- Periphery audit: the gateway (`litellm/custom_auth.py`) caches the key set
  and the plan; the ioserver guide prescribes an in-process JWKS cache; the
  JWT guides say not to call `/userinfo` or introspection per request. No
  per-request call to `get-session` or introspection exists in the repository
  or the documented integrations. Downstream SDK repositories were not
  inspected from this repository.
