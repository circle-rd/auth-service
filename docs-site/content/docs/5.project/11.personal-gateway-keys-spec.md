> Living document, status **implemented** (2026-11-26), pending deployment. It
> implements option A of the external-credential decision recorded in the
> raiversed `native_algorithm_analysis.md` §18. LiteLLM stays the only `/v1`
> surface; auth-service stays the only decision point. Nothing in this spec
> writes to LiteLLM for access control (LA-2).

## 1. Purpose

A consumer (IDE, CLI, agent) needs a long-lived credential to call the LLM
gateway. Access tokens expire; the browser must never hold one. auth-service
therefore issues a **personal gateway key**: an opaque, revocable credential
that the LiteLLM hook resolves on every request, exactly like a user access
token, with the entitlement lists narrowed to the key's **pool**.

- The key is bound to `(user, application, pool)`.
- A pool is an organization the user belongs to, or **whole network** (null)
  meaning "everything the user may reach through that application".
- The key names a pool; it does **not** carry a routing mode, a model list, a
  rate limit or a budget. Those are later phases and stay out of scope.

## 2. Scope

**In scope**

- `personal_gateway_keys` table and key format;
- user endpoints: list, create (full key shown once), revoke;
- machine endpoint used by the LiteLLM hook to resolve a key;
- hook branch for the key prefix, including immediate revocation;
- decision-token key reference and usage-record attribution;
- error codes `KEY_*`, documentation and the pre-production baseline.

**Out of scope**

- LiteLLM virtual keys (`sk-`), teams and access groups (LA-2);
- per-key routing modes (`best`, `efficient`, `free`) and routing groups —
  see `native_algorithm_analysis.md` §11/§18, hypothesis H18;
- per-key rate limits, budgets or quotas;
- an auth-service UI: the consumer application (raiversed) owns the screens
  and calls the user endpoints through its BFF;
- SSH, file and other non-LiteLLM schemes.

## 3. Decisions

| #  | Decision                                                                                                                                                                                                                             | Rationale                                                                                                                                                                    |
| -- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PK-1  | Keys are issued, stored and revoked by auth-service. LiteLLM never mints, stores or lists them; `sk-` keys remain LiteLLM-native and untouched.                                                                                      | One credential store, one revocation point; the gateway keeps no consumer credential state (LA-2).                                                                            |
| PK-2  | Key format: `cgk_` + 43 base64url characters (32 random bytes), regex `^cgk_[A-Za-z0-9_-]{43}$`. Only the SHA-256 base64url hash is stored; the full key is returned exactly once and never logged.                                   | High entropy, cheap lookup, no plaintext at rest; `cgk_` cannot collide with `sk-` or a three-segment JWT.                                                                    |
| PK-3  | The key is hashed with the same helper as the other opaque tokens (`hashOpaqueToken`, `src/services/oauth-tokens.ts`), exported instead of duplicated.                                                                               | AGENTS.md, no code duplication.                                                                                                                                               |
| PK-4  | Pool semantics: `organizationId = null` → the user's full entitlements for the key's application. `organizationId = <org>` → the resources the user owns **plus** the resources granted to that organization. Direct user grants, `everyone` grants and plan grants are excluded, and the user must still be an active member of the organization. | A pool narrows what the key reaches; it never widens it. Team shares stay the only cross-user source of a pool key.                                                           |
| PK-5  | Personal keys are resolved on **every** request; the hook must not serve a cached answer for them.                                                                                                                                    | Revocation is immediate, stronger than the 30 s JWT bound (LA-6); the resolution is one indexed read.                                                                         |
| PK-6  | The machine endpoint reuses the existing `gateway:entitlements:read` scope and returns the same payload shape as `POST /api/internal/gateway/entitlements`.                                                                           | The hook keeps one parser (`_parse`) and one identity builder; no new machine scope to provision.                                                                             |
| PK-7  | The decision token gains an optional `key` field, and `resource_usage_records` gains a nullable `gateway_key_id`.                                                                                                                     | Per-key usage attribution (the `requests30d` / `tokens30d` the consumer UI shows) without a second format change later.                                                       |
| PK-8  | User endpoints live under `/api/user/gateway-keys` and use the same admission as the user resource routes (`requireUserOrBearerCaller` + `resources:self:manage`).                                                                    | The consumer BFF already holds that scope and mints the user token server-side; no new scope, no new client configuration.                                                     |
| PK-9  | `POST /api/user/gateway-keys` is added to `AUTH_RATE_PATHS`.                                                                                                                                                                          | AGENTS.md §10: endpoints that issue credentials are rate-limited.                                                                                                             |
| PK-10 | Errors use a new `KEY_` domain (`src/errors.ts`); the AGENTS.md error-domain list gains `KEY_`.                                                                                                                                       | The resource domain already grew beyond the original list (`RES_`); a credential domain deserves its own prefix.                                                              |

## 4. Data model

New file `src/db/gateway-key-schema.ts` (LA-10: `src/db/schema.ts` is at its
line ceiling). Export the table from `src/db/index.ts` like the other schema
files.

```ts
export const personalGatewayKeys = pgTable(
  "personal_gateway_keys",
  {
    id: uuid("id").primaryKey().defaultRandom(),
    userId: text("user_id").notNull().references(() => user.id, { onDelete: "cascade" }),
    // The application the key was created for; it scopes the entitlements.
    applicationId: uuid("application_id").notNull().references(() => applications.id, { onDelete: "cascade" }),
    // null = whole network. Cascade: a deleted organization invalidates its keys.
    organizationId: text("organization_id").references(() => organization.id, { onDelete: "cascade" }),
    label: text("label").notNull(),
    keyHash: text("key_hash").notNull(),
    maskedKey: text("masked_key").notNull(),
    lastUsedAt: timestamp("last_used_at", { withTimezone: true }),
    revokedAt: timestamp("revoked_at", { withTimezone: true }),
    createdAt: timestamp("created_at", { withTimezone: true }).defaultNow().notNull(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).defaultNow().notNull(),
  },
  (t) => [
    uniqueIndex("personal_gateway_keys_hash_idx").on(t.keyHash),
    index("personal_gateway_keys_user_idx").on(t.userId),
    check("personal_gateway_keys_label_check", sql`length(${t.label}) BETWEEN 1 AND 80`),
    check("personal_gateway_keys_hash_check", sql`length(${t.keyHash}) = 43`),
  ],
);
```

- `organization.id` is `text` (BetterAuth); `applications.id` is `uuid`.
- A user holds at most `PERSONAL_GATEWAY_KEYS_MAX_PER_USER` **active** keys
  (config, default 20). Revoked keys do not count.
- Baseline: delete `drizzle/` and regenerate `0000_initial_schema.sql`
  (LA-11); the diff must contain only this table, the `gateway_key_id` column
  and nothing else.

## 5. Key lifecycle

1. **Create** — `POST /api/user/gateway-keys`.
2. **List** — `GET /api/user/gateway-keys` (active keys only, masked).
3. **Revoke** — `DELETE /api/user/gateway-keys/:keyId` (sets `revokedAt`).
4. **Use** — `Authorization: Bearer cgk_…` against the LiteLLM gateway.
5. **Last used** — updated on every successful resolution.

The full key is returned **once**, in the create response, with
`Cache-Control: no-store`. It is never stored, never logged, never echoed by
any other endpoint, and never included in an `ApiError`.

## 6. User API

Registered under the `/api/user` prefix (`src/server.ts`, same block as the
resource routes). Admission: `requireUserOrBearerCaller` with
`resources:self:manage`, plus a consumer application: all three routes require
a bearer token from a consumer BFF. A web session has no application to bind
and is refused with `403 KEY_004`. The application is derived from the verified
bearer client id and always scopes the key: a consumer never sees or revokes
another application's key.

### 6.1 `GET /api/user/gateway-keys`

`200` with the calling application's active keys for the caller, masked:

```json
{ "keys": [ { "id": "…", "label": "IDE", "organizationId": "org_…", "maskedKey": "cgk_AbCdEf…wXyZ", "createdAt": "…", "lastUsedAt": "…" } ] }
```

`organizationId: null` is the whole-network pool. The organization name is
resolved by the consumer through its own organizations data; this endpoint
returns identifiers only.

### 6.2 `POST /api/user/gateway-keys`

Body: `{ "label": string(1..80), "organizationId": string? }`, `.strict()`.

Checks, in order:

1. the caller owns fewer than the configured maximum of active keys → else `409 KEY_005`;
2. when `organizationId` is present, the user is an active member of that
   organization → else `403 KEY_004`;
3. the key's application (the caller's, see §6.4) is active and has resource
   sharing enabled → else `403 KEY_004`.

`201` with the full key once: `{ id, label, organizationId, maskedKey, key, createdAt }`.

### 6.3 `DELETE /api/user/gateway-keys/:keyId`

Sets `revokedAt = now()` on a key owned by the caller and bound to the calling
application. `204`, idempotent for an already-revoked key; `404 KEY_002` for an
unknown, foreign or other-application key. Revocation is effective on the next
request (PK-5).

### 6.4 Application binding

The application is **not** read from the body. It is derived from the bearer
caller (`verified.clientId` → `applications.slug`): the key is bound to that
application and every management route is scoped to it. A web session has no
application to bind and is refused with `403 KEY_004`, so keys are created,
listed and revoked only through a consumer BFF, never from the auth-service
console. This keeps the entitlement scope well defined: the key inherits the
application scope of the client that created it.

## 7. Machine endpoint for the hook

`POST /api/internal/gateway/personal-keys/entitlements`
(`src/routes/gateway-internal.ts`), same `INTERNAL_RATE_LIMIT` as the JWT
endpoint.

Admission: `requireMachineScope(…, "gateway:entitlements:read")`.

Body: `{ "key": string }`, validated against the key regex first.

Responses:

| Situation                                                        | Status / code                                  |
| ---------------------------------------------------------------- | ---------------------------------------------- |
| Malformed, unknown or revoked key                                 | `401 KEY_001`                                  |
| User banned                                                       | `403 KEY_004`                                  |
| Key's application inactive or sharing disabled                    | `403 KEY_004`                                  |
| User not an active member of the key's application                | `403 KEY_004`                                  |
| Pool set and user not an active member of that organization       | `403 KEY_004`                                  |
| Known key, checks pass                                            | `200` with the entitlements payload below      |

`200` payload — the shape of the JWT endpoint plus `keyId`, so the hook keeps
one parser and can name the credential it authenticated:

```json
{
  "keyId": "…",
  "subjectId": "user_…",
  "clientId": "raiversed",
  "decisionId": "…",
  "expiresAt": "…",
  "models": ["…"],
  "agents": ["…"],
  "mcpServers": ["…"],
  "mcpToolPermissions": { "…": ["…"] },
  "resources": [ { "resourceId": "…", "uri": "…", "scheme": "llm", "kind": "model", "name": "…", "parentName": "", "applicationSlug": "raiversed", "ownerType": "user" } ]
}
```

- `subjectId` and `clientId` come from the key row; the hook trusts the answer,
  not the request.
- `decisionId` is signed with `signDecision({ sub, app, by, notAfter: null,
  key: keyId })`; `signDecision` and `decisionPayloadSchema` gain the optional
  `key` field (payload version stays 1).
- Empty lists are valid: the hook turns them into the `no-default-models` /
  `no-mcp-servers` sentinels (LA-5). An empty answer is never a silent allow.

### 7.1 Entitlement resolution with a pool

`listGatewayEntitlements(userId, caller, options?)` gains
`options.pool?: string`:

- `pool` unset → current behaviour, unchanged.
- `pool` set → the batch context (`src/services/resources/policy-batch.ts`)
  restricts grants to `subject_type = 'organization' AND subject_id = pool`;
  `user`, `everyone` and plan grants do not apply. Ownership is unchanged: a
  resource the user owns is always admitted by `decide()` (`isOwner`).
- The caller must still be an active member of the pool organization; this is
  re-checked at resolution time (`member` row), so leaving the team invalidates
  the key's reach even if the row persists.

## 8. LiteLLM hook

`litellm/custom_auth.py` gains one branch, before the JWT path:

```python
if api_key.startswith("cgk_"):
    # personal gateway key: resolved on every request, never cached
```

Behaviour:

1. validate the format; a mismatch raises the same 401 as an invalid token;
2. call the machine endpoint with `{ "key": api_key }`;
3. `401` with code `KEY_001` → `_reject`; a `401` with any other code can name
   an expired machine token, so the hook refreshes it once and retries before
   rejecting; `403` → the `EntitlementsDenied` 403 path; `5xx` / timeout →
   `_unavailable` (503), as for the JWT path;
4. build the identity from the answer: `user_id = subjectId`,
   `metadata.azp = clientId`, `api_key = f"cgk:{keyId}"`, plus the same
   `object_permission`, entitlements metadata and usage context as a JWT;
5. apply the same `_is_client_route` guard (users only reach LLM and MCP
   routes);
6. never log the key; `keyId` and the masked key are the only identifiers that
   may appear in logs.

No cache: the resolver call for a key bypasses `self._cache` (PK-5). The
machine token cache (`_access_token`) is unaffected.

`litellm/entitlements.py` gains a `resolve_key(key)` entry point that posts to
the personal-keys endpoint and reuses `_parse`; `Entitlements` gains
`key_id: str = ""`.

## 9. Usage attribution

- `decisionPayloadSchema` gains `key: z.string().uuid().optional()`; `verifyDecision`
  keeps failing on an unknown version or shape.
- `resourceUsageRecords` gains `gatewayKeyId: uuid("gateway_key_id")
  .references(() => personalGatewayKeys.id, { onDelete: "set null" })` — the
  ledger outlives the key.
- `POST /api/internal/gateway/usage` copies `decision.key` into the record when
  present; the request body is unchanged.
- Per-key aggregation is a consumer concern (raiversed) and is not part of this
  spec.

## 10. Error codes

New `KEY_` domain in `src/errors.ts`, following the existing pattern; the
AGENTS.md domain list gains `KEY_`.

| Code     | Status | Meaning                                                        |
| -------- | ------ | -------------------------------------------------------------- |
| `KEY_001` | 401    | Malformed, unknown or revoked gateway key                       |
| `KEY_002` | 404    | Gateway key not found (or owned by someone else)                |
| `KEY_003` | 400    | Invalid gateway key payload                                     |
| `KEY_004` | 403    | Membership, application or organization admission failed        |
| `KEY_005` | 409    | Active-key limit reached                                        |

The full key never appears in an error, a log line or a response other than the
create payload.

## 11. Configuration

| Variable                                | Default | Meaning                                        |
| --------------------------------------- | ------- | ---------------------------------------------- |
| `PERSONAL_GATEWAY_KEYS_MAX_PER_USER`    | `20`    | Active keys one user may hold                   |
| `PERSONAL_GATEWAY_KEYS_ENABLED`         | `true`  | Feature switch; `false` refuses create and use  |

No new secret. The hook needs no new environment variable: the personal-keys
endpoint lives under the same `GATEWAY_ENTITLEMENTS_URL` base.

## 12. Testing

Unit (co-located, `app.inject()`):

- key generation, hash, mask and format validation;
- create: label/org validation, limit, application binding;
- list: masked output, active only, ownership scoping;
- revoke: idempotent, foreign key → 404;
- machine endpoint: unknown/revoked → 401, banned user → 403, non-member → 403,
  pool → narrowed lists, whole network → full lists, empty → sentinels;
- decision token: `key` optional, verified and copied to the usage record.

Integration (`src/tests/*.integration.test.ts`):

- full lifecycle with a session and with a bearer caller;
- key usable after creation, dead immediately after revoke;
- leaving the organization invalidates a pool key's reach;
- usage ingestion with and without `key`.

Hook (`tests/litellm/`, `pnpm test:litellm`):

- `cgk_` branch: identity built from the answer, sentinels on empty lists,
  no cache between two resolutions, `_is_client_route` guard, malformed/401/403/5xx
  mapping, no key in logs.
